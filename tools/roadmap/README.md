# Инструменты ROADMAP (REPO-012)

`roadmap.py` проверяет [`docs/ROADMAP.md`](../../docs/ROADMAP.md) и выдаёт задачи, которые можно брать.
Только стандартная библиотека Python ≥ 3.10, без зависимостей.

| Команда | Что делает |
|---|---|
| `just roadmap lint` | Проверка файла; код возврата 1 при ошибках. Входит в Definition of Done (§0.3) и в CI |
| `just roadmap next` | Открытые задачи, у которых все `deps` отмечены `[x]` и нет открытого PR с `[ID]` в заголовке |
| `just roadmap next CORE PLAY-AND` | То же, только для указанных workstream |
| `just roadmap next --offline` | Без запроса к GitHub (`gh` не нужен) |
| `just roadmap next --json` | Машиночитаемый список для запуска волн агентов |
| `just roadmap issues sync` | Read-only план синхронизации только для задач из `good_first_issues.txt` |
| `just roadmap issues sync --apply` | Создать issues для готовых, вручную проверенных задач и закрыть устаревшие |
| `just roadmap test` | Unit-тесты инструмента |

`size: S` не означает, что задачу можно отдать новичку. Добавляйте ID в
`good_first_issues.txt` только после проверки: задача ограничена по объёму,
самостоятельна, не требует решения владельца, специальных ключей или
оборудования, настройки внешнего сервиса и не затрагивает рискованный код.
Пустой список означает, что синхронизация ничего не создаёт и не закрывает.

## Что проверяет `lint`

Ошибки (lint красный):

- строка задачи имеет вид `- [ ] **ID** Название` (или `- [x]`, или зачёркнутая отменённая задача); ID уникальны;
- ID стоит в разделе своего workstream (`### 3.N. CORE — …`);
- у каждой неотменённой задачи есть строки `Что:`, `deps:` и `done when:`; строка `deps:` имеет формат
  `deps: … · size: S|M|L · parallel: yes|no · веха: MN · ref: …`;
- все ID в `deps` и в пометке `(blocked: …)` существуют, не указывают на саму задачу и на отменённые задачи;
- в графе зависимостей нет циклов;
- у задачи `[x]` все зависимости тоже `[x]` (для задач `(owner)` — только предупреждение: владелец
  может принять решение раньше, чем закрыто исследование, которого оно ждало);
- задача не зависит от задачи более поздней вехи.

Предупреждения (lint зелёный): повтор одинаковой строки поля и расхождение таблицы
«Сводка по количеству задач» с фактическим числом задач.

Блоки кода (```` ``` ````) игнорируются, поэтому пример формата в §0.1 не считается задачей.

## Как `next` выбирает задачи

Задача попадает в список, если она открыта, не отменена, не помечена `(owner)`, все её `deps`
и блокеры из `(blocked: …)` отмечены `[x]`, и среди заголовков открытых PR нет `[ID]`
(запрос `gh pr list --state open`). Если `gh` нет или он не авторизован, выводится
предупреждение, и фильтр по PR не применяется.

## Прогресс: три бара

```bash
python3 tools/roadmap/roadmap.py progress --platforms
```

- **Система** — задачи вне экспериментальных вех и вехи подписки; рядом — «по объёму» (вес S = 1, M = 3, L = 8). Под ней — разбивка по размеру задач (S/M/L, сколько готово к работе прямо сейчас), задачи, которые ждут владельца, и прогресс по темам (ядро и источники, распознавание, плеер, интерфейс и ТВ, синхронизация и сервер, музыка, Twitch, дистрибутив, сборка и релизы, качество и тесты, документы и право, заготовки подписки) с числом готовых S/M/L. `--short` — только основные шкалы, `--deep` — ещё и каждый workstream внутри темы; вывод — дерево: корень «Kinolune» (весь план) → «Система» (размеры, темы, ждут владельца) → «Эксперименты», «Подписка», «Проверки»; 100 % здесь значит, что система готова.
- **Эксперименты** — вехи M11 (Apple Watch, visionOS) и M12 (ТВ-оболочка дистрибутива).
- **Диски** — веха M14: воспроизведение и копирование физических дисков, лицензия AACS — последним (ADR-0139).
- **Баги** — раздел BUG (§3.27, `docs/qa/bugs.md`): исправлено из найденных, открытые P0/P1/P2 и список открытых ошибок; в «Систему» не входит.
- **Подписка** — веха M13: запуск Kinolune+ после 100 % и появления аудитории (ADR-0136); заготовки SUB-002…SUB-008 входят в «Систему».
- **Проверки** — ячейки `docs/qa/test-catalog.md` (QA-014), проверенные на реальных устройствах (✅) из всех применимых; `🤖` — только автотесты; `--platforms` показывает разбивку по платформам. Полноту каталога проверяет `python3 tools/qa/check_catalog.py`: каждый `Key`/пункт меню из `lib/` есть в каталоге или в `tools/qa/catalog_allowlist.txt`.

Выбор задач под лимиты: `python3 tools/roadmap/roadmap.py next --size S` — только маленькие (когда лимит почти исчерпан), `--size L` — большие (после сброса); флаг можно повторять (`--size S --size M`).

**Прогноз** (строка под «Системой»): оставшийся объём системы (веса S/M/L) делится на объём, закрытый в день за последние `--window` дней (по умолчанию 3; по истории `docs/ROADMAP.md` в git, последний коммит каждого дня). Число пересчитывается при каждом запуске и меняется вместе со скоростью: при паузах и низких лимитах дата уезжает, при разгоне — приближается. Это ориентир, а не обещание.

## Страница прогресса

Живая страница со всеми задачами (REPO-015): **<https://github.com/DenisHumen/kinolune/blob/progress/README.md>** — открывается на github.com и в мобильном приложении GitHub. Она лежит в отдельной ветке `progress` без общей истории с `main` (там только `README.md`, `index.html` и `NOTE.txt`), поэтому PR не конфликтуют из-за неё. Ветку обновляет workflow [`progress.yml`](../../.github/workflows/progress.yml): на каждый push в `main`, на открытие, закрытие, переименование и готовность PR, раз в 3 часа и вручную (`gh workflow run progress.yml`). Коммит делается, только если содержимое изменилось; каждый раз ветка заменяется одним свежим коммитом.

Собрать локально (в игнорируемый `.progress/`):

```bash
python3 tools/roadmap/roadmap.py page --out .progress   # или: just roadmap page
```

`index.html` — та же страница для браузера: без внешних скриптов и шрифтов, светлая и тёмная тема, фильтр по статусу и поиск. Открытые PR берутся из `gh pr list`; без `gh` статус «в работе» не показывается (с пометкой на странице), для тестов — `--prs FILE` с JSON от `gh pr list --json number,title,headRefName,isDraft,url`.

Статусы:

| Статус | Когда |
|---|---|
| ⚪ не начато | `[ ]` и нет открытого PR |
| 🔵 в работе | `[ ]` и открыт PR с `[ID]` в заголовке или с веткой `тип/ID-…` (`feat/ID-…`, `fix/ID-…`) |
| 🟡 сделано, не проверено | `[x]`, но проверки задачи в каталоге не все ✅ |
| ✅ готово | `[x]` и все проверки задачи на устройствах ✅ |

**Как строка каталога относится к задаче.** В `docs/qa/test-catalog.md` нет колонки задачи. Строка считается проверкой задачи, если ID задачи написан в самой строке, в заголовке её раздела (`##`/`###`) или в абзаце-введении раздела («Первый запуск в три шага (UI-042)» — тогда к задаче относятся все строки раздела). Строки «Автотесты: …» не считаются; ID строк каталога (`SRC-120` и т. п.) отбрасываются, потому что таких задач нет. Проверка пройдена, когда все применимые ячейки (не `—`) — ✅; `🤖` — это автотесты, а не устройство. Сейчас так связаны только два-три десятка задач. Задача `[x]` без строк в каталоге из workstream, результат которых виден на устройстве (`DEVICE_WORKSTREAMS` в `progress_page.py`: ядро, сеть, медиатека, плеер, интерфейс, ТВ, музыка, Twitch, дистрибутив, упаковка, баги и др.), остаётся «сделано, не проверено»: ничто не показывает, что её проверили. Задачи `[x]` остальных workstream (решения, репозиторий, CI, документы, право, сайт, сообщество, QA-инструменты, заготовки подписки) — «готово»: проверять на устройстве нечего. Чтобы статус стал точнее, пишите ID задачи в строке или во введении раздела каталога.
