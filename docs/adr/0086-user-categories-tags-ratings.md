# ADR-0086: Свои категории, теги и оценки 1–5 — у каждого профиля свои, в «пространстве» библиотеки; фильтр и сортировка в запросах только по видимому

- **Статус:** Предложен
- **Дата:** 2026-11-15
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-022, LIB-009, LIB-010, LIB-012, UI-025, SYNC-009; [ADR-0055](0055-profiles-parental-filters.md) (профили и родительский контроль), [ADR-0079](0079-media-matching-across-devices.md) (ключи между устройствами)

## Контекст и проблема

Владелец хочет раскладывать медиатеку по-своему: свои категории (создать, переименовать, удалить, один элемент — в нескольких), теги (несколько на видео, с автодополнением) и оценка 1–5 звёзд; фильтр и сортировка по всем трём в любой медиатеке. На этом строится UI-025 «Личные медиа»: личные библиотеки с замком (PIN, пароль), в которые попадают нераспознанные файлы — у них нет ни произведения, ни TMDB id.

Вопросы: чьи это данные (профиля или всей семьи), как не выдать через них то, что профиль видеть не должен (ADR-0055), как отделить метки личных библиотек от основной и как это потом синхронизировать.

## Факторы решения

- Скрытое профилем не должно появляться ни через один API (ADR-0055): ни в списках, ни в счётчиках, ни в автодополнении.
- Оценка — мнение человека; категории и теги часто тоже личные («посмотреть с N», «скучно»).
- Название тега само по себе может выдать содержимое («ужасы», «для взрослых»).
- Нераспознанный файл должен принимать метки так же, как фильм.
- Схема — только расширение (expand-only), миграции из диапазона LIB-022.
- Синхронизация должна ложиться на модель `pa-sync` (LWW-регистры по стабильным id, ADR-0079), не на локальные `id`.

## Рассмотренные варианты

1. **Всё общее на семью** (как коллекции TMDB, `profile_id = NULL`). Удобно раскладывать вместе, но детский профиль видит названия тегов и категорий взрослых, а оценка одного становится оценкой всех.
2. **Оценки по профилю, категории и теги — общие.** Меньше дублирования, но та же утечка названий и спор, чья категория.
3. **Всё по профилю** (как избранное, коллекции пользователя, плейлисты LIB-010). Названия не пересекают профили; у семьи, которой нужна общая раскладка, — один профиль.
4. Категории как ручные коллекции LIB-010 (`collections.kind = 'manual'`). Коллекция — упорядоченный список с позициями и внешними TMDB-коллекциями; категория — измерение фильтра без порядка. Смешивать — значит усложнить обе.

## Решение

Вариант 3.

**Схема** (миграция `202611300000_LIB-022_categories_tags_ratings`, `pa_library::labels`):

- `user_categories` (`profile_id`, `space`, `sync_id`, `name`, `name_key`, `position`) и `user_category_items`;
- `user_tags` (`profile_id`, `space`, `name`, `name_key`) и `user_tag_items`; тег живёт, пока он есть хоть у одного элемента;
- `user_ratings` (`profile_id`, элемент, `stars` 1–5).

Элемент — как в списках LIB-010: произведение (`work_id`: фильм, сериал целиком) или стабильный `media_key` (эпизод, трек, **нераспознанный файл** — `file:<OSHash>`). В `pa-catalog` цель метки — `LabelTarget`: элемент каталога или `file:`-ключ любого файла с отпечатком; ключ распознанного файла ставит метку на его элемент.

Имена сравниваются по `name_key` (обрезано, пробелы схлопнуты, нижний регистр): «Sci-Fi» и « sci-fi » — один тег, показывается первое написание. Уникальность категории — по `(profile_id, space, name_key)`.

**Пространство (`space`).** `''` — основная медиатека. Каждая личная библиотека UI-025 получит своё пространство (`[a-z0-9_:-]`, до 64 символов): её категории и теги не видны в основной и не попадают в её автодополнение. В `pa-catalog` это `Labels` — дескриптор над `LabelSpace` (`Catalog::labels()` — основная); UI-025 добавит вариант `LabelSpace` и выдаст дескриптор только после снятия замка. Оценки к пространству не привязаны: элемент лежит в одной библиотеке, и оценка идёт за ним.

**Видимость.** `pa-library` хранит только ссылки; фильтрует `pa-catalog`:

- категория считает и отдаёт только видимые профилю элементы и файлы (`file_allowed!` для нераспознанных);
- `tags()` и `suggest_tags()` возвращают только теги, у которых есть видимый элемент, со счётом видимых;
- вызовы про один элемент на скрытом отвечают `NotFound` — как на несуществующем;
- запросы LIB-009 (`LibraryFilter.categories` / `tags` / `ratings`, `SortField::UserRating`) и фасеты работают на индексе, в котором только видимые произведения; чужие категории в индекс не попадают, так что id чужой категории в фильтре ничего не находит.

**Фильтр и сортировка.** Внутри поля — ИЛИ, между полями — И (как в LIB-009); `ratings: [0]` — «без оценки». Сортировка по оценке: без оценки — в конце в обе стороны, равные — по названию. Фильтр относится к произведениям (фильмам и сериалам), то есть к тому, что перечисляют запросы; метки эпизодов фильтр сериала не наследует.

**Синхронизация** — отдельной задачей (SYNC-013): данные к ней готовы. Категории известны другим устройствам по `sync_id` (случайные 32 hex), теги — по `name_key`, элементы — по стабильным ключам ADR-0079 (`tmdb:movie:…`, `file:…` + `aliases`), а не по `work_id`. Оценка ложится на существующую операцию `rating.set` (`0..=10`): звёзды × 2. Для категорий и тегов нужны новые виды операций; старые узлы не разбирают незнакомый `op`, поэтому порядок включения — решение для SYNC-013.

## Последствия

- Плюсы: никакой утечки названий между профилями; общее правило видимости для всех трёх; личные медиа UI-025 получают метки без изменений схемы, в том числе для нераспознанных файлов.
- Минусы: семья, которая хочет общую раскладку, делает её в одном профиле; удалённое произведение (`ON DELETE CASCADE`) теряет метки, как и избранное — при перераспознании в новое произведение метки остаются на старом и уходят вместе с ним.
- Подсчёт видимых элементов категории и тега идёт по каждой записи (нужно для правила видимости); при сотнях тегов и тысячах меток это миллисекунды, при росте — кэш по `Stamp` индекса.
