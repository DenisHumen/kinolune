# ADR-0104: Аниме по кадрам через trace.moe — запасной путь только по согласию, 5–10 кадров на файл, решение при ≥ 90 % согласия, результат по отпечатку файла

- **Статус:** Предложен
- **Дата:** 2026-11-17
- **Решают:** владелец проекта (вопросы решены агентом по правилу «максимально просто для клиента»), мейнтейнер (детали)
- **Связано:** META-031, META-016, META-015, META-030, LIB-025; [ADR-0101](0101-review-inbox.md), [ADR-0103](0103-content-kind-classifier.md)

## Контекст и проблема

Часть аниме не распознаётся ни по имени файла, ни по папке, ни по встроенной базе аниме (META-030), ни по TMDB, AniList и Shikimori: сквозная нумерация через сезоны, сокращённые или транслитерированные названия, «голые» папки. Такие работы попадают в инбокс «На проверку» (META-016), и пользователь решает руками.

trace.moe находит сцену аниме по одному кадру: AniList ID, эпизод (в порядке AniList) и время. Это сторонний сервис, а кадры — содержимое файлов пользователя. Бесплатный тариф без ключа (ключа у владельца нет): 100 поисков за скользящие сутки, один запрос за раз, 100 запросов в минуту на IP; 402 — квота кончилась или второй параллельный запрос, 429/503/504 — подождать (docs/legal/providers.md, trace.moe).

Нужно решить: когда спрашивать, сколько кадров и каких, как голосовать, что писать в библиотеку, как получать согласие и как беречь квоту.

## Факторы решения

- Приватность: ни одного кадра без явного согласия; «Мои видео», «Личное» и закрытые библиотеки не уходят никуда.
- Простота для пользователя: один переключатель; результат сам появляется в библиотеке или в «На проверку», без новых экранов.
- Точность: неверное «авто» хуже, чем лишний вопрос в инбоксе. API само говорит, что совпадения ниже 0,9 «скорее всего неверны».
- Квота 100 поисков в сутки на всё устройство: 10 файлов в день в худшем случае.
- Тесты без сети: записанные ответы.

## Рассмотренные варианты

1. **Запасной путь в ядре (`pa_catalog::frame_search`) после прогона метаданных: только аниме из инбокса, 5–10 кадров на файл, голосование с порогом 90 %, результат по отпечатку файла; переключатель согласия в настройках, по умолчанию выключен.**
2. Кадры для всех нераспознанных видео, включая фильмы и сериалы: trace.moe знает только аниме — кадры ушли бы из устройства зря, квота кончилась бы на чужом.
3. Один кадр на файл: дёшево, но одна сцена-флешбэк или общий опенинг франшизы даёт уверенный неверный ответ.
4. Поиск по вектору ColorLayout (`trace.moe-id`, до 10 векторов в одном запросе): меньше трафика и кадр не покидает устройство в виде картинки, но нужна своя реализация MPEG-7 ColorLayout на Rust и сверка с JS-эталоном; квоту тратит так же (по поиску на вектор). Отложено.

## Решение

Выбран вариант **1**.

**Когда.** Работы вида `anime` в инбоксе «На проверку» (`auto_review` или «не найдено»), без решения пользователя, NFO и «Это не фильм». Файлы — только видео с типом содержимого `video` (LIB-025), не «Личное», не пропавшие, с отпечатком. Сериалы и фильмы вида `show`/`movie` не отправляются: даже если это аниме с русским названием, база аниме и AniList их уже видели, а риск отправить живое кино выше выгоды. Ищется по файлу за раз, до двух файлов работы за прогон; как только один файл дал ответ — работа решена.

**Кадры.** Позиции — середина файла: эпизод до часа — от 20 % до 85 % длительности (мимо опенинга, эндинга и анонса следующей серии), длиннее — 10–90 %. Порядок — последовательность ван дер Корпута (1/2, 1/4, 3/4, 1/8 …): первые кадры далеко друг от друга, следующие — между ними. Ключевой кадр в точке декодирует `pa-probe` (наш LGPL FFmpeg, как trickplay) в 640 пикселей шириной — рекомендованный trace.moe размер, JPEG качества 85. Пропускаются: чёрные (средняя яркость < 20), тёмные с редким светлым — титры на чёрном (> 85 % тёмных пикселей) и плоские — затемнения, вспышки (СКО яркости < 10), а также повтор уже взятого ключевого кадра (ближе 2 с). На каждый нужный кадр — до трёх позиций.

**Голосование.** Лучший результат кадра голосует за свою запись AniList и эпизод, если `similarity` ≥ 0,9; слабый результат или пустой ответ — кадр «против». От 5 кадров: запись с ≥ 90 % голосов от всех отправленных кадров — совпадение (5 из 5, 9 из 10). Кадры добавляются до 10; поиск останавливается раньше, как только 90 % стало недостижимо даже если все оставшиеся кадры проголосуют за лидера (две разные записи и один пустой кадр — уже конец, 3 поиска вместо 10). Эпизод берётся, если ≥ 90 % голосов победителя называют один и тот же; иначе название ставится, а эпизод остаётся из имени файла. Эпизод trace.moe — `episode_start`, если файл у него одна серия; иначе целое `episode` (aniep).

**Совпадение (≥ 90 %).** В одной транзакции: прежние данные провайдеров работы убираются (как при выборе в инбоксе), работа получает AniList ID (если ID уже у другой работы — сливается с ней), автоматические матчи её файлов становятся `auto` с согласием как `confidence` и кадрами в `explanation_json` (`trace_moe`: AniList, эпизод, доля, число кадров), найденный файл получает эпизод в сезоне 1 (порядок AniList), `work_metadata` стирается. Следующий прогон метаданных читает AniList по ID и **не** ищет TMDB по именам, которые уже не нашлись (`WorkInfo.frames`), — иначе слабый результат TMDB вернул бы работу в `auto_review`. В приложении прогон метаданных сам запускает поиск по кадрам в конце и, если что-то совпало, сразу ещё один прогон метаданных — название, обложка и серия появляются без действий пользователя.

`decided_by` остаётся `scorer` (новое значение потребовало бы пересобрать таблицу `matches` из-за CHECK); источник решения виден в `explanation_json` и в `frame_searches`.

**Иначе — на проверку.** Работа остаётся в инбоксе; записи AniList, которые назвали кадры, показываются там кандидатами `anilist` с долей кадров как оценкой и строкой «Почему: совпало N % кадров (trace.moe)». Выбор такого кандидата — окончательное решение пользователя (`review_choose` принимает `anilist` для работ вида `anime`).

**Согласие.** Один переключатель в «Настройки → Метаданные», под базой аниме: «Распознавать аниме по кадрам», подпись «До 10 кадров нераспознанной серии уходят на сервис trace.moe». По умолчанию выключен. Хранится в настройках приложения (`metadata_anime_frame_search`), передаётся в ядро с каждым прогоном (`CoreMetadataSettings.anime_frame_search`); ядро без `FrameSearchOptions::consent` возвращается сразу — не читает файлов, не спрашивает даже квоту. В политике конфиденциальности — строка trace.moe в §4.

**Квота и лимиты.** Без ключа. Один запрос за раз и не чаще раза в секунду; на 402 «параллельный запрос», 429, 500/502/503/504 — повтор с отступом (2, 4, 8 с, `Retry-After` уважается), после трёх повторов прогон останавливается. 402 «квота кончилась» не повторяется — прогон останавливается, следующий продолжит. Перед первым поиском прогона — `GET /me` (квоту не тратит): тратится не больше остатка и не больше 30 поисков за прогон; файл начинается, только если остатка хватает на 5 кадров. Отказ сервера разобрать картинку (400) — кадр не считается.

**Кэш.** Итог файла (`matched`/`review`/`no_frames`, AniList ID, эпизод, доля, число кадров, кандидаты) — таблица `frame_searches` по отпечатку содержимого (`files.fingerprint`): файл не ищется второй раз — ни после пересканирования и переноса, ни в новой базе с теми же файлами. Картинки, ссылки на превью trace.moe и имена наших файлов не хранятся.

## Последствия

- Хорошо: работы, которые раньше требовали ручного выбора, решаются сами с серией; несогласованные ответы не становятся тихой ошибкой, а подсказывают кандидатов в инбоксе; без согласия поведение не меняется.
- Плохо: на бесплатной квоте — около 10–20 файлов в сутки; остальные ждут следующих прогонов. Эпизод получает только найденный файл; остальные файлы работы сохраняют номера из имён (поиск каждой серии съел бы квоту). Работы вида `show` не ищутся по кадрам.
- Записанные ответы (`pa-catalog/tests/fixtures/trace_moe/*.jsonl`) синтетические, в форме настоящих: при изменении API trace.moe тесты этого не заметят — нужна ручная проверка на живом сервисе (владелец, с включённым переключателем).
- Вариант 4 (вектор ColorLayout вместо картинки) — возможное улучшение приватности и трафика позже.
- Свой ключ trace.moe (из ROADMAP: «опционально») не добавлен: по условию задачи достаточно одного переключателя; поле ключа можно добавить позже, клиент к нему готов (заголовок `x-trace-key` не отправляется сейчас вовсе).
