# ADR-NNNN: Музыка на Android переживает смахивание приложения — движок Flutter принадлежит процессу, а не `MainActivity`; видео без PiP в фоне ставится на паузу

- **Статус:** Предложен
- **Дата:** 2026-11-15
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `PLAY-AND-008`, `MUS-003`, `MUS-011`, `TWI-009`; [ADR-0065](0065-android-media-session-bridge.md) (дополняет раздел «Не входит»), [ADR-0063](0063-music-queue-per-profile-prefs.md), [ADR-0012](0012-release-0-1-player-media-kit.md)

## Контекст и проблема

ADR-0065 подключил Media3 `MediaSessionService` с мостом `SimpleBasePlayer` к нашему libmpv, но плеер, очередь и весь Dart-код живут в движке Flutter, которым владеет `FlutterActivity`. Смахнули приложение из «Недавних» — активность уничтожается, движок вместе с ней, сервис ставит паузу и останавливается. Для плеера «как Spotify» это не годится.

Решения владельца:

1. Музыка продолжает играть после смахивания, уведомление и экран блокировки по-прежнему ею управляют, а открытое снова приложение показывает живую очередь и позицию.
2. Видео, которое ушло в фон без окна PiP (PiP выключен или не поддержан, Android TV), ставится на паузу, а не играет дальше.

## Факторы решения

- Один движок воспроизведения (libmpv): gapless, ReplayGain, правка плейлиста на месте (MUS-002, MUS-003), сетевые источники через `pa-vfs` и loopback-прокси (ADR-0038) — всё это уже работает в Dart.
- Лицензия: без новых зависимостей, без GPL.
- Без утечек: движок без UI живёт ровно столько, сколько его держит музыка.
- Повторное открытие показывает то же состояние, а не восстановление из настроек.

## Рассмотренные варианты

1. **Один движок Flutter на процесс** (`KinoluneEngine`): `MainActivity` берёт его через `provideFlutterEngine` и не уничтожает (`shouldDestroyEngineWithHost = false`); пока музыка держит медиасессию, движок живёт без активности, новая активность подключается к нему же.
2. Отдельный фоновый движок или изолят, которым владеет `MediaSessionService`, только для музыки: очередь и libmpv переезжают туда, UI говорит с ним по каналу.
3. Перевести музыку на Media3 ExoPlayer внутри сервиса: нужен свой `DataSource` поверх `pa-vfs` / прокси, нет части форматов libmpv, второй движок, теряются MUS-002 / MUS-003.

## Решение

Выбран **вариант 1**. Он не дублирует плеер, очередь и сетевой стек: продолжает играть тот самый `MusicPlayerController`, и UI при повторном открытии просто снова рисует его состояние. Вариант 2 требует разделить приложение на два изолята с синхронизацией очереди, профилей (ADR-0063) и прокси — много кода ради того же результата; при этом память процесса почти та же, потому что основную часть занимают libmpv и ядро на Rust, а не виджеты. Вариант 3 — второй движок и потеря решений ADR-0012 и MUS-002/003.

Конкретика:

- **`KinoluneEngine` (приложение, `app.kinolune`).** Хранит движок и считает активности. Когда активность уничтожается (не из-за смены конфигурации), движок уничтожается сразу, если медиасессией не владеет музыка (`MediaBridge.keepsEngineWithoutUi()`, чистая `BackgroundPolicy`): без музыки всё как раньше. Если музыка играет или стоит на паузе, движок остаётся; Dart получает `AppLifecycleState.detached`, кадры не рисуются, таймеры, libmpv и каналы работают. Когда сессия заканчивается без активности (уведомление смахнули после паузы, очередь остановлена), движок уничтожается через 5 с: Dart успевает сохранить очередь (MUS-003). Multicast-lock mDNS живёт столько же, сколько движок; обработчик канала `app.kinolune/device` снимается в `cleanUpFlutterEngine`, чтобы движок не держал старую активность.
- **`PlaybackService.onTaskRemoved`.** Музыка — ничего не делает (сервис остаётся на переднем плане, пока играет); видео или live — команда `stop` в Dart, сессия снимается, сервис останавливается.
- **Команда `stop` у музыки** (смахнули уведомление на паузе — Media3 шлёт stop) ставит паузу и снимает захват сессии, но не очищает очередь: следующее «Play» возвращает уведомление; приложение без UI отпускает движок.
- **Видео в фоне.** `PlayerScreen` ставит паузу на `AppLifecycleState.hidden` / `paused`, если не открыто окно PiP (`SystemPip.active`); в PiP активность только на паузе (`inactive`) и видео идёт. Само не продолжается: пользователь нажимает Play. Параметр `pauseInBackground`, по умолчанию на Android и iOS.
- Фоновый движок workmanager (TWI-009) — отдельный и сессией не владеет (ADR-0065), его это не касается.

### Последствия

- Хорошо: Spotify-подобное поведение без второго плеера; уведомление, экран блокировки и кнопки гарнитуры работают и после смахивания; повторное открытие показывает ту же очередь, трек и позицию без восстановления.
- Хорошо: без музыки жизненный цикл прежний — движок уходит вместе с активностью.
- Плохо: пока играет музыка без UI, в памяти остаётся весь Dart-код приложения (виджеты не рисуются). Замер памяти — отдельно (QA).
- Плохо: если система всё же убьёт процесс (нехватка памяти, агрессивные прошивки), музыка останавливается; при следующем запуске очередь восстанавливается из настроек (MUS-003) на паузе. Возобновление по кнопке гарнитуры после смерти процесса (`onPlaybackResumption`, `MediaButtonReceiver`) — не здесь.
- Плохо: состояние UI (открытые экраны) переживает смахивание, пока играет музыка; это ожидаемо для плеера, но отличается от «чистого» запуска.

### Как проверяем соблюдение

- JUnit плагина `pa_player`: `BackgroundPolicyTest` (`./gradlew :pa_player:testDebugUnitTest` из `clients/flutter/app/android`).
- `flutter test` в `pa_player`: `test/media_session_test.dart` — `stop` снимает сессию и оставляет очередь; видео встаёт на паузу в фоне без PiP и играет в PiP.
- Эмулятор: музыка играет, `adb shell am stack remove <task>` (смахивание из «Недавних») — через 60 с позиция идёт, `KEYCODE_MEDIA_*` и `cmd media_session dispatch` работают; повторный запуск показывает тот же трек и позицию; видео + Home без PiP — пауза. Скриншоты в `docs/screenshots/progress/play-and-008-swipe/`.
