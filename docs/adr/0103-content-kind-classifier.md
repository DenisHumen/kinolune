# ADR-0103: Тип содержимого решает чистый классификатор в `pa-recognition`, по папкам; «Мои видео» не уходят к провайдерам, «Это не то» запоминается у папки

- **Статус:** Предложен
- **Дата:** 2026-11-17
- **Решают:** владелец проекта (направление — [ADR-0099](0099-auto-content-type-personal-place.md)), мейнтейнер (детали)
- **Связано:** LIB-025, UI-034, MUS-018, LIB-002; [ADR-0098](0098-personal-media.md), [ADR-0099](0099-auto-content-type-personal-place.md)

## Контекст и проблема

ADR-0099 решил: тип содержимого пользователь не выбирает нигде. Ядро само определяет для каждого файла и папки фильм/сериал/аниме, ролик с телефона или камеры («Мои видео»), музыку или аудиокнигу. Ролики не отправляются в TMDB и другие базы, но и не прячутся. Ошибку исправляет одно действие «Это не то» у папки. До LIB-025 распознавание шло только для источников с `sources.content_type = 'video'`, музыка индексировалась по расширению, а аудиокниг и «Моих видео» не было вовсе.

Нужно решить, где живёт классификатор, на чём он основан, где хранится его решение и как оно сочетается с ручными решениями пользователя.

## Факторы решения

- Максимум автоматики: ни одного вопроса пользователю при добавлении источника.
- Приватность: ошибка «свой ролик ушёл в TMDB» хуже, чем «фильм оказался в „Моих видео“» (его возвращают одним нажатием). Тихих ошибок «фильм ↔ своё видео» — меньше 1 % (done when LIB-025).
- Качество меряется корпусом, как у распознавания фильмов, без сети и без настоящих путей пользователей.
- Миграции только расширяющие (LIB-002); существующее распознавание не ломается.

## Рассмотренные варианты

1. **Чистый классификатор `pa_recognition::content` по признакам пути и тегов, решение по папкам; результат — таблица `file_content_kinds`.**
2. Модуль рядом со сканером (`pa-scanner`): сканер знает пути и теги музыки, но не знает разбор имени релиза (год, сезон/серия, группа), который нужен, чтобы отличить фильм от ролика.
3. Классификация после запроса к TMDB («нет совпадений в базах» → своё видео): даёт лучшую точность для файлов без признаков, но отправляет имена личных роликов в сеть — противоречит ADR-0099.
4. ML-модель: нет размеченных данных пользователей, нужна бы большая модель на всех платформах; признаки и так сильные.

## Решение

Выбран вариант **1**: модуль `pa_recognition::content` (рядом с разбором имён, который он использует; без ввода-вывода), вызывается каталогом на каждом скане.

**Признаки видео** (положительный счёт — свой ролик, порог 3):

- имя камеры/телефона: `IMG_`, `VID_`, `MVI_`, `DSC`, `DJI_`, `GOPR`, `GX…`, `PXL_`, `P1…`, `C0001` (у коротких префиксов — минимум четыре цифры сразу), имена-даты `20240612_183000`, `2024-06-12 18.30.00`, `2024_0612_183000_001` (видеорегистраторы), `VID-20240612-WA0003`, записи экрана: +6;
- папка камеры (`DCIM`, `Camera`, `Camera Roll`, `WhatsApp Video`, `GoPro`, `Dashcam`, `Фото`, `100MEDIA`…): +3;
- теги контейнера, которые пишут телефоны и камеры (`make`, `model`, `com.apple.quicktime.*`, `com.android.*`): +7;
- против: сезон/серия −4, год −3, теги релиза (разрешение, источник, кодек, группа, HDR, издание) −3, дата эфира с названием −2. У имени камеры цифры не считаются серией или годом;
- папка, где больше половины файлов — ролики и нет ни одного релиза, забирает файлы без своих признаков (`Birthday.mp4` рядом с `VID_…`).

**Признаки аудио** (положительный — аудиокнига, порог 3): `.m4b`/`.aax` +6; главы в длинном файле +4; жанр `Audiobook`/`Speech`/`Spoken word`/«Аудиокнига» +6, музыкальный жанр −2; слова «аудиокнига», «читает», «чтец», `audiobook`, `narrated by`, `read by`, `unabridged`, «радиоспектакль» в пути и тегах +5; нумерация «Глава/Chapter/Kapitel N» +2,5; дорожка от 25 минут +1,5, короче 9 минут −1; слова релиза музыки в пути (`FLAC`, `320`, `OST`, `EP`, `Remaster`, `Discography`…) −1,5. Книга решается целиком: медиана длины по папке от 20 минут +2; 25+ дорожек в сумме от 5 часов +3; больше половины файлов с сильной уликой делают книгой всю папку. Файл с сильной собственной уликой (|счёт| ≥ 4) не подчиняется папке: один `.m4b` среди песен не делает их книгой.

**Хранение** (миграция `202612120000_LIB-025_content_kinds`, только расширение):

- `file_content_kinds`: `kind` (действует), `detected` (что сказал классификатор), `version`, `score`, `reasons_json` — для объяснения;
- `folder_content_overrides`: «Это не то» у папки; самая длинная папка побеждает, действует на файлы того же носителя;
- `files.embedded_tags_json` (колонка была, но не заполнялась): `pa-probe` пишет туда только ключи камеры/телефона и число глав; координаты не хранятся — вместо значения `"1"`.

**Скан:** после анализа контейнера и отпечатков `pa_catalog::content_kind::classify` решает все файлы источника папка за папкой и пишет изменившиеся строки. Распознавание (`recognize::run`) берёт только видео без строки или с `kind = 'video'`; ограничение `content_type = 'video'` снято. Значения `sources.content_type` `video` и `music` теперь только история: видео в бывшем «музыкальном» источнике тоже распознаётся, если похоже на релиз. `personal` по-прежнему делает источник личным (ADR-0098), такие файлы не классифицируются. Файл, ставший `own_video`, теряет автоматический матч (`auto`/`auto_review`, не `user`/`nfo`); матч пользователя или из NFO оставляет файл видео — ручное решение сильнее классификатора.

**«Мои видео»** (`Catalog::own_videos`): файлы `own_video` основной медиатеки без живого матча, видимые профилю (`file_visible!`), новые сверху; воспроизведение — через обычные `play_parts`. Не прячутся и не запираются: «Скрыть в Личное» — отдельное действие пользователя (ADR-0099 §3, UI-034).

**Аудиокниги** — дорожки музыкальной медиатеки с `MusicTrack.audiobook`; в приложении — раздел «Аудиокниги» внутри «Музыки» (книги по альбомам), из «Главной» и «Медиатеки» музыки они убраны. Отдельная вкладка — MUS-018.

**«Это не то»** (`Catalog::not_this`): одно действие у папки в обзоре источника. Основной тип файлов папки меняется на другой тип того же носителя (`video` ↔ `own_video`, `music` ↔ `audiobook`) и запоминается. Повторное нажатие возвращает определённый тип и удаляет строку переопределения. Сразу после — перераспознавание источника, так что фильм появляется в медиатеке без нового скана. Форм нет.

**Не входит:** «Скрыть в Личное» рядом с «Моими видео» (UI-034/UI-035), отдельная вкладка аудиокниг (MUS-018), акустическое распознавание (MUS-017), повторный анализ контейнера уже проанализированных файлов ради тегов камеры (теги появятся у новых и изменённых файлов; имена и папки работают сразу).

### Качество на корпусе

Корпус — `core/crates/pa-recognition/tests/data/content_corpus.jsonl` (генератор рядом, `gen_content_corpus.py`): 453 выдуманных пути с тегами — фильмы (в том числе без года и тегов, с «опасными» названиями `Pi`, `Clip`, `The Camera Roll`), сериалы, ежедневные шоу с датами, аниме, альбомы (классика с частями по 25 минут, DJ-миксы на час, компиляции), аудиокниги (m4b, папки по 30 частей без тегов, «читает», главы, жанр Speech, радиоспектакль, курс), ролики с телефонов, камер, дронов, видеорегистраторов, записи экрана, и смешанные папки (`Downloads`, `Telegram Desktop`). Тест `content_corpus` решает файлы по папкам, без участия пользователя.

| | Первый прогон | После правок |
|---|---|---|
| Верно | 438 из 453 (96,7 %) | **443 из 453 (97,8 %)** |
| «Фильм ↔ своё видео» | 5 (1,10 %) | **2 (0,44 %)** |

Правки после первого прогона: имена видеорегистраторов `2024_0612_183000` (известная схема, сначала не учтённая) и ошибка, при которой один сильный файл (`.m4b`) тянул за собой слабые файлы папки. Оставшиеся ошибки честные: книга, нарезанная на короткие дорожки без тегов и слов в пути (8 файлов → музыка), и два ролика, экспортированных из редактора без тегов в обычную папку (→ фильм; уходят в распознавание, у TMDB совпадения обычно нет). Их исправляет «Это не то». Числа проверяет тест: ≥ 95 % и < 1 %.

### Последствия

- Хорошо: пользователь ничего не выбирает; один источник может содержать всё; ролики с телефона не уходят в сеть; решение объяснимо (`reasons_json`) и обратимо одним действием.
- Плохо: каждый скан заново решает все файлы источника (чистые функции, пишутся только изменения). На библиотеке в десятки тысяч файлов это лишний проход по `files`; если станет заметно — решать только папки с новыми файлами.
- Плохо: ролик без признаков (переименован и пересохранён) классифицируется как фильм и его имя уходит в поиск TMDB, пока пользователь не нажмёт «Это не то». Лучше не сделать без запроса в сеть.
- В папке со смешанными носителями одно переопределение: «Это не то» по аудио заменяет переопределение по видео той же папки.

## Решения по открытым вопросам (2026-11-17)

Владелец поручил решать самим по правилу «всё максимально просто для пользователя».

1. **Старое значение `content_type = 'music'`** — подсказка, а не запрет. Видео в таком источнике распознаётся, если похоже на релиз.
2. **Ролик без признаков, который провайдер не нашёл, уходит в «Мои видео» сам.** Признаков релиза в имени нет: ни года, ни сезона, ни серии, ни даты, ни группы, ни студии, ни CRC. Тогда после прогона метаданных с исходом `not_found` файл становится своим роликом с причиной `not_found_untitled`. Задачей для проверки он не становится. Решение запоминается: такой ролик больше не распознаётся, поэтому исход `not_found` исчезает, а ролик остаётся. Вернуть его можно действием «Это не то». Фильм с годом, который не нашли, остаётся в «На проверку».
3. **«Это не фильм» (META-016) отправляет файлы работы в «Мои видео».** Каждый файл получает переопределение вида `own_video`, совпадения снимаются, работа без файлов удаляется. Повторное сканирование и полное обновление метаданных этого не меняют. Отменить можно через «Это не то».
4. **«Скрыть в Личное»:** долгое нажатие или правый клик по ролику предлагает перенести его папку в «Личное». Целый источник так не переносится: ролик в корне источника этого пункта не получает.
5. **Главный экран** с одними только своими роликами показывает ряд «Мои видео», а не «пусто».
