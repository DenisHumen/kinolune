# ADR-NNNN: Решать матч по трём состояниям и отдавать сомнительные в инбокс «На проверку» с кандидатами и объяснением

- **Статус:** Предложен
- **Дата:** 2026-11-17
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** META-016 (эта задача), META-013/014 (поиск и скорер, [ADR-0084](0084-scorer-pair-features-joint-group.md)), META-033 ([ADR-0096](0096-other-language-titles.md)), META-017 (правила папок), META-018 (обученный скорер), META-020 (LLM по opt-in), UI-025 ([ADR-0098](0098-personal-media.md)), `docs/research/03-metadata-recognition.md` §4.2 [7], §4.6

## Контекст и проблема

После META-033 результаты с оценкой 0,6–0,92 показываются с названием и постером в состоянии `auto_review`, но у пользователя нет места, где их подтвердить или исправить. Работы ниже 0,6 получают `not_found` и не видны вовсе. «Исправить распознавание» на странице фильма умеет только переименовать или принять ID TMDB, введённый руками. Замер на корпусе v0 показал 1,14 % тихих ошибок (уверенно и неверно) — выше цели ROADMAP (≤ 1 %), причём все они с уверенностью 1,0: порогом их не убрать.

## Факторы решения

- Тихие ошибки ≤ 1 % на dev-сплите, test не используется для подбора.
- Пользователь видит, почему приложение так решило, и исправляет одним нажатием.
- Решение пользователя окончательно: его не перерешают ни скан, ни новая версия парсера или скорера.
- Без своих серверов (ADR-0004); LLM — только по opt-in (META-020), по умолчанию выключен.
- Данные TMDB хранятся не дольше разрешённого (6 месяцев).

## Рассмотренные варианты

1. Поднять порог авто — не помогает: ошибки с уверенностью 1,0.
2. **Три состояния, сигнал «потерянное слово типа», кандидаты и объяснение в базе, инбокс в ядре.**
3. Только экран поверх существующего `fix_match` — нет кандидатов и объяснений, ручная очередь остаётся невидимой.

## Решение

Выбран вариант **2**.

**Состояния** (`pa_catalog::metadata`): оценка лучшего результата поиска `p ≥ AUTO = 0,92` — `auto`; `REVIEW = 0,70 ≤ p < 0,92` (без ничьей; от `ACCEPT = 0,75` — и при ничьей, с понижением) — `auto_review`, название и постер результата с пометкой «проверьте»; ниже — ручная очередь (`work_metadata.outcome = 'not_found'`), данных провайдера нет. LLM-фолбэк — META-020, выключен.

**Слово типа** (`lost_marker`): если в главном названии работы есть `ova`, `oad`, `ona`, `special(s)`, `sp`, `movie`, `film`, `gekijouban` или `recap`, а в совпавшем названии кандидата его нет, оценка названия не выше 0,85 — такой матч никогда не `auto`. Это убрало 42 из 44 тихих ошибок корпуса (`Fairy Tail OVA` → сериал `Fairy Tail`).

**Кандидаты и объяснение**: каждый поиск сохраняет до пяти взвешенных результатов в `work_candidates` (ID, название, оригинальное название, год, постер, описание, оценка) с `explanation_json` — сигналами (`MatchSignals`): сходство названия и ярус, совпавшее название, год файла и кандидата, тип, серии в сезонах (есть / нет), отклонение длительности, язык звука, провайдер, ничья, потерянное слово. У матча `matches.explanation_json.signals` — сигналы выбранного результата. Кандидаты перезаписываются каждым поиском и удаляются решением пользователя; это данные поиска TMDB, они обновляются вместе с метаданными и не синхронизируются.

**API инбокса** (`pa_catalog::review`, FRB `CoreLibrary.review_*`): количество; список (сначала «проверьте», от наименее уверенных, потом ручная очередь); запись по элементу; «Верно» (`user_confirmed`); другой кандидат или результат ручного поиска (`user_set`: данные прежнего результата удаляются, следующий прогон читает выбранный по ID, работа с тем же ID поглощает эту); ручной поиск по названию и году (ранжируется с признаками файлов, ничего не пишет); «Это не фильм» (`work_reviews.not_media`: файлы остаются в медиатеке под своими именами, провайдеров больше не спрашивают). Перенести в «Личное» — существующий UI-025. Решения пользователя не трогают `replan_outdated`, новый скорер и прогоны метаданных (`numbering::recomputable!` пропускает `user_*`).

**Приложение**: строка «На проверку» со счётчиком в Настройки → Медиатека, список, страница работы с кандидатами, постерами и строкой «Почему: …», «Верно», «Это оно», «Найти вручную», «Это не фильм и не сериал». «Исправить распознавание» на странице фильма или сериала открывает ту же страницу (без ядра — прежний диалог). Дизайн простой; редизайн — позже.

### Последствия

- Хорошо: тихие ошибки на train + dev 1,14 % → 0,05 % при том же Recall; test без изменений (0,32 %, 3); ручная очередь видна и решается; объяснение есть у каждого кандидата. Замер — `tools/recognition-eval/baselines/v0/meta016.md`.
- Плохо: OVA и фильмы франшизы, которые TMDB ведёт внутри сериала, теперь всегда «проверьте» (Coverage train + dev 94,06 % → 92,97 %); работы 0,60–0,70, которые META-033 показывал с названием, теперь в ручной очереди (с кандидатами).
- Нейтрально: нижний порог 0,70 взят из исследования — в синтетическом корпусе нет оценок 0,6–0,85; подобрать его по реальным данным — META-018. Таблицы `work_candidates` и `work_reviews` (миграция `202612090000_META-016_review_inbox`, только expand).

### Как проверяем соблюдение

- `pa-catalog/tests/review_inbox.rs` (состояния по порогам, кандидаты и сигналы, решения окончательны после пересканирования и полного обновления метаданных, «не фильм» снимает данные провайдера), `tests/other_language_titles.rs` (`lost_marker`, ручная очередь с кандидатом).
- `pa_library/test/review_inbox_test.dart` (на нативном ядре), `app/test/review_inbox_test.dart` (виджеты).
- Замер `pa-eval` — `meta016.md`.
