# ADR-NNNN: Импорт медиатеки v0: SMB-элементы по пути GVfs, ожидающий прогресс в своей таблице, пароли по ID источника v0

- **Статус:** Предложен
- **Дата:** 2026-11-15
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-015, UI-024, LIB-004, LIB-018; ADR-0032 (ключ `file:` — OSHash), ADR-0076 (отпечатки); `docs/dev/db.md` §«Переход с pa_library v0»

## Контекст и проблема

Импорт базы Dart-пакета `pa_library` v0 в схему v1 (`pa_catalog::Catalog::import_v0`) появился вместе с переходом приложения на Rust-ядро (UI-024) и переносил только локальные папки. Чего не хватало до критерия LIB-015 «все элементы и прогресс распознанных видны в v1»:

- элементы SMB-источников пропускались: v0 читал шару через GVfs-монтирование и хранил путь вида `/run/user/1000/gvfs/smb-share:server=nas,share=video/Movies/x.mkv`, а ядро обращается к шаре через `pa-vfs` по адресу `smb://nas/video`. Вместе с элементом терялся и его прогресс — даже у распознанного фильма с TMDB ID;
- прогресс нераспознанного элемента, файл которого нельзя прочитать при импорте (шара не смонтирована, диск отключён), выбрасывался: ключ `file:<OSHash>` нечем посчитать, а `db.md` обещал, что «запись ждёт в импорте»;
- адрес v0 `smb://user@host/share` попадал в `sources.uri` как есть, а `pa-sources` адреса с именем пользователя отклоняет — такой источник не подключался;
- пароли SMB приложение v0 хранило в `flutter_secure_storage` под ключом `smb_password_<ID источника v0>`, а перенос в хранилище ядра (`migrateLegacySmbPasswords`, LIB-018) искал ключ по ID ядра — после импорта ID другие, пароль не находился.

## Факторы решения

- Старый файл только читается; повторный запуск ничего не дублирует.
- Схема меняется только expand (новая миграция, новая таблица).
- Следующий скан через `pa-vfs` должен находить те же строки `files`, иначе матчи (в том числе исправленные вручную, `user_set`) пропадут.
- Импорт не монтирует шары и не ходит в сеть.

## Рассмотренные варианты

1. **Путь внутри шары из пути GVfs**, прогресс распознанных — по ключу `tmdb:` даже без файла, ожидающий прогресс — в отдельной таблице `import_v0_progress`, переносится сканом после отпечатков; пары «ID v0 → ID ядра» — в отчёте импорта для переноса паролей.
2. Пропускать SMB-элементы (как было) и ждать, пока скан найдёт файлы заново: теряются ручные исправления и прогресс нераспознанных; распознанный прогресс тоже, если локальное распознавание без ключа TMDB не найдёт тот же TMDB ID.
3. Ожидающий прогресс — в `progress` с временным ключом (`v0:<item_id>`): засоряет таблицу, которую синхронизирует `pa-sync`, и ряд «Продолжить».
4. Пароли — сопоставлять источники по адресу в Dart, читая резервную копию `*.v0.bak`: нужно повторить нормализацию адреса в Dart и читать SQLite v0 из приложения.

## Решение

Вариант 1.

- **SMB-источник:** имя пользователя из адреса уходит в `username` (если в v0 его не было, пароль из адреса отбрасывается), `uri` — нормализованный `pa_sources::SmbAddress` (`smb://host/share[/folder]`). Ранее импортированный источник с адресом «как в v0» находится и не дублируется.
- **SMB-элементы:** в пути ищется сегмент `smb-share:` с теми же `server` и `share` (без учёта регистра, с percent-декодированием — как сравнивал v0), затем папка источника; остаток — `files.path` (`/Movies/x.mkv`), такой же, какой запишет сканер `pa-vfs`. Путь, который так не разбирается, — элемент пропускается и считается (`items_skipped`).
- **Прогресс распознанных** пишется под `tmdb:movie:<id>` / `tmdb:episode:<show>:<s>:<e>` и тогда, когда файл не удалось сопоставить: следующий скан найдёт произведение по TMDB ID.
- **Ожидающий прогресс:** если файл нераспознанного элемента не прочитать (OSHash не посчитать), состояние кладётся в `import_v0_progress` (по `file_id`, каскадно с файлом). Скан после `fingerprint::fill_missing` и `follow_moves` вызывает `import_v0::apply_pending`: строки с готовым отпечатком переходят в `progress` под ключом `file:<fingerprint>` (побеждает более новое состояние) и удаляются. Повторный импорт обновляет строку, только если состояние v0 новее. Если SMB-шара смонтирована в момент импорта, файл хэшируется сразу через путь GVfs — значение OSHash то же, что даст `pa-vfs`.
- **Пароли:** отчёт импорта (`ImportReport::v0_sources`, в FRB — `CoreImportReport.v0Sources`) содержит пары «ID источника v0 → ID ядра». Приложение передаёт их в `AppServices` и `migrateLegacySmbPasswords` ищет пароль сначала под ID v0, затем под ID ядра, переносит в хранилище ядра и удаляет старые копии.
- **Не переносится:** `items.parsed_*` (следующий скан разбирает имена текущим парсером — гипотезы парсера v0 хуже и без версии), `tmdb_cache`, `settings`. Теги треков читает скан, который приложение запускает сразу после импорта.

## Последствия

- Хорошо: у пользователя со старой базой остаются SMB-элементы с ручными исправлениями и прогресс; источники с `user@` подключаются; пароль не нужно вводить заново.
- Плохо: пары ID живут только в памяти того запуска, в котором прошёл импорт. Если в этот запуск хранилище секретов не открылось, пароль v0 остаётся в `flutter_secure_storage`, но при следующем запуске связь уже не известна — пароль придётся ввести на экране «Источники».
- Плохо: прогресс, записанный импортом и `apply_pending`, идёт мимо `ProgressSink` — на другие устройства он уйдёт только со следующим изменением (как и раньше у импорта).
- Импорт пишет прогресс в профиль 1 (в v0 профилей не было).
- Пути SMB, которые v0 получал не через GVfs (например, ручное монтирование `/mnt/nas`), не сопоставляются: таких источников v0 не создавал.
