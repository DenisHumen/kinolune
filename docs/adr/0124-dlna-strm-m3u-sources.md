# ADR-0124: Серверы UPnP/DLNA, плейлисты M3U и файлы `.strm` — источники без входа поверх одного HTTP-файла с политикой ссылок

- **Статус:** Предложен
- **Дата:** 2026-11-18
- **Решают:** владелец проекта (поручил решать по правилу «максимально просто для клиента»), мейнтейнер
- **Связано:** NET-018, NET-011, NET-020, LIB-018, NET-007; [ADR-0013](0013-pa-vfs-blocking-positional-reads.md), [ADR-0019](0019-lan-discovery-mdns.md), [ADR-0038](0038-network-playback-loopback-proxy.md)

## Контекст и проблема

ROADMAP NET-018: «UPnP ContentDirectory browse; разбор `.strm` и плейлистов M3U как источников». Done when: тест против minidlna в Docker; M3U с HTTP-ссылками воспроизводится. Нужно, чтобы DLNA-серверы появлялись в поиске по сети и в «Добавить источник», а ссылки из `.strm` и M3U проходили те же правила безопасности, что и прочие адреса.

Источники в ядре — это `pa_vfs::Vfs` (папки и файлы) и `ByteSource` (файл с размером и чтением по смещению): скан, распознавание, пробинг и прокси воспроизведения работают одинаково для SMB, WebDAV, Jellyfin, Subsonic. Всё, что выдаёт DLNA-сервер или плейлист, — это файлы по HTTP-ссылкам.

Отдельной «политики SSRF» в проекте до этого не было: были правила «только `http`/`https`», «логин и пароль в адресе не принимаются», редиректы только на `http(s)` с лимитом (WebDAV). Плейлист и `.strm` — первые места, где адрес приходит не от пользователя, а из чужого файла, и приложение идёт по нему само.

## Факторы решения

- Для пользователя: DLNA-сервер находится сам и добавляется в одно касание, без логина; плейлист — одна ссылка или файл.
- Те же медиатека, распознавание, прокси и плеер, что у остальных источников; без своего пути воспроизведения.
- Ссылка из чужого списка не должна вести приложение в домашнюю сеть или на само устройство (роутер, NAS-админка, наш loopback-прокси, адрес метаданных облака).
- Без новых тяжёлых зависимостей и без GPL (minidlna — только тестовый сервер в Docker).

## Рассмотренные варианты

1. **Один HTTP-файл (`pa-vfs-http::HttpFile`) и два `Vfs`: `DlnaFs` и `PlaylistFs`**, `.strm` открывается тем же HTTP-файлом при воспроизведении и пробинге. Политика ссылок — на адресах, к которым реально идёт соединение.
2. **Отдавать плееру прямой URL** (mpv сам откроет ссылку) — без размеров и без пробинга, в обход прокси, медиатеки и профилей; разные правила для разных источников.
3. **Отдельный «медиасервер-клиент» DLNA по образцу Jellyfin** (свои библиотеки, свои метаданные) — DLNA не даёт ничего, кроме дерева папок и ссылок; лишняя сложность.

## Решение

Выбран вариант **1**.

### HTTP-файл и политика ссылок (`pa-vfs-http`)

- `HttpFile` — `ByteSource` поверх `ureq` (rustls, без OpenSSL): размер берётся из `HEAD` (или из `GET` первого байта, если сервер не отвечает на `HEAD`); чтение — запросами `Range: bytes=a-b` по 8 МиБ, последовательные чтения продолжают один ответ, перемотка начинает новый; после `hint_random_access` — по 256 КиБ. Сервер без поддержки диапазонов работает с начала файла и для перемоток до 64 МиБ.
- **Политика ссылок `LinkPolicy`** — по зонам адреса: `Loopback` (это устройство) < `Lan` (RFC 1918, `100.64.0.0/10`, `fc00::/7`) < `Public`. Ссылка из списка может вести только в зону **того же уровня или публичнее**, чем место, откуда пришёл список:
  - адрес, который ввёл пользователь (адрес плейлиста, адрес DLNA-сервера) — любая зона;
  - плейлист с сервера в интернете — только интернет;
  - плейлист или DLNA-сервер в домашней сети, файл на устройстве или на сетевой папке, `.strm` — домашняя сеть и интернет, **никогда само устройство**;
  - сервер на самом устройстве (пользователь ввёл `localhost`) — всё.
  - Никогда, даже по вводу пользователя: unspecified, multicast, broadcast, link-local (`169.254.0.0/16` с адресом метаданных облака, `fe80::/10`), зарезервированные.
- Проверка — в резолвере HTTP-клиента: из адресов DNS выкидываются запрещённые, и если не осталось ни одного, соединение не открывается (`PermissionDenied`). Так проверяется и первый запрос, и каждый редирект, и DNS-имя, которое позже резолвится в другое место (DNS rebinding). Системный прокси для таких запросов выключен (иначе проверялся бы адрес прокси).
- Только `http`/`https`, без логина и пароля в ссылке; редиректов не больше 5. Ошибки называют хост, но не ссылку (в ссылках плейлистов часто токены).
- Зона источника (плейлиста по ссылке, DLNA-сервера) определяется по его адресам в момент чтения: берётся **самая публичная** из них. Остаточный риск: тот, кто управляет DNS адреса плейлиста, может между проверкой и подключением выдать адрес из домашней сети и так расширить зону его ссылок; адрес плейлиста при этом выбрал сам пользователь.

### DLNA (`pa-dlna`)

- **Поиск:** SSDP `M-SEARCH` `urn:schemas-upnp-org:device:MediaServer:1` на каждый IPv4-интерфейс (`if-addrs`, интерфейс многоадресной рассылки задаётся через `socket2`), дважды, ответы 2,5 с; ответ принимается, только если `LOCATION` — `http` на том же адресе, с которого пришёл ответ (устройство не может направить приложение на чужой хост). Затем описания устройств (`friendlyName`, `UDN`, `controlURL` ContentDirectory, в том числе во вложенных устройствах), дубликаты по UDN убираются.
- В приложении DLNA-серверы появляются в «В этой сети» рядом с SMB/WebDAV из mDNS: пока список открыт, ядро ищет их сразу и затем каждые 15 с (`CoreSourceDiscovery`, FRB `dlna_search`). Касание открывает форму с именем и адресом — остаётся «Добавить и просканировать».
- **Адрес источника** — URL описания устройства (`http://host:8200/rootDesc.xml`); входа нет (DLNA открыт всей домашней сети), поэтому в форме нет логина, пароля и синхронизации пароля.
- **Дерево:** контейнеры — папки, элементы `videoItem`/`audioItem` — файлы с именем по `dc:title` и расширением из ссылки или MIME; картинки и плейлисты сервера пропускаются; из нескольких `res` берётся исходный файл (`http-get`, не транскод `DLNA.ORG_CI=1`); элементы-ссылки (`refID`) пропускаются. `Browse` постранично по 200, до 20 000 детей в папке; если сервер не дал размер — `HEAD`, без размера элемент не показывается. Листинги кешируются на минуту.
- **Одно представление:** серверы показывают одни и те же файлы в нескольких видах («Все видео», «По жанрам», «Папки»). Если в корне есть вид папок (`Browse Folders`, `Folders`, `Media Folders`, «Папки», «Обзор папок») — корнем источника становится он, иначе — корень `0`. Так каждый файл попадает в медиатеку один раз, в структуре папок, которую понимает распознавание.
- Потоки идут по `http-get`-ссылкам сервера через `HttpFile` с политикой зоны сервера, затем через общий loopback-прокси.

### Плейлисты M3U/M3U8 (`PlaylistFs`)

- **Адрес:** ссылка `http(s)` или файл на устройстве. Файл хранится как `m3u+file:///…`, а не `file://`: каталог считает `file://` папкой с локальными путями файлов.
- Разбор: `#EXTM3U`, `#EXTINF:<длительность> <атрибуты>,<название>` (`group-title`), `#EXTGRP`; относительные ссылки — от адреса плейлиста (после редиректов); ссылки не `http(s)`, с паролем и относительные в локальном файле пропускаются. HLS-плейлист одного потока (`#EXT-X-TARGETDURATION`, `#EXT-X-STREAM-INF`) — ошибка «это один поток, а не список».
- **Файлы:** у каждой ссылки берутся размер и тип (`HEAD`, 8 параллельно, результаты помнятся); файл — название из `#EXTINF` (или имя из ссылки) плюс расширение из ссылки или MIME; ссылки на страницы (`text/html`), без размера и недоступные пропускаются. `group-title` — папка. Повторы имён — «Название (2)». Не больше 5000 ссылок, плейлист до 16 МиБ, перечитывается раз в минуту.
- **Прямые эфиры (IPTV) не показываются:** `#EXTINF:-1`, ссылки на `.m3u8`/`.m3u` и всё без размера — это поток без конца, его нельзя сделать файлом медиатеки, и для него нужна своя модель (каналы, EPG, без «Продолжить просмотр»). ТВ-каналы проекту не нужны (решение владельца 2026-11-18): задача NET-024 вырезана, такие записи просто пропускаются.

### `.strm`

- `.strm` в любом источнике (локальная папка, SMB, WebDAV…) сканируется как видео: расширение в `pa-scanner::VIDEO_EXTENSIONS`, распознавание уже знало его как расширение и берёт название из имени файла.
- При воспроизведении и пробинге (`pa_catalog::open_media`) вместо текста открывается ссылка из первой непустой строки без `#`: только `http(s)` без пароля, по политике «файл на устройстве или на сетевой папке» (домашняя сеть и интернет, не само устройство); у ссылки должен быть размер. `plugin://`-ссылки Kodi не поддерживаются. В приложении локальный `.strm` открывается через прокси ядра, а не как путь к файлу.
- Файловый менеджер (UI-035) показывает `.strm` как обычный текстовый файл.

## Последствия

- Новые крейты `pa-vfs-http` и `pa-dlna`, виды источника `dlna` и `playlist` в `pa-sources` (без логина: имя пользователя и пароль для них отклоняются), FRB `dlna_search`. Новые зависимости — только уже бывшие в lock-файле: `url`, `socket2`, `if-addrs`.
- Синхронизация источников между устройствами (SYNC-010) для `dlna` и `playlist` не включена: адрес DLNA-сервера в одной сети мало что значит на другом устройстве, а синхронизация пароля не нужна. Можно добавить позже без миграций.
- Тесты: юнит-тесты разбора (SSDP, описание, DIDL-Lite, M3U, `.strm`, зоны), локальный HTTP-сервер (диапазоны, сервер без диапазонов, редиректы, блокировки политики), мок UPnP-сервера (SSDP, постраничный Browse, вид папок, поток), `pa-catalog/tests/links.rs` (M3U из HTTP-ссылок сканируется и играет через прокси побайтно; `.strm` на адрес в домашней сети играет, на само устройство — нет), против **minidlna в Docker** (`core/crates/pa-dlna/tests/minidlna/run.sh`, контейнер `pa-test-net018-minidlna-*`, opt-in feature `server-tests`): SSDP-поиск через мост Docker, дерево, поток и скан в медиатеку с проигрыванием через прокси.
- Не проверено на реальных устройствах: телевизоры, NAS с DLNA (Synology, Plex DLNA, Serviio, Windows Media Player) и Android/iOS — поиск SSDP на телефоне (Android получает ответы unicast, multicast-lock для них не нужен; на iOS multicast — после entitlement, PKG-012).
