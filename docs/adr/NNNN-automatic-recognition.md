# ADR-NNNN: Автоматическое распознавание: недоделанная работа доделывается сама, источники проверяются при запуске, возврате в приложение и появлении сети

- **Статус:** Предложен
- **Дата:** 2026-11-17
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-024 (эта задача), LIB-005 (watcher), LIB-023 ([ADR-0095](0095-fast-network-library-recognition.md)), CORE-016 (логи диагностики), META-033 ([ADR-0096](0096-other-language-titles.md))

## Контекст и проблема

Требование владельца: пользователь никогда не нажимает «Сканировать» — ни ради новых релизов, ни ради других файлов. Отчёт (macOS, alpha.11, SMB, ~1000 файлов): распознавание шло, при запуске видео приложение упало (это отдельная задача — mpv и CoreAudio), часть аниме осталась нераспознанной, после перезапуска распознавание не продолжилось. В логе после перезапуска — скан SMB за ~1 с (1028 файлов) и больше ничего о метаданных; экспорт снят через 6 с после старта, так что лог сам по себе ничего не доказывает.

Разбор кода показал, где работа терялась или не продолжалась:

1. **Отложенная проба поздних серий** (LIB-023) запускалась только после ручного скана. Автоматический скан watcher-а (старт, таймер, изменения) её не запускал — длительности и дорожки поздних серий не появлялись, пока пользователь не нажмёт кнопку.
2. **Метаданные после автоматического скана** запускались только по событию watcher-а и без следа в логе: старт и конец прогона не писались (только решения по отдельным работам), поэтому по логу нельзя было понять, шёл ли прогон.
3. **Ничто не запускало прогон без скана.** Прогон остановлен (нет сети, AniList недоступен, пять ошибок подряд, приложение закрыли) — работы ждали следующего события watcher-а. Для локальных папок это «следующее изменение файлов», то есть возможно никогда; для сети — 15 минут.
4. **Флаг `anime_pending` мог «залипнуть»**: работа, у которой больше нет этапа аниме (TMDB сказал, что это не аниме), записывалась без снятия флага и оставалась «в ожидании» навсегда.
5. **Убитый скан не доделывался.** Watcher перезапускается без стартового скана после правки источника; файлы, найденные до убийства, но не распознанные, ждали таймера (сеть) или изменения (локальные папки).
6. **Ничто не проверяло источники при возврате в приложение и появлении сети**: на Android и macOS процесс спит или замораживается, монотонный таймер watcher-а при этом не идёт.
7. **Нет видимости**: в настройках только результат ручного скана этого сеанса.

Что *не* терялось: каждый шаг распознавания хранит состояние в базе (файл без `parse_results`/`matches`, работа без строки `work_metadata`, `anime_pending`, `probed_at_ms IS NULL`, `last_scan_finished_at_ms IS NULL`), записи идут по одной работе в транзакции, поэтому убийство процесса ничего не портит и не теряет — нужно только, чтобы кто-то снова запустил шаг. pa-jobs в распознавании не участвует (там ed2k и загрузки, у них своя аренда задач).

## Факторы решения

- Без ручных действий на всех платформах: Linux, Windows, macOS, Android, Android TV.
- Дёшево: только инкрементальный список файлов, без повторного хеширования и чтения больших файлов (правила LIB-023: проба — только заголовки, ed2k — никогда в скане).
- Никаких циклов «ошибка → проверка → ошибка», никакой нагрузки на провайдеров сверх их лимитов.
- Лог диагностики владельца должен показывать старт и конец каждого прогона и каждой автоматической проверки.

## Рассмотренные варианты

1. Поставить распознавание в pa-jobs (аренда, повтор после падения).
2. Считать недоделанное по базе и запускать «догоняющий» прогон: при старте, после каждой автоматической проверки, по таймеру; источники проверять при старте, возврате в приложение, появлении сети и по таймеру.
3. Только уменьшить интервал таймера сети.

## Решение

Выбран вариант **2**: состояние и так в базе, pa-jobs добавил бы вторую копию состояния и миграцию без выигрыша; вариант 3 не решает потерю после убийства и тратит сеть.

**Ядро (`pa-catalog`).**
- `Catalog::pending_work(language, tmdb)` — что распознавание ещё должно: нераспознанные видео (нет живого совпадения и разбора текущей версией парсера), работы, которые возьмёт следующий прогон метаданных (тот же запрос, что у прогона; без ключа TMDB — только аниме), из них `anime_pending`, неудачные работы до срока повтора, файлы без пробы, источники с незавершённым сканом. Только чтение базы.
- `Catalog::sources_to_finish()` — источники, скан которых надо доделать (скан не закончился или есть нераспознанные видео).
- Watcher: при старте без стартового скана всё равно сканирует такие источники (`WatchReason::Unfinished`); `LibraryWatcher::check_now(min_age)` сканирует отслеживаемые источники, не проверявшиеся `min_age`, и должников — сразу, без задержки дребезга (`WatchReason::Check`). Скан — обычный инкрементальный: полный список, но проба, отпечатки и распознавание только новых и изменённых файлов.
- Прогон метаданных снимает `anime_pending` у работ без этапа аниме (больше не залипает).
- Логи INFO (opt-in диагностика CORE-016): `metadata run start` (работ, аниме, язык, провайдеры), `metadata run end` (найдено, не найдено, ошибок, объединено, остановлен, ошибка, сколько ещё ждёт, время), `metadata run skipped: no provider`, `auto check` (источник, причина, файлов, добавлено/изменено/удалено, ошибка, время), `auto check requested`.

**Приложение.**
- `RustLibrary` (интерфейс `LibraryAutoRecognition`), пока watcher запущен: «догоняющий» прогон — метаданные для ждущих работ, затем отложенная проба — при старте (метаданным SMB не нужен), после каждого события watcher-а (даже без изменений) и раз в 5 минут; один прогон за раз, повтор по запросу во время прогона. Если файлов без пробы не стало меньше за проход (FFmpeg нет, шара не отдаёт файл), таймер их не трогает до следующего скана или проверки. Таймер (и только он, не события — иначе неудачный скан зациклится) просит watcher доделать источники с нераспознанными файлами или убитым сканом. Смена ключа TMDB или языка запускает прогон сразу. Закрытие приложения останавливает прогон (записанное остаётся).
- `LibraryAutoCheck`: `AppLifecycleListener` (`onResume`, `onShow`: Android, Android TV, iOS, macOS, Windows, Linux) → проверка источников старше 2 минут; `connectivity_plus` — сеть вернулась после «нет сети» → проверка всех источников и повтор неудачных работ сразу (`retry_failed`).
- Таймер сетевых источников — как был, 15 минут (полный инкрементальный список); локальные папки — уведомления ОС.
- Настройки → Медиатека: как работает автоматическая проверка, когда была последняя (только что / N минут назад / время / ошибка), идёт ли распознавание (шаг и счёт), сколько ждут, сколько не загрузилось и будет повторено. Кнопка «Сканировать» остаётся.

### Последствия

- Хорошо: убитый в любой момент прогон доделывается сам при следующем запуске (метаданные — сразу, без ожидания шары), скан — при старте watcher-а; новые файлы на сетевом источнике появляются при запуске, возврате в приложение, появлении сети и раз в 15 минут; в логе видно каждый прогон и каждую проверку.
- Плохо: на десктопе возврат фокуса окну раз в 2 минуты листает источники (для 1000 файлов SMB — около секунды); долгий этап аниме держит блокировку сканов ядра, и автоматическая проверка ждёт его конца (так было и раньше с метаданными после скана).
- Нейтрально: миграций нет; FRB API: `CoreLibrary.check_now`, `CoreLibrary.pending_work`, `CoreMetadataSettings.retry_failed`.

### Как проверяем соблюдение

- `pa-catalog/tests/metadata.rs`: `a_killed_metadata_run_is_finished_by_the_next_one` (дочерний процесс тестового бинарника падает по `abort()` посреди прогона, следующий прогон берёт ровно оставшееся), `anime_pending_is_finished_and_never_sticks`, `without_a_key_only_anime_count_as_waiting`.
- `pa-catalog/tests/connect.rs` (сетевой источник через `Vfs` в памяти): `check_now_picks_up_a_new_file_on_a_network_source`, `a_scan_killed_before_recognition_is_finished_on_the_next_start`.
- `pa_library/test/rust_library_test.dart`: убитый скан доделывается после перезапуска без ручного скана; `checkNow` сразу листает источники и приносит новый файл.
- `app/test/library_auto_check_test.dart`, `app/test/settings_about_test.dart` (строки статуса).

## Открытые вопросы

- Интервал таймера сетевых источников (15 минут) и порог возврата в приложение (2 минуты) — значения по умолчанию; настройка — по запросу владельца.
- Фоновая проверка на Android, когда приложение выгружено (WorkManager), — не входит: новые файлы появятся при следующем открытии приложения.
