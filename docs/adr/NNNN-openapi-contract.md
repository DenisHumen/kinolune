# ADR-NNNN: OpenAPI сервера генерируется из кода (utoipa), контракт замораживается, совместимость ±1 major

- **Статус:** Предложен
- **Дата:** 2026-11-18
- **Решают:** владелец проекта (поручил решать по правилу «максимально просто для клиента»), мейнтейнер
- **Связано:** SRV-002, SRV-001, SRV-003, SRV-004, SRV-006, DOC-004; `docs/research/04` §1.5, §4.2; [ADR-0019](0019-lan-discovery-mdns.md), [ADR-0004](0004-no-project-servers-local-sync.md)

## Контекст и проблема

У медиасервера (`server/`, бинарь `alpha-media`) уже есть HTTP-эндпоинты: `/health`, `/healthz`, сопряжение (`/api/v1/pair`, `/api/v1/pair/invite`), список и отзыв устройств (`/api/v1/devices`), хаб синхронизации (`/api/v1/sync`). Описания API не было: клиенты (SRV-006, `pa-remote`) и документация (DOC-004) опирались бы на код. ROADMAP SRV-002 требует OpenAPI 3.1 через utoipa, `docs/api/openapi.json` как генерируемый файл, проверку дрейфа в CI, версию протокола и совместимость клиент ↔ сервер ±1 major; «done when» — CI падает, если код и спецификация расходятся, и есть контракт-тесты для N-1.

Сервер работает у пользователя; клиенты и сервер обновляются независимо (телефон обновился, NAS — нет, и наоборот), поэтому правило совместимости должно быть простым и проверяемым автоматически.

## Факторы решения

- Спецификация не может разойтись с кодом незаметно — ни в путях, ни в полях ответов.
- Клиенту — одно число для проверки совместимости, одна форма ошибок, никаких настроек.
- Лицензия MPL-совместимая (`cargo deny`), без новых тяжёлых зависимостей.
- Не трогать общие workflow CI (параллельно идёт CI-008).

## Рассмотренные варианты

1. **utoipa + utoipa-axum:** маршруты регистрируются из `#[utoipa::path]` обработчиков (`routes!`), спецификация собирается из тех же аннотаций.
2. **utoipa только для документа:** `#[openapi(paths(...))]` отдельно от роутера axum — маршрут можно добавить и забыть описать.
3. **OpenAPI руками** (YAML) + тесты на соответствие — двойная работа, дрейф ловится только тестами.

## Решение

Выбран вариант **1**: маршрут без описания невозможен по построению, а поля ответов описываются теми же типами, которые сериализуются (`server/src/api.rs`). utoipa 6.0 и utoipa-axum 0.3 — MIT OR Apache-2.0; новые транзитивные крейты — `utoipa-gen`, `pastey` (тоже MIT OR Apache-2.0).

**Документ.** OpenAPI 3.1, `info.version` = `"<major>.<minor>"` (сейчас `1.0`) — версия API, не версия программы. Генерируется `pa_server::api::openapi_json()`; лежит в `docs/api/openapi.json` (руками не правится). Обновить: `just server openapi`; посмотреть у запущенной установки: `alpha-media --openapi`.

**Версии.** `API_MAJOR` (сейчас 1) — это `v` в TXT mDNS (ADR-0019), префикс `/api/v1` и `api.major` в `/health`; `API_MINOR` растёт при добавлениях. `/health` теперь отдаёт `"api": {"major": 1, "minor": 0}`.

**Совместимость ±1 major.** Клиент и сервер работают вместе, если их major отличаются не больше чем на единицу: `pa_discovery::api_compatible(client, server)` и `ServerTxt::is_compatible` — клиент проверяет это по TXT `v` ещё до подключения. Поддержку старого major несёт более новая сторона: сервер N обслуживает клиентов N-1 (это проверяют контракт-тесты ниже), клиент N+1 умеет говорить с сервером N (проверяется тестами клиента, когда он появится — SRV-006). Внутри одного major изменения только добавляющие: новые эндпоинты, новые необязательные поля, новые коды ошибок. Клиент обязан игнорировать незнакомые поля и обрабатывать незнакомый `4xx`/`5xx` как общую ошибку.

**Ошибки.** Все ошибки эндпоинтов `/api` — JSON `{"error": "<текст>"}` (`ApiError`); тексты по-английски, для логов, не для показа. Исключение — отказы разбора запроса самим axum (неверный query, не WebSocket-апгрейд): `400` с текстом, описан без тела.

**Замороженные контракты.** `docs/api/compat/openapi-<major>.<minor>.json` — копии спецификации, на которые уже могут опираться клиенты. Сейчас заморожен `1.0` (этот PR): серверных релизов ещё не было, но с этого момента API v1 меняется только добавлениями. При серверном релизе с новым minor — `just server openapi-freeze`. При переходе на major N+1 в каталоге остаётся последний контракт N (это и есть N-1), контракты старше N-1 удаляются — тест требует ровно это.

**Контракт-тесты** (`server/tests/contract/`, запускаются в `cargo test --workspace`):

- `committed_spec_matches_code` — `docs/api/openapi.json` байт в байт совпадает со сгенерированным;
- `server_answers_as_specs_describe` — запущенный сервер на каждую операцию текущей спецификации и каждого замороженного контракта отвечает задокументированным кодом и телом, проходящим JSON Schema 2020-12 (крейт `jsonschema`, уже есть в workspace); для текущей спецификации ещё и строго: поле, которого нет в схеме, — ошибка. Операция без сценария в `live.rs` — ошибка;
- `current_spec_keeps_frozen_contracts` — текущая спецификация обратно совместима с каждым замороженным контрактом. Ломающим считается: удалённая операция или параметр; новый обязательный параметр или тело; сужение принимаемых значений запроса; исчезнувшее обязательное поле ответа; расширение типа или enum ответа (в том числе `null`); новый или удалённый успешный код (`101`, `2xx`); смена типа содержимого. Описания, теги и `operationId` в контракт не входят;
- `compat_checker_tells_additive_from_breaking` — сам проверяльщик на добавляющих и ломающих правках;
- `frozen_contracts_are_the_supported_ones` — при `API_MAJOR > 1` контракт N-1 обязан быть, контракты старше — удалены.

**CI.** Тесты идут в `rust.yml` (nextest по всему workspace) при любых изменениях Rust. Правку только файлов `docs/api/**` ловит отдельный маленький `openapi.yml` (тот же тест-таргет), чтобы не трогать общие workflow.

**Не входит:** аутентификация в спецификации (SRV-003 добавит схему безопасности и `401` — это добавление), публикация документации на сайте (DOC-004), генерация клиентского кода по спецификации (решит SRV-006).

### Последствия

- Хорошо: описание и маршруты не расходятся; клиент проверяет совместимость одним сравнением; N-1 проверяется автоматически на каждом PR.
- Плохо (цена): новая зависимость utoipa (proc-macro, время сборки сервера); WebSocket-эндпоинты описаны только как апгрейд (`101`), их протоколы — в `docs/api/sync-protocol.md` и `pa_pairing::pair`, не в OpenAPI.
- Требует работы: SRV-003 и SRV-006 добавляют эндпоинты через `routes!` и сценарии в `server/tests/contract/live.rs`; при первом серверном релизе — `just server openapi-freeze`, если minor вырос.

### Как проверяем соблюдение

`cargo test -p pa-server --test contract` в `rust.yml` и `openapi.yml`; `cargo deny check` — лицензии новых крейтов.
