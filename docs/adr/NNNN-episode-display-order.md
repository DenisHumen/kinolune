# ADR-NNNN: Порядок серий сериала — перенумерация в ядре по `display_preferences`, AniDB из `episode_mappings`

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `UI-010`, `UI-009`, `PLAY-005`, `META-008`, `META-027`, `docs/research/03-metadata-recognition.md` §4.2 (DisplayPreference), `docs/research/01` §2.2, §1.4

## Контекст и проблема

Страница сериала (`UI-010`) должна показывать серии в порядке, который выбрал пользователь: TMDB, абсолютный или AniDB (аниме, где один сезон TMDB — это две записи AniDB, или наоборот). Схема v1 (`LIB-001`) уже содержит `display_preferences (profile_id, work_id, scheme)`, `episodes.absolute_number` и `episode_mappings` со схемой `anidb`, но никто их не читал и не заполнял. Нужно решить, где перенумеровывать серии, что значит «сезон» в порядке AniDB и что делать, когда данных для выбранного порядка нет.

## Факторы решения

- Без новой миграции (горячий файл у параллельных агентов) и без изменения ключей прогресса.
- Один источник правды для всех клиентов (Flutter, позже tvOS).
- Работает без сети и без загруженных маппингов аниме; запасной путь v0 не ломается.
- Выбор хранится на профиль и сериал, как в исследовании 03 §4.2.

## Рассмотренные варианты

1. Перенумерация в ядре (`pa-catalog`), выбор — в `display_preferences`.
2. Перенумерация в приложении по данным, которые ядро отдаёт как есть.
3. Отдельная таблица порядков с полной копией номеров на каждую схему.

## Решение

Выбран вариант **1**.

- `Catalog::show_episodes(show, order)` отдаёт серии с номерами в нужном порядке, номера TMDB рядом и прогресс каждой серии (для Hide Spoilers и полос прогресса); `order = None` — порядок из `display_preferences` профиля, иначе TMDB. `Catalog::set_episode_order` пишет `display_preferences`. Файлы, совпадения и ключи прогресса не меняются: перенумерация только для показа.
- **TMDB** — `episodes.season_number` / `episode_number`.
- **Абсолютный** (в `display_preferences` — схема `tvdb_absolute`, единственная абсолютная в CHECK) — обычные серии одной лентой в сезоне 1: `episodes.absolute_number`, если провайдер его дал, иначе счёт по всем обычным сериям работы, которые знает каталог (и без файлов), в порядке TMDB. Спецвыпуски остаются в сезоне 0.
- **AniDB** — строки `episode_mappings` со схемой `anidb`. У AniDB нет сезонов, поэтому `season_number` строки — номер записи AniDB во франшизе (1, 2…; NULL = 1), 0 — спецвыпуски AniDB (`S1`…). Из нескольких строк одной серии берётся с наибольшей `confidence`, затем меньшим `part`. Серии без строки сохраняют номера TMDB. Порядок предлагается, только если строка есть хотя бы у одной серии с файлом.
- Порядок без данных молча заменяется на TMDB (и в ответе виден фактический порядок), чтобы старый выбор не ломал страницу после смены совпадения.
- Приложение без ядра (v0) считает TMDB и абсолютный порядок само (`orderEpisodes` в `pa_library`) и не хранит выбор.

**Не входит:** заполнение `episode_mappings` из Anime-Lists (`pa-anime-mappings` загружает список на устройстве, но метаданные его пока не применяют) — до этого порядок AniDB есть только в тестовых фикстурах; порядки `tvdb_aired`, `tvdb_dvd` и группы эпизодов TMDB (`tmdb_group`).

### Последствия

- Хорошо: нет миграции; Up Next (`PLAY-005`) и прогресс работают по-прежнему; клиенты получают готовые номера.
- Плохо: смысл `season_number` у схемы `anidb` закреплён этим ADR, а не схемой; абсолютный счёт без `absolute_number` зависит от полноты данных TMDB о сериях.
- Требует работы: применять маппинги Anime-Lists в прогоне метаданных (новая задача META), после чего порядок AniDB появится у реальных аниме; профили (`LIB-012`) заменят константу профиля.

### Как проверяем соблюдение

`core/crates/pa-catalog/tests/episode_order.rs` (TMDB → AniDB на фикстуре, абсолютный счёт, запасной TMDB, прогресс), `pa_library` `test/episode_order_test.dart` и `rust_library_test.dart`, widget-тест страницы `clients/flutter/app/test/show_detail_test.dart`.
