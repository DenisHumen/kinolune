# ADR-0033: SMB через libsmb2 — загрузка в рантайме, пул контекстов, read-ahead с параллельным prefetch

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** NET-002, NET-003, NET-011, NET-021, CI-004, CI-012, QA-007 ([ADR-0133](0133-bad-network-tests-netem.md)); [ADR-0005](0005-license-mpl2-dco.md) (LGPL только динамически), [ADR-0013](0013-pa-vfs-blocking-positional-reads.md) (синхронный `pa-vfs`), [ADR-0027](0027-player-io-adapters-fn-pointers.md) (FFmpeg и libmpv без линковки из Rust); `docs/research/02` §3.1, §4

## Контекст и проблема

SMB — главный источник медиа на NAS, а в Android-клиенте его нет совсем. Research 02 §4 выбрал [libsmb2](https://github.com/sahlberg/libsmb2) (C, LGPL-2.1+, SMB 2.0.2–3.1.1, встроенный NTLMSSP, подпись и шифрование SMB3, работает на iOS и tvOS). LGPL-код у нас — только отдельной заменяемой библиотекой (§0.3 п.10). Нужно решить: как Rust-ядро получает функции libsmb2, как из небезопасного по потокам контекста сделать `Vfs` для многих потоков и как держать поток 4K-ремукса по Wi-Fi.

## Факторы решения

- LGPL: libsmb2 — отдельный `.so`, `.dll`, `.dylib` или embedded framework, пользователь может её заменить.
- `cargo test --workspace` и CI ядра должны работать без собранной libsmb2 (так же, как для FFmpeg и libmpv в ADR-0027).
- Один код загрузки для Linux, Windows, Android, macOS, iOS и tvOS; на iOS динамический код — только во framework внутри бандла.
- Контекст libsmb2 не потокобезопасен; сканер и плеер читают из разных потоков (`Arc<dyn Vfs>`, `read_at(&self)`).
- Поток 80 Мбит/с при RTT 30 мс и 1 % потерь (NET-003): один запрос за раз на одном TCP-соединении этого не даёт.

## Рассмотренные варианты

1. `smb2-sys` с `cargo:rustc-link-lib=dylib=smb2` в `build.rs`: линковка на этапе сборки.
2. Загрузка библиотеки в рантайме через `libloading` (ISC) и таблица указателей на функции.
3. Pure-Rust клиент `smb` (smb-rs, MIT) вместо libsmb2.

## Решение

Выбран вариант **2**.

- `tools/libsmb2` собирает libsmb2 6.3.x только как разделяемую библиотеку (на iOS и tvOS — `smb2.framework`, плюс `smb2.xcframework`) с лицензионным гейтом по образцу `tools/ffmpeg` и `tools/mpv`. Kerberos выключен: NTLMSSP встроенный, внешних зависимостей нет.
- Крейт `pa-smb2`: `sys` — C ABI (типы и таблица функций), `Smb2Lib` — загрузка (`$PA_SMB2_LIB`, затем имена платформы, в том числе `@rpath/smb2.framework/smb2`), `Context` — безопасная обёртка (`Send`, не `Sync`, все вызовы через `&mut self`; файлы — `FileId` с проверкой владельца вместо сырых указателей). Ошибки классифицируются по NT status, затем по errno (значения errno различаются между ОС).
- Отсутствие библиотеки — ошибка `LibraryUnavailable` при первом SMB-подключении, а не падение приложения.
- Проверка «линкуется динамически» из NET-002: гейт `tools/libsmb2/check-license.sh` на каждом таргете (тип файла, зависимости через `readelf`/`otool`/`objdump`, install name `@rpath`), а для нативных таргетов — `ldd`/`otool -L` тестовой C-программы. Наши Rust-бинарники libsmb2 не линкуют вовсе.
- Крейт `pa-vfs-smb` (NET-003): `SmbFs` держит пул контекстов (по умолчанию до 6), каждый со своим кэшем открытых файлов. `list` и `stat` — один запрос на свободном контексте. `ByteSource` читает случайные запросы напрямую, а при последовательном чтении включает read-ahead: блоки по 1 МБ, буфер 64 МБ по умолчанию (настраивается, ориентир 32–256 МБ), до 4 блоков параллельно на разных соединениях в фоновых потоках. Обрыв соединения выбрасывает контекст из пула, запрос повторяется один раз на новом.
- SMB1 libsmb2 не умеет. Флаг `allow_smb1` в конфигурации есть по требованию NET-003, но включённый он даёт `Unsupported` с подсказкой включить SMB2 на сервере: старый протокол не поддерживаем даже по флагу.

### Последствия

- Хорошо: LGPL-библиотека остаётся заменяемым файлом, ядро собирается и тестируется без неё; одна обёртка на все платформы.
- Хорошо: параллельные запросы на нескольких соединениях обходят ограничение одного TCP-потока при потерях.
- Плохо (цена решения): сигнатуры и `struct smb2_stat_64` повторены вручную в `pa-smb2::sys`. Защищено закреплённой версией (6.x держит ABI и soname), проверкой экспортов в гейте и тестами против реальной библиотеки.
- Плохо: `smb2_get_nterror` нет в `libsmb2.syms`, поэтому MSVC-сборка его не экспортирует; наша Windows-сборка — mingw-w64, экспортирует всё. Для mingw нужен патч (`patches/libsmb2/0001`), он описан и войдёт в архив исходников.
- Цель NET-003 «80 Мбит/с при 30 мс и 1 % потерь» сначала не была достигнута (29 Мбит/с по умолчанию, 66 — с 32 соединениями); её закрыл NET-021, см. раздел ниже.
- Нейтрально: каждый открытый `SmbFs` держит до 6 TCP-соединений и потоки prefetch; при закрытии источника они освобождаются.

### Как проверяем соблюдение

`cargo tree -p pa-smb2` — только `libloading`; `nm` наших бинарников не содержит определённых `smb2_*`; CI `libsmb2.yml` гоняет гейт на всех таргетах; `pa-vfs-smb` проходит контракт-сьют `pa-vfs` против Samba в Docker (`tests/servers/run.sh`).

## NET-021: скорость на каналах с потерями (2026-11-18)

Решает агент по правилу владельца «максимально просто для клиента»: всё автоматически, новых настроек нет.

### Что мешало

- **Вытеснение блоков впереди читателя.** Буфер read-ahead был LRU: блок, скачанный заранее, оказывался «старше» блока, который читатель только что прочитал, и при заполнении окна выбрасывался непрочитанным, а потом скачивался снова. При 4 параллельных блоках это почти незаметно, при 16–32 съедало половину скорости: замеры NET-003 «50 Мбит/с с 16, 66 — с 32 соединениями» во многом были этим. Теперь выбрасываются сначала блоки позади читателя (самый дальний), потом самый дальний впереди.
- **Один TCP-поток на канале с потерями.** При 30 мс и 1 % случайных потерь CUBIC сервера даёт потоку единицы Мбит/с, и клиент может только добавлять потоки. Четыре параллельных блока по умолчанию — это около 23 Мбит/с.

### Решение

`pa-vfs-smb::adapt::Tuner` — один на `SmbFs`, общий для открытых файлов:

- **Сигналы.** Сколько читатель ждал блоки; время каждого блока (запрос → последний байт); RTT маленького запроса — `stat` при открытии файла (база на пустом канале) и `fstat` на только что освободившемся соединении примерно раз в 200 мс во время потока.
- **Эпоха** — не меньше 1 с и не меньше одного блока на параллельный слот. Если читатель ждал сеть не меньше 20 % эпохи и канал не копит очередь, число параллельных блоков удваивается: 4 → 8 → 16 → 32 (`DEFAULT_MAX_PREFETCH_PARALLEL`), пул соединений растёт до числа блоков + 2.
- **Очередь.** Канал «копит очередь», если минимальный RTT эпохи больше 2 × базового + 1 мс: канал заполнен (быстрая LAN, Wi-Fi на пределе своей скорости), и новые соединения только наполняют буфер роутера. На канале с потерями, который не заполнен, RTT остаётся у базы, и число растёт дальше. Шаг, после которого появилась очередь, откатывается (после одной эпохи разогрева: новые соединения логинятся и выходят из slow start), повторная попытка — не раньше чем через 30 с.
- **Почему не сравнение скоростей.** Сначала шаг оценивался по скорости до и после (в том числе по закону Литтла: блоки × байты / среднее время блока). На канале с потерями скорость одного соединения сильно плавает (slow start в начале, таймауты повторной передачи), и сравнение эпох откатывало удачные шаги: медиана на профиле «30 мс, 1 %» оставалась 40–60 Мбит/с.
- **Окно.** Окно read-ahead вмещает блоки в полёте дважды и данные, которые читатель съест за время самого медленного блока эпохи, тоже дважды: не меньше настроенного (64 МиБ), не больше 128 МиБ (если настроено больше — настроенное). Окно только растёт: уменьшение выбрасывало уже скачанные блоки впереди, на профиле с потерями это вдвое снижало скорость.
- **Ничего не меняется,** если читатель не ждёт сеть. Плеер на хорошей сети не голодает, поэтому в LAN остаются 4 блока, как в NET-003. Соединения не закрываются до закрытия источника: закрытие живого контекста посреди потока однажды упало в `smb2_destroy_context` (см. «Последствия»), а простаивающее соединение серверу почти ничего не стоит.
- **API для экспериментов, не для пользователя.** `SmbConfig::with_max_prefetch_parallel` (равное `with_prefetch_parallel` фиксирует число блоков), `SmbFs::prefetch_parallel()` и `SmbFs::read_ahead_window()`.

### Замеры

Сервер сборки (32 ядра), Samba 4.21 в одноразовом контейнере alpine, CUBIC, netem на `eth0` контейнера (`core/crates/pa-vfs-smb/tests/servers/bench.sh`). Поток 192 МиБ подряд чтениями по 256 КиБ, release, проверка SHA-256, по 4 прогона; медиана (разброс), Мбит/с.

| Профиль | netem | До (main) | После (NET-021) |
|---|---|---|---|
| `lan` | — (мост docker, упор в процессор) | 13 818 (13 451–15 160) | 15 672 (15 485–16 180) |
| `gige` | `delay 500us rate 1gbit` | 951,6 (951,5–951,6) | 951,2 (951,0–951,3) |
| `wifi` | `delay 30ms 5ms distribution normal loss 0.1% rate 300mbit` | 67,4 (52,8–140,7) | 159,0 (144,5–166,1) |
| `lossy` | `delay 30ms loss 1%` (профиль NET-003) | 23,2 (21,1–24,6) | 173,8 (150,1–224,8) |

- Профиль `wifi` — ближе к настоящему Wi-Fi: повторы 802.11 исправляют почти все потери на радиоканале, до TCP доходит около 0,1 %; разброс задержки и предел скорости канала. Профиль `lossy` — прежний, каждая потеря доходит до TCP; он строже настоящего Wi-Fi.
- LAN не хуже: на `gige` упор в 1 Гбит/с, в конце каждого прогона 4 блока (канал заполнен, RTT растёт — шаг вверх откатывается); на `lan` читатель (SHA-256) медленнее сети и не ждёт её, число блоков не растёт.
- Повтор по 15 прогонов (под gdb, ловили падения): `lossy` — медиана 155,7 (121,9–227,6, все выше 80), `wifi` — 182,3 (163,6–202,0), `gige` — 950,8 (950,5–951,2); ни одного падения.
- Тест `stream_wifi_netem_80_mbit` из контракт-сьюта (`run.sh`, debug-сборка) снова включён: 173,6 Мбит/с, все 86 тестов сьюта зелёные.
- Фиксированное число блоков после исправления вытеснения (окно 64 МиБ, по 2 прогона), `lossy`: 8 — 48,5, 16 — 90,6, 24 — 124, 32 — 146, 48 — 179, 64 — 140–196; `wifi`: 16–48 — 210–227. Верхняя граница 32 даёт двукратный запас к цели при умеренном числе соединений (у Samba это процессы `smbd`).

### Цель NET-021

80 Мбит/с на профиле «30 мс, 1 % потерь» достигнуты (медианы 174 и 156 в двух сериях release, 174 в debug; минимум из 19 прогонов release — 122), пересмотр цели не нужен. Замер на настоящем Wi-Fi делает владелец по строкам SRC-127…SRC-130 каталога проверок (`docs/qa/test-catalog.md`): пример `smb_speed` в автоматическом режиме и с фиксированными 4 блоками (как до NET-021), по кабелю и по Wi-Fi 5 ГГц; итоговые числа дописываются сюда.

### Последствия NET-021

- Хорошо: в 7,5 раза быстрее на профиле с потерями и в 2,4 раза на профиле «Wi-Fi», без настроек и без потерь в LAN.
- Плохо: до 34 TCP-соединений (и процессов `smbd` у Samba) на источник, пока он открыт, и до 128 МиБ окна на файл при медленных блоках. Порог очереди (2 × RTT + 1 мс) на проводной LAN с маленькими буферами коммутатора может не сработать; тогда при копировании «как можно быстрее» (офлайн-загрузка) число блоков вырастет до 32 — скорость от этого не падает, но NAS с HDD может читать хуже; не проверено.
- Плохо: во время отладки промежуточных версий тест трижды упал с SIGSEGV; один раз gdb показал `smb2_destroy_context` при закрытии контекста посреди потока (эту ветку кода убрали). 130 принудительных закрытий простаивающих контекстов посреди потока, 12 прогонов с libsmb2 под AddressSanitizer и 61 прогон итоговой версии (45 из них под gdb) падение не повторили. Подозрение на libsmb2 6.3.2 остаётся (в `smb2_destroy_context` `smb2->pdu` освобождается без обнуления перед обходом `waitqueue`); если повторится — отдельная задача на исправление в libsmb2.
