# ADR-NNNN: Готовые FFmpeg и libmpv для CI — имя по хэшу входов, actions/cache и релиз `prebuilt`

- **Статус:** Предложен
- **Дата:** 2026-11-18
- **Решают:** владелец проекта (направление), мейнтейнер (детали; владелец поручил решать по правилу «максимально просто для клиента / проекта»)
- **Связано:** CI-008, PLAY-001, PLAY-002, PLAY-013, CI-002, NET-008; [ADR-0027](0027-player-io-adapters-fn-pointers.md); `docs/research/02` §3.1

## Контекст и проблема

`ffmpeg.yml` и `libmpv.yml` уже складывали результат в `actions/cache` по хэшу рецепта, но на практике CI всё равно пересобирал FFmpeg и libmpv:

- **Кэш GitHub ограничен 10 ГБ на репозиторий** и вытесняет самое старое. Кэши Rust (≈2,5 ГБ на ветку) и MPVKit (≈470 МБ на прогон) вытесняют сборки libmpv за часы. 18 ноября сборка по тегу `app-v0.1.0-alpha.15` пересобрала Linux (7 мин), Android (4–5 мин на ABI) и оба macOS (5–8 мин): кэш `main` для них уже был вытеснен.
- **Кэш виден только своей ветке и `main`.** Сборка на ветке PR, сборка по тегу и пробный прогон релиза на ветке не видят кэш друг друга; `ffmpeg.yml` на `main` не запускался вовсе.
- Другие workflow не получали готовые библиотеки: интеграционные тесты `pa-player-io` (ADR-0027) пропускались в CI без `PA_PLAYER_IO_LIB_DIR`.

Нужно: неизменный рецепт не пересобирается ни в каком прогоне; лицензионные проверки идут на каждом артефакте; PR из форков ничего не пишут и не получают секретов.

## Рассмотренные варианты

1. **Только `actions/cache`, ключи поаккуратнее.** Ничего нового, но не решает ни вытеснение, ни область видимости веток.
2. **Workflow-артефакты прогона на `main`, скачивание по `run-id` из других прогонов.** Нужен токен с `actions: read` и поиск «последнего удачного прогона»; артефакты живут максимум 90 дней; для форков неудобно.
3. **Ассеты одного релиза `prebuilt` + `actions/cache` как быстрый первый уровень.** Ассеты публичные, не вытесняются, скачиваются анонимно по HTTPS из любого прогона (ветка, тег, форк). Пишет только `main`.
4. **Пакеты/образы в GHCR (OCI).** Тот же эффект, что 3, но нужен `oras`/`docker` в каждом job и права `packages`.

## Решение

Вариант 3.

- **Имя сборки — хэш её входов** (`tools/ci/prebuilt.sh key <lib> <target>`): `<lib>-<target>-<рецепт>[-<тулчейн>]`, где «рецепт» — 16 hex sha256 всех файлов рецепта (скрипты, `versions.sh`, патчи, Docker-образы — те же пути, что раньше были в `RECIPE_GLOB`), «тулчейн» — 8 hex от версий NDK, Xcode, meson, ninja (только для целей, собираемых на раннере; у Docker-целей образ закреплён digest-ом в рецепте). Одинаковое имя означает одинаковые входы.
- **Порядок поиска в каждом job сборки:** `actions/cache` (`prebuilt-<имя>`) → ассет `<имя>.tar.xz` релиза `prebuilt` → сборка. Скачивание анонимное (`curl`, без токена), любой сбой загрузки — просто сборка. Найденное в релизе сохраняется и в `actions/cache` ветки.
- **Лицензионный гейт идёт всегда**, откуда бы ни пришла сборка: `check-license.sh --artifact`, для Linux и macOS arm64 ещё `--run` (`avutil_license()` = «LGPL version 2.1 or later», `mpv_client_api_version`), для Android — `bundle.sh check-android`, для Linux libmpv — golden-кадры субтитров. GPL-канарейки (`--enable-gpl`, `-Dgpl=true` и др. роняют сборку) остались в job `Sources and GPL canary`.
- **Публикует только `prebuilt.yml` на `main`** (push в рецепты или ручной запуск): вызывает `ffmpeg.yml` и `libmpv.yml` с `publish: true`; job сборки упаковывает новый результат в workflow-артефакт `prebuilt-<имя>` только после всех проверок; отдельный job `publish` (единственный с `contents: write`, кода из репозитория не запускает) загружает отсутствующие ассеты в релиз. Ассеты не перезаписываются. На других ветках `prebuilt.yml` только собирает и проверяет. Триггер `push: main` из `libmpv.yml` перенесён сюда.
- **Исходники рядом (LGPL §6):** вместе с бинарниками публикуются `ffmpeg-sources-<рецепт>.tar.xz` и `libmpv-sources-<рецепт>.tar.xz` (upstream-архивы с SHA256SUMS и наш рецепт с патчами).
- **Релиз `prebuilt` — пре-релиз** с пометкой «Not an app release»: он не становится «latest», а обновлятор приложения читает только теги `app-v*` (ADR-0088).
- **Первый клиент:** job `nextest` в `rust.yml` берёт `libmpv-linux-x86_64` (в нём и FFmpeg) из кэша или релиза, проверяет лицензию (`--artifact` и `--run`) и запускает `pa-player-io` с `PA_PLAYER_IO_LIB_DIR`. Если для текущего рецепта сборки ещё нет (PR меняет рецепт), тесты пропускаются с предупреждением: сам `rust.yml` ничего не собирает.
- libsmb2 не трогаем: собирается за минуту, кэшируется только исходник.

## Последствия

- Плюсы: неизменный рецепт не пересобирается ни на ветках, ни по тегам, ни в форках; вытеснение кэша больше не стоит 5–8 минут на цель; ключ кэша считается одним скриптом вместо копий `find | sha256sum` в каждом job.
- Минусы: на странице Releases появляется служебный пре-релиз `prebuilt`; ассеты копятся (≈15 МБ на цель, ≈11 + 7 целей на рецепт) — чистить вручную старые имена, когда их станет много.
- Доверие: в релиз пишет только `main` после гейтов; читающие прогоны всё равно повторяют лицензионную проверку. Подмена ассета возможна только с правами записи в репозиторий — те же права, что нужны для правки самих workflow.
- Смена Xcode на образе раннера даёт новое имя и одну пересборку; новое имя попадёт в релиз при следующем push в рецепт или ручном запуске `prebuilt.yml` на `main`.
