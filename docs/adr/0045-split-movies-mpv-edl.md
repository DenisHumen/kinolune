# ADR-0045: Фильм из нескольких файлов играет одной шкалой через EDL mpv

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-020, LIB-017, LIB-007, LIB-010, PLAY-005; [ADR-0012](0012-release-0-1-player-media-kit.md), [ADR-0038](0038-network-playback-loopback-proxy.md), [ADR-0043](0043-disc-main-title-and-iso.md)

## Контекст и проблема

Анализ папок (LIB-007, LIB-017) записывает части одного фильма как участников группы с ролью `part` и номером: `Movie.cd1.avi` и `Movie.cd2.avi`, VOB основного набора DVD (`VTS_01_1.VOB`, `VTS_01_2.VOB`, …). Элемент медиатеки и его версия указывают на первую часть, и до LIB-020 приложение играло только её: у DVD — около 1 ГБ из 4–8.

Нужно, чтобы фильм играл целиком: одна шкала, перемотка через границу частей, прогресс «Продолжить просмотр» на элементе. Плеер приложения — media_kit поверх нашего LGPL libmpv (ADR-0012); media_kit принимает только URI, доступа к `mpv_handle` у приложения нет (ADR-0038). Сетевые файлы плеер читает через loopback-прокси по HTTP.

## Факторы решения

- Одна шкала и перемотка по всему фильму; прогресс хранится на элементе, а не на части.
- Работает одинаково для локальных путей и URL прокси, на Linux и Android.
- Без форка media_kit, без нативного кода, без новых зависимостей и без GPL.
- Ядро не привязано к конкретному плееру: нативные плееры (PLAY-AND, PLAY-APL) склеивают части своими средствами.

## Рассмотренные варианты

1. **EDL mpv (`edl://`)**: ядро отдаёт упорядоченный список частей, клиент собирает URI `edl://%<байты>%<часть 1>;%<байты>%<часть 2>`.
2. Протокол FFmpeg `concat:` (побайтная склейка): только для VOB (для `cd1`/`cd2` с двумя заголовками контейнера не годится), нужен `lavf://` и протокол в белом списке media_kit.
3. Плейлист из частей: у каждой части своя шкала, перемотки через границу нет, «Продолжить» пришлось бы считать по частям.
4. Склейка (ремукс) в один файл при скане: копия гигабайтов, запись в источник или кэш, сетевые источники только на чтение.

## Решение

Вариант **1**.

- Ядро: `Catalog::play_parts(source_id, rel_path)` (`pa-catalog/src/play.rs`) возвращает все присутствующие части группы `part` по номеру — с части 1, даже если передана вторая; иначе один файл. Через `pa-frb` — `CoreLibrary::play_parts`. Синтаксис EDL в ядро не попадает.
- Приложение: `RustLibrary.playParts` превращает части в локальные пути или URL прокси, `playVideo` при двух и более частях передаёт плееру `partsUri(parts)` из `pa_player` — URI EDL; длина каждой части — в байтах UTF-8, поэтому `;`, `,` и `%` в путях и URL безопасны. Начало и длина сегментов не задаются: mpv берёт каждую часть целиком от её первой метки времени. Прогресс сохраняется по `item.id`, длительность — общая.
- media_kit 1.2.6 передаёт URI с незнакомой ему схемой в `loadfile` без изменений (`Media.normalizeURI`, `uri_parser`: схема не сетевая и не `file`), отдельный путь не нужен.
- Причина «не играет» (`Unplayable`, ADR-0043) идёт через `CoreItem.unplayable` и `CoreVersion.unplayable` кодом (`disc_image`); приложение показывает переведённое сообщение вместо плеера.

Проверено на настоящем LGPL libmpv (`pa_player/test/edl_libmpv_test.dart`): фильм из двух AVI и DVD из MPEG-PS, разрезанного по сектору 2048 байт на два VOB (вторая часть начинается с середины потока), играют одной шкалой 12 с локально и по HTTP с `Range`; перемотка во вторую часть даёт верную позицию и верный кадр. mpv для VOB сам учитывает начальную метку второй части (сегмент `6.0–12.0` из источника с `start 6.6`).

Основной поток Blu-ray по самому длинному плейлисту `.mpls` (опция LIB-020) не сделан: нужен разбор MPLS, склейка клипов по плейлисту и смена выбора основного потока, от которого зависят совпадения и прогресс (ADR-0043). Это отдельная задача.

### Последствия

- Хорошо: DVD из папки и фильм из частей играют целиком, с общей шкалой, «Продолжить» и Up Next работают как с одним файлом; путь одинаков для локальных и сетевых источников.
- Хорошо: mpv делает главу на каждую часть.
- Плохо: mpv открывает все части при загрузке (по сети — несколько HTTP-запросов через прокси до начала воспроизведения).
- Плохо: субтитры рядом с частями (`Movie.cd1.srt`, `Movie.cd2.srt`) не склеиваются; приложение подгружает только субтитры первой части.
- Нейтрально: нативные плееры (Media3, AVPlayer) получат тот же список частей из ядра и склеят его своими средствами (`ConcatenatingMediaSource`, `AVMutableComposition`).
