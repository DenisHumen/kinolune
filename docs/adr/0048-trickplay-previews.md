# ADR-0048: Trickplay-превью — ключевые кадры через FFmpeg ядра, BIF как кэш, чтение BIF и Jellyfin

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** PLAY-009, LIB-006, LIB-013, LIB-018, UI-013; [ADR-0034](0034-pa-probe-libavformat-runtime.md), [ADR-0036](0036-image-cache-in-core.md), [ADR-0038](0038-network-playback-loopback-proxy.md)

## Контекст и проблема

При перемотке плеер должен показывать кадр под пальцем (`docs/research/01` §1.5). Done when PLAY-009: для двухчасового фильма с SMB превью доступно меньше чем за 60 с, показ при перемотке — меньше чем за 100 мс.

Плеер приложения — media_kit (ADR-0012), второго экземпляра libmpv для превью у нас нет, а держать второй декодер в UI дорого. В ядре уже есть FFmpeg (LGPL, грузится в рантайме, `pa-probe`, ADR-0034) и чтение любых источников через `pa-vfs` (LIB-018). Превью нужны одинаково для локальных папок, SMB и WebDAV, без монтирования.

Часть медиатек уже содержит превью других программ: BIF (Plex, Emby, Roku) и папки trickplay Jellyfin 10.9+ рядом с файлом.

## Факторы решения

- Скорость по сети: читать как можно меньше байт (ключевой кадр, а не GOP).
- Превью по всей шкале как можно раньше, ещё до конца генерации.
- Только LGPL FFmpeg в рантайме, без новых нативных библиотек и без GPL.
- Один формат хранения, удобный для чтения с диска и по сети.
- Чистый API для OSD (UI-013) и для серверной фоновой задачи.

## Рассмотренные варианты

1. **Ключевые кадры через FFmpeg ядра** (`pa-probe`: libavformat, libavcodec, libswscale), JPEG в Rust, хранение — BIF в LRU-кэше. Чтение BIF и Jellyfin рядом с файлом.
2. Второй экземпляр mpv/media_kit в UI для «живого» превью: тяжёлый, на TV и телефонах не годится, по сети читает GOP целиком.
3. Внешний `ffmpeg` CLI как у Jellyfin: в клиентах CLI нет, а GPL-сборки системного ffmpeg нам нельзя.
4. Спрайт-листы (как Jellyfin) вместо BIF: лишний шаг сборки листа и обрезка на стороне UI для каждого кадра.

## Решение

Вариант **1**.

- **`pa-probe::FrameGrabber`**: seek (`AVSEEK_FLAG_BACKWARD`) к ключевому кадру не позже нужного времени, чтение пакетов до первого ключевого, декод только его (отправка пакета и drain), масштабирование `sws_scale` в RGB 320 px с учётом SAR и матрицы BT.601/709/2020; PQ (HDR10) приводится к SDR простым тон-маппингом. Если после seek ключевого кадра нет (MPEG-TS, конец файла), шаг назад, в крайнем случае чтение с первого байта. Функции декодера и libswscale грузятся лениво, отдельно от таблицы пробера: проба работает и без libswscale. Зеркалится только префикс `AVFrame` до `format` (не менялся с FFmpeg 1.x, смещения закреплены тестом).
- **`pa-trickplay`** (новый крейт): интервал 10 с (как у Jellyfin), для длинных медиа — больше, не более 1200 кадров; до 4 параллельных грабберов поверх одного `ByteSource`; порядок «от грубого к точному» (каждый 32-й, затем 16-й…), поэтому уже через доли секунды превью есть по всей шкале и `frame_at` отвечает ближайшим готовым кадром. Повтор одного ключевого кадра (длинный GOP) не декодируется второй раз. JPEG кодирует `jpeg-encoder` (чистый Rust).
- **Хранение — BIF** (формат Roku): один файл на медиафайл, индекс и JPEG подряд; тот же формат читается рядом с медиа (Plex/Emby). Кэш — LRU по mtime с лимитом размера, как кэш картинок (ADR-0036); ключ — источник, путь, размер и mtime файла.
- **Порядок источников превью**: BIF рядом с файлом → папка Jellyfin `<имя>.trickplay/<ширина> - <cols>x<rows>/<n>.jpg` (отдаётся лист и прямоугольник тайла) → наш кэш → генерация, если включена.
- **Сеть**: у `pa_vfs::ByteSource` появился необязательный метод `hint_random_access`; SMB и WebDAV после него читают ровно запрошенное без упреждающего чтения для воспроизведения. Превью открывают собственный дескриптор файла, плеер (прокси) не затронут. Без этого SMB-бэкенд на каждом ключевом кадре запускал prefetch на 64 МиБ: 1,3 ГиБ трафика вместо 200 МиБ.
- **API**: `Trickplay::prepare(Media) -> Session` (фон), `Session::frame_at`, `status`, `release`; `Trickplay::ensure` и `JOB_KIND = "trickplay"` — для серверной фоновой задачи (`pa-jobs`). В Dart: `CoreTrickplay`/`CoreTrickplaySession` (`pa-frb`), `LibraryTrickplay` (`pa_library`), `TrickplaySource`/`TrickplayFrame`/`TrickplayLoader`/`TrickplayImage` (`pa_player`) — интерфейс для OSD UI-013. Клиент генерирует лениво (при открытии файла), по опции `trickplayGenerate` (по умолчанию включена); Up Next готовит превью только при первой перемотке.
- **Лицензия `jpeg-encoder`**: `(MIT OR Apache-2.0) AND IJG` — DCT взят из libjpeg. IJG — разрешительная лицензия без копилефта (требует упоминания в документации), поэтому в `deny.toml` добавлено исключение только для этого крейта.

Замеры на сервере сборки (сгенерированный фильм 2 ч, 1080p H.264 8 Мбит/с с зерном, GOP 10 с, 7,2 ГБ, Samba в Docker, 4 воркера; файл в page cache сервера):

| Канал | Покрытие всей шкалы | Все 721 кадр | Прочитано |
|---|---|---|---|
| локальный диск | 0,10 с | 1,4 с | — |
| SMB, loopback | 0,13 с | 1,9 с | — |
| SMB, задержка 2 мс, 200 Мбит/с | 0,5 с | 9,2 с | 199 МиБ |
| SMB, задержка 5 мс, 100 Мбит/с | 1,0 с | 18,5 с | 199 МиБ |

`frame_at` из памяти: в среднем 50–80 нс, худший случай меньше 2 мкс.

### Последствия

- Хорошо: done when PLAY-009 выполняется с запасом; превью работают для локальных, SMB и WebDAV источников одинаково.
- Хорошо: превью Plex/Emby/Jellyfin рядом с файлом используются без генерации.
- Плохо: ключевой кадр не всегда точно на отметке (у кадра честное время, но GOP 10 с даёт шаг до 10 с); точный кадр потребовал бы декодировать GOP.
- Плохо: тон-маппинг HDR упрощённый (без перевода цветового охвата BT.2020), Dolby Vision профиля 5 даёт неверные цвета.
- Плохо: интервал папки Jellyfin не записан в ней: берём 10 с или оцениваем по длительности.
- Нейтрально: сервер (SRV) пока не ставит задачу `trickplay` в очередь — нужен обработчик в сервере, когда у него появится своя медиатека.
