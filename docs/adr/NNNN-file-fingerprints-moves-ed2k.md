# ADR-NNNN: Отпечатки файлов: OSHash в скане и для переездов, ed2k — фоновой задачей по политике источника

- **Статус:** Предложен
- **Дата:** 2026-11-15
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-004, LIB-003, LIB-005, LIB-021, SYNC-004, CORE-011; `docs/research/03-metadata-recognition.md` §4.2; ADR-0032 (ключ `file:` — OSHash)

## Контекст и проблема

С ADR-0032 скан уже считает OSHash каждого файла (`files.oshash`, он же `files.fingerprint` — ключ `file:`), но:

- переименованный или перемещённый файл скан видел как «старый пропал, новый появился»: матч, оффлайн-копии, версии и сегменты пропуска висят на `files.id` и терялись (прогресс переживал переезд только благодаря ключу `file:`);
- ed2k (нужен для AniDB) не считался вовсе. Он читает файл целиком — на SMB это гигабайты трафика и батарея.

## Факторы решения

- OSHash читает 2 × 64 КиБ: дёшев и по сети, его можно считать для всех файлов в скане.
- ed2k нельзя считать в скане и нельзя по умолчанию гонять по сети с телефона.
- Значение OSHash менять нельзя: иначе прогресс под `file:`-ключами потеряет файлы (ADR-0032).
- Лицензии: только MIT/Apache-зависимости.

## Рассмотренные варианты

1. Переезд по OSHash после отпечатков: сохраняется **старая** строка `files`, она получает новый путь; ed2k — задача `pa-jobs` с политикой источника.
2. То же, но сохраняется новая строка, а ссылки (`matches`, `offline_copies`, `skip_*`, `version_prefs`, `twitch_files`…) переписываются на неё.
3. Переезд по `inode` в сканере.

## Решение

Выбран вариант **1**.

- **OSHash** остаётся как в ADR-0032 (`pa_catalog::fingerprint::oshash`); для файлов от 128 КиБ значение совпадает с эталонной реализацией OpenSubtitles (тест-векторы).
- **Переезд.** Сразу после отпечатков скан и пересканер папок вызывают `pa_library::fingerprints::follow_moves`: живая новая строка и пропавшая строка того же источника с тем же OSHash и размером — один файл. Старая строка получает путь, mtime, inode новой и строки структуры папок (`file_group_members`, `group_assets`) нового пути, новая удаляется. Поэтому за файлом идут все таблицы, ссылающиеся на `files.id`, в том числе будущие. Пара не образуется, если новая строка появилась раньше чем за сутки до пропажи старой (это копия, оригинал которой удалили) или у новой строки уже есть матч, выбранный пользователем. Из нескольких пропавших кандидатов берётся пропавший последним. Переезд между источниками не отслеживается (прогресс всё равно переживает его по ключу `file:`).
- **ed2k** (MD4 по блокам 9 728 000 байт, крейт RustCrypto `md4`, MIT/Apache) — `pa_catalog::fingerprint::ed2k`. В `files.ed2k` пишется вариант исходного eDonkey («red»): при размере, кратном блоку, добавляется MD4 пустого блока; он воспроизводит опубликованное значение для 9 728 000 нулевых байт. Вариант eMule («blue») возвращается рядом (`without_empty_chunk`), но не хранится.
- **Задача** `file_ed2k` (`Ed2kHandler`, `ed2k_job`) или `Catalog::hash_ed2k`; политика источника `sources.ed2k_policy`: `auto` (по умолчанию: локальные папки в фоне, сеть — когда приложение сообщает «простаивает на Wi-Fi», или по запросу), `always`, `never` (только по запросу). Фоновая задача не идёт от батареи, «простой» требует безлимитной сети, задача по запросу — приоритет пользователя. Хэш сохраняется сразу после каждого файла; файл, изменившийся при чтении, не сохраняется; нечитаемый повторяется через сутки.

## Последствия

- Хорошо: матч, оффлайн-копии и прочее переживают переименование и перенос; ed2k не стоит трафика по умолчанию; SYNC-004 получает OSHash как ключ контента.
- Плохо: две одинаковые копии, одна из которых исчезла, а другая появилась в течение суток, считаются переездом; в редком случае файла, кратного 9 728 000 байт, AniDB может ждать «blue» — тогда его можно посчитать заново.
- Не сделано здесь: приложение пока не ставит задачу `file_ed2k` и не показывает политику ed2k в настройках источника (нужна привязка FRB) — это решение владельца о том, на каких устройствах включать фон.
