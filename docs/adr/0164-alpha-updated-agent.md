# ADR-0164: `alpha-updated` — агент обновлений NAS-ОС поверх bootc: сокет, окно обслуживания, вето медиасервера

- **Статус:** Предложен
- **Дата:** 2026-11-25
- **Решают:** мейнтейнер (владелец делегировал решения)
- **Связано:** DIST-009, DIST-010, DIST-011, DIST-012, DIST-013, DIST-014; [ADR-0010](0010-nas-os-phase0.md); [исследование 05](../research/05-nas-linux-distro.md) §4.1–4.2

## Контекст и проблема

ADR-0010 замаскировал `bootc-fetch-apply-updates.timer`: стоковый таймер ставит обновление и сразу перезагружает машину, в том числе посреди фильма. Нужен свой агент, который:

- проверяет, скачивает, ставит и откатывает обновления через штатные команды bootc;
- никогда не перезагружает NAS во время воспроизведения;
- даёт API для веб-админки (DIST-013/014) и, через неё, для клиентского приложения;
- не открывает управление ОС в сеть.

Нужно было решить пять вопросов: транспорт и права API, модель настроек «авто», как применять скачанное и перезагружаться, как медиасервер запрещает перезагрузку, и где хранить состояние.

## Рассмотренные варианты

**Транспорт API.**

1. Unix-сокет, доступ по группе: `root:alpha-admin 0660`, сокет создаёт systemd.
2. HTTP на loopback с токеном.
3. D-Bus-сервис с polkit.

**Вето медиасервера.**

1. Агент сам спрашивает медиасервер (`GET /api/v1/system/activity`, SRV-019) по HTTPS на loopback.
2. Медиасервер берёт блокировку logind (`systemd-inhibit --what=shutdown`).
3. Файлы-«запреты» в `/run`.

**Применение и перезагрузка.**

1. `bootc upgrade --apply`: bootc сам перезагружает.
2. `bootc upgrade --from-downloaded` без `--apply`, затем агент сам делает `systemctl reboot`.

## Решение

1. **API — HTTP/JSON на unix-сокете `/run/alpha-updated/api.sock`.** Сокет создаёт `alpha-updated.socket` (`SocketGroup=alpha-admin`, `SocketMode=0660`). Группа задана в `sysusers.d`, `alpha-admin.service` получает её через `SupplementaryGroups=`. Наружу и даже на loopback API не слушает: права проверяет ядро, токены не нужны. Все изменяющие запросы попадают в журнал с uid, gid и pid клиента (`SO_PEERCRED`). D-Bus и polkit дали бы то же, но с лишней зависимостью (`godbus`) и XML-интерфейсом. Админке всё равно нужен REST, а прокси HTTP→HTTP тривиален. Пути — `/v1/...`; во внешнем API админки они станут `/api/system/update…` (05 §4.1).
2. **Настройки:** `channel` (`stable` | `beta`), `auto` (`off` | `download` | `install`, для простых клиентов принимается и `true`/`false`), `window` (`"HH:MM-HH:MM"`, местное время, можно через полночь). По умолчанию `install` в окне 03:00–05:00 (05 §4.2 п.8). Режим `off` всё равно проверяет обновления раз в 6 часов: проверка — это только манифест, а пользователь видит «есть обновление» («только уведомлять»). Новое устройство берёт канал из тега, с которого его установили.
3. **Скачивание отдельно от применения.** Фоновая загрузка идёт через `bootc upgrade --download-only`: деплоймент заблокирован и не применится при случайной перезагрузке. Применение — `bootc upgrade --from-downloaded`, без `--apply`. Перезагружает сам агент (`systemctl reboot`). Так между «разблокировать» и «перезагрузить» остаётся точка, где агент ещё раз спрашивает вето. Если за это время началось воспроизведение, деплоймент остаётся staged, и агент перезагрузит машину позже в том же окне.
4. **Вето — интерфейс `Vetoer` и HTTPS-реализация с пиннингом.** Агент спрашивает медиасервер `GET https://127.0.0.1:8487/api/v1/system/activity` (SRV-019: только loopback, сессии на паузе тоже считаются занятостью) и ждёт `{busy, sessions, reason}`.
   - **Проверка сервера.** У сервера самоподписанный сертификат (SRV-004). При каждом запросе агент читает файл сертификата `/var/lib/alpha-media/tls/server.crt` и сверяет SHA-256 DER-сертификата сервера с этим файлом. Системные CA не используются; `InsecureSkipVerify` включён только вместе с этим пином. Читать файл при каждом вызове проще, чем хранить пин: при перевыпуске сертификата ничего синхронизировать не нужно, а root, читающий файл, и так доверяет этой машине.
   - **Решения по ответу:**
     - `busy` или `sessions > 0` — откладывает;
     - несовпадение пина, другая ошибка TLS, тайм-аут, другой код ответа или неверный JSON — тоже откладывает («не знаю» значит «не перезагружать»), в журнал пишется понятная строка;
     - нет файла сертификата (сервер не установлен или ни разу не запускался), отказ в соединении или `404` — «не занят»: без сервера ничего не играет.
   - **Plain HTTP** — только запасной путь для сервера с `[tls] enabled = false`. Его определяют, когда нет файла сертификата или когда на TLS-рукопожатие пришёл HTTP-ответ (обычно 400). Отдельно читать конфиг сервера не нужно.

   Явное «Обновить сейчас» и «Откатить» от пользователя вето не проверяют. Блокировки logind оставлены на потом: их можно добавить вторым `Vetoer` через `MultiVeto`, но тогда пришлось бы держать блокировку на каждую сессию в медиасервере и тянуть D-Bus в агент.
5. **Одна операция за раз**, с фоновым выполнением: API отвечает `202` и описанием операции, на вторую операцию — `409 busy`. Расписание: шаг раз в минуту; проверка раз в 6 часов; после ошибки — повтор не раньше чем через 30 минут, чтобы не долбить реестр без сети.
6. **Состояние — `/var/lib/alpha/updated/{settings,state}.json`**, запись атомарная (temp, fsync, rename). В `state.json` есть запись о последнем применении. После перезагрузки агент сверяет её с загруженным digest и ставит `booted` или `not-booted`: старая версия загрузилась, потому что greenboot откатил обновление или его выбрали в меню. Это опора для DIST-010 (откат `@var`) и DIST-011 (сообщение «обновление отменено»).
7. **Сборка:** Go только со стандартной библиотекой, без внешних модулей. Бинарник статический (`CGO_ENABLED=0`), собирается в стадии `go-build` того же закреплённого по digest образа `fedora-bootc` (Go из Fedora). Второй базовый образ закреплять не нужно, лицензии внешних модулей проверять не нужно. Демон работает от root без `ProtectSystem` и приватных mount-пространств: bootc нужно настоящее пространство имён (`/sysroot`, `/boot`).

## Последствия

- `+` NAS не перезагружается во время просмотра: проверка перед разблокировкой и ещё одна прямо перед перезагрузкой, а при любом сомнении — отложить.
- `+` Случайная перезагрузка (отключили свет, пользователь перезагрузил сам) не ставит скачанное обновление без разрешения.
- `+` Админке и приложению хватает одного маленького JSON API; права — обычная группа Unix.
- `−` Вето работает, только пока медиасервер с SRV-019 отвечает на `/api/v1/system/activity`. Заглушка фазы 0 отвечает 404, то есть «не занят». Если в конфиге сервера задан свой `[tls] cert`, путь нужно передать агенту (`ALPHA_MEDIA_TLS_CERT`). Иначе агент не найдёт файл и посчитает сервер неустановленным.
- `−` `--download-only` и `--from-downloaded` требуют достаточно новый bootc (в базе 45 — 1.17). Для версий без поля `downloadOnly` в статусе агент сам помнит скачанный digest.
- `−` Смена канала (`bootc switch`) создаёт обычный staged-деплоймент, а не download-only: он применится при любой следующей перезагрузке. Это осознанно, канал меняет сам пользователь.
- Поэтапная раскатка по манифесту и когортам — DIST-012. Снапшот `@var` перед применением — DIST-010. Проверки greenboot — DIST-011.
