# ADR-0052: Live Twitch с низкой задержкой — локальный HLS-прокси, prefetch-сегменты, реклама «как есть»

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** TWI-006, TWI-004, TWI-014, UI-013; `docs/research/06` §2.1, §2.4, §6.4; [ADR-0012](0012-release-0-1-player-media-kit.md), [ADR-0038](0038-network-playback-loopback-proxy.md), [ADR-0041](0041-build-flavor-mechanism.md)

## Контекст и проблема

Нативное воспроизведение Twitch (TWI-004, только flavor `full`) отдаёт плееру мастер-плейлист usher. Для live нужны: задержка меньше 5 с в режиме «Низкая задержка», догон эфира, кнопка «К эфиру», индикатор задержки в статистике OSD и распознавание рекламы, чтобы показать «Реклама · 0:15», запретить перемотку и не считать рекламу просмотром. Блокировать, пропускать или ускорять рекламу нельзя (06 §2.4, AGENTS.md).

Twitch добивается низкой задержки prefetch-сегментами (`#EXT-X-TWITCH-PREFETCH`): следующие 1–2 сегмента объявляются до того, как закодированы, и отдаются потоком по мере кодирования. HLS-демуксер FFmpeg (внутри libmpv/media_kit) этот тег не знает и стандартные LL-HLS части (`#EXT-X-PART`) тоже не читает. Задержку и рекламу нужно привязать к `#EXT-X-PROGRAM-DATE-TIME` и `#EXT-X-DATERANGE`, а их libmpv наружу не отдаёт.

## Факторы решения

- Задержка < 5 с с тем плеером, что уже есть (media_kit/libmpv, ADR-0012), без своего демуксера.
- Ни один сегмент не отбрасывается и не меняется — реклама в том числе; это должно проверяться тестом.
- Код Twitch GQL/usher/HLS — только в `full` (`cfg(pa_twitch_native)`, ADR-0041).
- Честная метрика задержки: «стена» минус program date-time кадра на экране.
- Не трогать OSD: UI-013 строит панель статистики, TWI-014 — плеер стримов.

## Рассмотренные варианты

1. **Локальный прокси в ядре** (`pa_twitch::playback::live::LiveProxy`): плеер открывает `http://127.0.0.1:<порт>/<токен>/live.m3u8`; прокси переписывает медиаплейлист (prefetch → обычные сегменты), сегменты передаёт потоком байт-в-байт и по пути знает program date-time отданного плееру, live edge и рекламные интервалы.
2. Отдавать плееру URL usher напрямую и мерить задержку по `time-pos`: prefetch-сегменты не играются (задержка 6–10 с), program date-time и DATERANGE плееру недоступны.
3. Собственный HLS-клиент с подачей потока в mpv через `stream_cb` (`pa-player-io`): больше кода, та же логика, без выигрыша для live.
4. Встроенный плеер Twitch (TWI-005): это отдельный путь для store-сборок, не нативное воспроизведение.

## Решение

Выбран вариант **1 — локальный прокси**, потому что он даёт prefetch-сегменты стандартному демуксеру FFmpeg и при этом видит всё, что нужно для задержки и рекламы, не меняя ни байта медиа.

- **Плейлист** (`MediaPlaylist`): сегменты с program date-time (из тега или выведенный от предыдущего сегмента до `#EXT-X-DISCONTINUITY`), prefetch-сегменты (длительность — как у последнего обычного), стандартные LL-HLS теги считаются, но не играются, `#EXT-X-DATERANGE` класса `twitch-stitched-ad` (или `ID` `stitched-ad-…`) — рекламный перерыв; сегменты с заголовком `Amazon|…` — тоже реклама.
- **Перезапись** (`MediaPlaylist::rewrite`): каждая строка остаётся как прислал Twitch; меняются только URI сегментов (`s/<sequence>.<ext>` на прокси) и `URI` у `#EXT-X-MAP`. В режиме «Низкая задержка» `#EXT-X-TWITCH-PREFETCH` становится `#EXTINF` + URI, в режиме «Стабильно» prefetch-строки не выводятся (плеер ждёт полных сегментов). Сегменты не удаляются никогда.
- **Сегменты** идут от Twitch к плееру потоком по чанкам (chunked, если у источника нет `Content-Length`): prefetch-сегмент приходит в плеер по мере кодирования.
- **Задержка** = `now − PDT(playhead)`, где `PDT(playhead)` = program date-time конца отданных плееру данных (конец последнего полного сегмента плюс доля текущего по байтовой скорости предыдущего) минус секунды в кэше плеера (`demuxer-cache-time − time-pos`, их сообщает Dart-контроллер).
- **Догон** (`CatchUpPolicy`): цель 3 с («Низкая задержка») или 8 с («Стабильно»); выше цели на 1 с — 1,05×, на 3 с — 1,1×, с гистерезисом до цели; mpv сохраняет высоту тона. Во время рекламы — всегда 1,0×. Скорость, выбранную пользователем, не трогаем. Отставание больше цели на 20 с — `should_jump`: UI предлагает «К эфиру».
- **«К эфиру»**: прокси забывает позицию (`/reset`), плеер заново открывает URL прокси и стартует у края. Во время рекламы недоступно (`seek_allowed = false`).
- **Опции libmpv** (`liveMpvOptions` в `pa_player`): `live_start_index=-2` (первый prefetch-сегмент, то есть кодируемый сейчас) или `-3` для «Стабильно», короткий `analyzeduration`, `cache-pause-wait`, `video-latency-hacks`, перемотка назад в пределах кэша (`demuxer-seekable-cache`, `demuxer-max-back-bytes`).
- **Данные для OSD**: `LivePlaybackController.status` (`LiveStatus`: задержка, режим, скорость догона, реклама с остатком, `seekAllowed`, `countsAsProgress`, строки `info` для панели статистики). Сам OSD не меняется — его делают UI-013 и TWI-014.
- Отчёт прокси доступен и из Rust (`LiveProxy::report`), и по HTTP (`/<токен>/stats.json?ahead=&rate=`), поэтому Dart-слою не нужны новые FRB-функции, кроме запуска прокси (в TWI-014).

Не входит: DVR по всему окну плейлиста (только назад в пределах кэша плеера), «Смотреть с начала эфира» через VOD текущего стрима, переключатель режима и плашка «Реклама» в UI (TWI-014), FRB-обвязка запуска прокси (TWI-014).

### Последствия

- Хорошо: задержка ≈ 1 с на тестовом потоке (вместо 6–10 с без prefetch), метрика сверена с истиной; реклама проходит полностью, это проверяют тесты.
- Хорошо: прокси переиспользует подход ADR-0038 (loopback + случайный токен) и не зависит от плеера: годится и для AVPlayer/ExoPlayer.
- Плохо: все байты live идут через loopback (копирование в памяти, без диска); ещё один поток с tokio-рантаймом на время просмотра.
- Плохо: задержка — оценка: часть данных между прокси и кэшем mpv (буферы FFmpeg) не видна; на тесте ошибка < 0,5 с.
- Требует работы: TWI-014 — запуск прокси из приложения (FRB), переключатель «Низкая задержка / Стабильно», «К эфиру», плашка «Реклама»; UI-013 — вывод `LiveStatus.info` в панели статистики.

### Как проверяем соблюдение

- `core/crates/pa-twitch/tests/live.rs`: фейковый origin в стиле Twitch (prefetch, `twitch-stitched-ad`) → прокси → клиент как HLS-демуксер FFmpeg; все сегменты, рекламные включительно, приходят байт-в-байт и по порядку.
- `clients/flutter/packages/pa_player/test/live_libmpv_test.dart`: тот же сценарий на настоящем libmpv с сегментами из FFmpeg; задержка < 5 с, плеер проходит рекламу целиком на скорости 1×, контроллер помечает её; «К эфиру» после паузы возвращает задержку < 5 с.
