# ADR-0088: Обновление из приложения во флейворе `full`: GitHub Releases раз в сутки, SHA256SUMS в ядре и хук minisign, PackageInstaller и замена AppImage

- **Статус:** Предложен
- **Дата:** 2026-11-15
- **Решают:** владелец проекта
- **Связано:** `PKG-018`, `PKG-009`, `PKG-005`, `PKG-008`, `PKG-011`, `CORE-013`, `CORE-014`; [ADR-0004](0004-no-project-servers-local-sync.md), [ADR-0007](0007-store-full-build-flavors.md), [ADR-0039](0039-remote-config-minisign.md), [ADR-0041](0041-build-flavor-mechanism.md), [политика конфиденциальности §4](../legal/privacy-policy.md)

## Контекст и проблема

Сборки из GitHub Releases (флейвор `full`) обновляются только вручную: пользователь должен сам заметить релиз, скачать файл и поставить его. Владелец попросил обновление из приложения. Своих серверов у проекта нет (ADR-0004), поэтому источник — только GitHub. Магазины (флейвор `store`) обновляют приложение сами и запрещают самоустановку кода, поэтому в store-сборке не должно быть ни кода установки, ни разрешения Android `REQUEST_INSTALL_PACKAGES`.

Важная деталь текущих релизов: `release-app.yml` подписывает APK ключом из секретов, а пока их нет — отладочным ключом Flutter. На чистом раннере GitHub этот ключ создаётся заново в каждом запуске. Проверено на реальных файлах: сертификат `kinolune-0.1.0-alpha.5-android-x86_64.apk` — SHA-256 `55243d69…`, `alpha.6` — `03c6ae4b…` (оба `CN=Android Debug`). Android ставит обновление только с тем же ключом, поэтому между альфами обновление поверх невозможно — ни из приложения, ни руками.

## Факторы решения

- Без серверов проекта и без идентификаторов в запросах; проверку можно выключить.
- Подменённый или повреждённый файл не должен установиться ни при каких условиях.
- Подпись релизов: ключа пока нет, создавать его агент не вправе — нужен «спящий» механизм, который включается без новой версии приложения.
- Store-сборки без кода установки и разрешения (политики Google Play, App Store).
- Понятное сообщение, когда Android откажет из-за другого ключа подписи.
- Минимальные правки общих файлов приложения (настройки, ARB, `main.dart`).

## Рассмотренные варианты

1. **Свой Dart-код: GitHub API + проверка в ядре + установка по платформам** (выбран).
2. Пакет вроде `ota_update`/`in_app_update`: Android-only, не умеет AppImage, `in_app_update` — Google Play.
3. AppImageUpdate/zsync для Linux: нужен `.zsync` в релизе и встроенный в AppImage URL обновления; дельты для 45 МБ не окупаются, а зависимость от внешнего инструмента усложняет сборку.
4. Только уведомление «есть новая версия» со ссылкой: не решает задачу владельца.

## Решение

**Где и когда.** Только флейвор `full` (новая возможность `self-update` в `pa-flavor`, `AppFlavor.selfUpdate` в Dart). Раз в сутки (при старте и возврате приложения, если прошло 24 ч) и по кнопке «Проверить обновления» в «Настройки → О программе → Обновления» приложение делает `GET https://api.github.com/repos/DenisHumen/project_alpha/releases?per_page=30` с `User-Agent: Kinolune` — без токена, cookie, версии и идентификаторов устройства. Ошибки автоматической проверки молчат; ручной — показываются (в том числе лимит GitHub 60 запросов в час с адреса). Переключатель «Проверять обновления раз в день» выключает автоматическую проверку.

**Что предлагается.** Релизы с тегом `app-v<semver>`, не черновики; версия сравнивается по semver (`0.1.0-alpha.6 < 0.1.0-alpha.10 < 0.1.0`). Канал: «Стабильные релизы» или «Включая пре-релизы»; по умолчанию — пре-релизы, пока сама установленная версия — пре-релиз (сейчас альфа), иначе стабильные. Текущая версия читается у платформы (`versionName`, `version.json`) — это `--build-name` релизной сборки. Changelog — текст релиза до сгенерированной таблицы «Downloads», без блока-предупреждения. Найденная автоматически версия показывается баннером поверх приложения («Обновить» / «Позже»; «Позже» скрывает баннер для этого релиза, в «О программе» он остаётся).

**Какой файл.** Android — APK первой подходящей ABI из `Build.SUPPORTED_ABIS` (`android-arm64-v8a`, `armeabi-v7a`, `x86_64`), иначе `universal`: split-APK устанавливается поверх и split, и universal (код версии split больше). Linux — `x86_64.AppImage`, если приложение запущено из AppImage (`$APPIMAGE`) и его папка доступна на запись; иначе `linux-x86_64.tar.gz` и инструкция. Windows и macOS — пока страница релиза (PKG-005, PKG-008). Flatpak/Snap (`FLATPAK_ID`, `SNAP`) — проверки нет, обновляет система. Store-сборки — ссылка на страницу в магазине (известна пока только Google Play).

**Проверка (ядро, новый крейт `pa-update`, `update_verify_artifact` в `pa-frb`).**

1. *Хук подписи.* В подписанном удалённом конфиге (ADR-0039) появилась секция `updates.release_public_key` — строка `minisign.pub`. Нет ключа — шаг пропускается. Есть — `SHA256SUMS.minisig` обязателен и должен проверяться этим ключом (prehashed, `file:SHA256SUMS` в доверенном комментарии — та же проверка `TrustedKey`, что у конфига); битый ключ в документе делает весь документ невалидным, битый ключ на проверке — отказ. Цепочка доверия: ключ конфига вшит в приложение, ключ релизов приходит в подписанном конфиге — ротация без новой версии приложения.
2. *Контрольная сумма.* Файл должен быть в `SHA256SUMS` релиза и давать тот же SHA-256 (считается потоково). Размер сверяется ещё и с размером из API.

Любой отказ — файл удаляется, установка не начинается, пользователь видит «файл повреждён или подменён». Без ключа подписи контрольные суммы защищают от повреждения и обрыва, но не от подмены релиза на GitHub — это ограничение до появления ключа.

**Kill-switch.** Kill-switch `updates.install` (или `updates.*`) в удалённом конфиге оставляет только «Открыть страницу релиза» — на случай сломанного релиза или установщика.

**Установка.**

- *Android* (`src/full` в Gradle): `PackageInstaller`-сессия, системное подтверждение обязательно. Разрешение `REQUEST_INSTALL_PACKAGES` и приёмник результата — в `src/full/AndroidManifest.xml`, код — `src/full/kotlin/.../UpdateBridge.kt`; store получает пустую заглушку `src/store/...`. Флейвор Gradle берёт из `--dart-define=KINOLUNE_FLAVOR` (свойство `dart-defines`), по умолчанию `store`, как Dart. Перед установкой сравниваются сертификаты скачанного APK и установленного приложения (`GET_SIGNING_CERTIFICATES`, с учётом ротации v3). Другой ключ — установка не начинается, вместо неё сообщение: «Этот релиз подписан другим ключом… удалите Kinolune и установите новую версию со страницы релиза. Медиатека, настройки и прогресс… пропадут, если не синхронизированы». То же сообщение — при `STATUS_FAILURE_CONFLICT` от установщика. Нет разрешения «Установка неизвестных приложений» — кнопка «Разрешить установку» открывает системную страницу.
- *Linux AppImage*: файл скачивается скрытым файлом **в ту же папку** (`.<имя>.update`), проверяется, получает права старого (+x), `fsync`, затем `rename(2)` поверх `$APPIMAGE` — атомарно: после сбоя на диске либо старый, либо новый файл. Имя файла остаётся прежним. Работающий процесс держит смонтированную копию старого файла; «Перезапустить» запускает новый через `sh -c 'sleep 1; exec …'` без переменных старого монтирования (`APPDIR`, `APPIMAGE`, `LIBMPV_LIBRARY_PATH`…) и завершает текущий.
- *tar.gz*: инструкция (скачать, распаковать, заменить папку) и кнопка страницы релиза.

**Проверка флейворов в CI.** `flavors.yml` распаковывает store AAB и падает, если в манифесте или dex есть `REQUEST_INSTALL_PACKAGES`, `InstallResultReceiver` или канал `app.kinolune/updates`; `full-only-patterns.txt` — Dart-строки апдейтера для `libapp.so`. `release-app.yml` требует разрешение в каждом full-APK (`aapt2 dump permissions`).

## Последствия

- Пока APK подписаны одноразовым отладочным ключом, обновление Android из приложения (и вручную) между релизами CI невозможно; приложение объясняет это заранее, не доводя до системной ошибки. Обновление заработает после PKG-009: постоянный ключ в секретах `ANDROID_KEYSTORE_BASE64` и др. Первый релиз с постоянным ключом всё равно потребует одной переустановки (у существующих установок — отладочные ключи).
- AppImage обновляется на месте; tar.gz, Windows и macOS — пока вручную.
- Подпись релизов включается без новой версии приложения: владелец заводит ключ, подписывает `SHA256SUMS` (`minisign -S -m SHA256SUMS`, файл `SHA256SUMS.minisig` в релиз) и публикует ключ в `updates.release_public_key` подписанного конфига. С этого момента релиз без подписи не ставится — подписывать нужно каждый релиз.
- Store-сборки не содержат ни кода, ни разрешения; F-Droid и Flathub — тоже `full`, но F-Droid обновляет сам, Flathub определяется во время работы (см. открытые вопросы).

## Открытые вопросы

- **Постоянный ключ подписи Android (PKG-009, владелец).** Без него обновление Android не работает.
- **Ключ minisign для релизов** и шаг подписи `SHA256SUMS` в `release-app.yml` (ключ — офлайн у владельца, CI подписывать не должен) — решение владельца.
- **F-Droid:** сборка F-Droid — `full`, но самообновление там запрещено политикой; нужна отдельная константа (например, `--dart-define=KINOLUNE_SELF_UPDATE=false`) в рецепте PKG-010.
