# ADR-NNNN: Модель stats overlay и адаптивный буфер: одна запись `PlaybackStats` для всех движков, отчёт через диагностику CORE-008, read-ahead по уровням для сетевых папок и медиасерверов

- **Статус:** Предложен
- **Дата:** 2026-11-18
- **Решают:** владелец проекта (направление: «максимально просто для клиента»), мейнтейнер (детали)
- **Связано:** PLAY-010, PLAY-003 ([ADR-0017](0017-player-engine-contract.md)), UI-013 ([ADR-0050](0050-player-osd.md)), CORE-008 ([ADR-0082](0082-local-diagnostics-pa-log.md)), LIB-018 ([ADR-0038](0038-network-playback-loopback-proxy.md)), LIB-023 ([ADR-0095](0095-fast-network-library-recognition.md)), TWI-006 ([ADR-0052](0052-twitch-live-low-latency.md)), UI-014 ([ADR-0114](0114-track-panels.md))

## Контекст и проблема

В плеере уже есть оверлей статистики (UI-013): движок libmpv раз в секунду кладёт в `EngineState.stats` набор строк «ключ → текст». У контракта ядра (`pa-playback`, PLAY-003) есть своя запись `PlaybackStats` из семи полей, её заполняют mock, Media3 (Kotlin) и движок Apple (Swift). Это два разных описания одного и того же, и в обоих нет того, что просит PLAY-010: профиль кодека, HDR-метаданные (MaxCLL/MaxFALL), профиль Dolby Vision, вывод на экран, статус AFR, путь звука (passthrough, декод, LPCM), скорость сети против битрейта.

Вторая половина задачи — буфер. Сетевые источники (SMB, WebDAV, SFTP, FTP) плеер читает через loopback-прокси ядра (ADR-0038), медиасерверы (Jellyfin, Emby) — по http(s). libmpv держит в памяти не больше `demuxer-max-bytes`: media_kit ставит 32 МиБ, это 13 с потока 20 Мбит/с. На Wi-Fi со всплесками потерь такого запаса не хватает, и фильм встаёт на подгрузку.

Вопросы: где живёт модель и как проверить, что её заполняют все движки; как пользователь отдаёт отчёт; как включается оверлей с пульта; как и где подстраивать буфер; когда подсказывать транскод.

## Факторы решения

- Одна модель для всех движков и один формат на проводе; никаких новых настроек.
- Пульт: всё доступно кнопками Вверх/Вниз/OK/Назад и Info.
- Отчёт — одним нажатием, и туда же, куда пользователь уже отдаёт диагностику (CORE-008), без новых окон и серверов.
- Буфер подстраивается сам: пользователь не должен знать, что такое read-ahead.
- Без новых зависимостей и миграций; движки, написанные до PLAY-010, продолжают собираться.

## Рассмотренные варианты

1. **Расширить строки «ключ → текст» в Dart.** Просто, но модели для Kotlin/Swift нет, контрактный тест невозможен, отчёт — только текст.
2. **Одна запись `PlaybackStats` в ядре, зеркало в Dart с тем же JSON.** Все поля PLAY-010 необязательные (`Option`), правила согласованности — в одной функции `check`, которую гоняет контрактный кейс `stats`.
3. **Отдельное окно «Статистика» с настройками буфера.** Больше контроля, но это настройки, которых пользователь не просил, и лишний экран на ТВ.

Буфер:

- **a.** Оставить буфер libmpv по умолчанию и увеличить его для всех.
- **b.** Уровни буфера по измерениям: старт с обычного запаса, при остановке или медленной сети — больше, в пределах файла уровень только растёт.
- **c.** Адаптивный read-ahead в прокси ядра (`pa-proxy`).

## Решение

Выбраны варианты **2** и **b**.

### Модель

- `pa_playback::PlaybackStats` (новый модуль `stats`) — семь полей PLAY-003 плюс поля PLAY-010: движок и версия, контейнер, профиль, размер, частота кадров, разрядность, `dynamic_range` (тот же `DynamicRange`, что в матрице возможностей), MaxCLL/MaxFALL, профиль DV, аппаратный декодер, потери декодера, вывод (размер, частота экрана, диапазон после тон-маппинга), `afr` (`off`/`switched`/`matched`/`unsupported`), `audio_path` (`passthrough`/`decoded`/`lpcm`), каналы на входе и выходе, частота дискретизации, `source` (`local`/`network`/`server`/`live`), скорость сети, цель буфера, число остановок.
- Все новые поля — `Option`, в JSON `null`; в `pa-ffi` у них `#[uniffi(default = None)]`, поэтому Media3 и движок Apple собираются без правок и заполнят поля в своих задачах (PLAY-AND, PLAY-APL).
- `PlaybackStats::check` — правила: ширина и высота вместе, частоты положительные и конечные, `hw_decoder` только при `hw_decoding`, `audio_path` и `audio_passthrough` согласны, MaxCLL/MaxFALL не у SDR, профиль DV только у Dolby Vision, нет скорости сети у локального файла; `check_progress` — счётчики (потери кадров, остановки) не убывают. Неизвестное поле правило не нарушает.
- Контрактный кейс `stats` (тот же, что гоняют mock, Kotlin и Swift через `pa-ffi`) теперь проверяет `check` и `check_progress` через секунду воспроизведения. Новый кейс не добавлялся: списки кейсов в Swift и Kotlin не меняются.
- Dart-зеркало — `pa_player` `PlaybackStats` с тем же JSON. Файл `core/crates/pa-playback/tests/fixtures/playback_stats.json` читают тесты обеих сторон: каждая разбирает его и записывает обратно тот же JSON. `statsContractProblems` (в `pa_player/testing.dart`) — тот же кейс для Dart-движков: `FakePlayerEngine` в обычных тестах, `MediaKitEngine` на настоящем libmpv (`stats_libmpv_test.dart`).
- `MediaKitEngine` заполняет модель из свойств mpv (`mpv_stats.dart`, чистая функция над чтением свойств — сопоставление проверяется без libmpv). AFR во Flutter-плеере пока `off`: смену режима экрана делают PLAY-DSK-008 и задача Android TV.
- `EngineState.playbackStats` — модель; `EngineState.stats` остаётся для строк вне модели (задержка эфира TWI-006, A/V sync).

### Оверлей и пульт

- Включается как раньше: клавиша S или строка «Показывать статистику» в панели «Информация» (на пульте — кнопка Info или кнопка «Информация» в OSD). Оверлей не берёт фокус.
- Строки — из модели (`PlaybackStats.rows`), подписи и слова переводятся словарём `engineInfoKey`; технические значения (кодеки, `3840×2160`, `HDR10`) не переводятся.
- Подсказка о транскоде — жёлтая строка сверху оверлея, только если источник — медиасервер и он не успевает: скорость сети меньше 1,2 битрейта или 3 остановки. Сетевой папке транскод не предлагается: она не умеет, ей помогает буфер.

### Отчёт в один клик

- В панели «Информация» под переключателем — «Сохранить отчёт о воспроизведении» (`info-stats-export`). Нажатие снимает свежие числа и пишет обычный отчёт диагностики CORE-008 (тот же zip, та же папка «Загрузки», то же окно «Отчёт сохранён» со ссылкой на issue), в котором есть `extra/playback.txt` (строки статистики по-английски и название) и `extra/playback.json` (модель).
- `pa-log` получил `ReportInfo.attachments`: файлы приложения в `extra/` с очищенным именем и той же редакцией путей и секретов, что у логов. Мост `diagnostics_export_report` принимает `attachments`.
- Строка видна, только если в приложении есть диагностика ядра (`PlayerScreen.statsExporter` выставляет `startDiagnostics`); без ядра (демо, тесты) её нет.

### Адаптивный буфер

- Тип источника — по URI, который открывает плеер: loopback http — сетевая папка через прокси (loopback `.m3u8` — эфир Twitch), другой http(s) — медиасервер, остальное — локальный файл. EDL из частей — по первой части.
- Локальные файлы и эфир — без плана: у libmpv для них правильные значения, эфир держит короткий кэш нарочно (ADR-0052). Движок с собственными опциями кэша (`mpvOptions` с `cache`) тоже не трогается.
- Уровни: обычный — 30 с вперёд, продолжение после остановки через 1 с; осторожный — 60 с и 3 с; потери — 120 с и 6 с (реже, но дольше стоять лучше, чем заикаться). Память — запас по времени на битрейт плюс четверть, от 32 МиБ до 512 МиБ на десктопе и 192 МиБ на телефоне и ТВ-приставке. В libmpv: `cache=yes`, `cache-secs`, `demuxer-readahead-secs`, `demuxer-max-bytes`, `cache-pause-wait`.
- Раз в 2 с движок читает `cache-speed`, `demuxer-cache-duration` и битрейт. Скорость учитывается, только пока кэш набирается (полный кэш не читает и выглядел бы медленной сетью), со сглаживанием. Скорость меньше 1,5 битрейта — не ниже осторожного уровня, меньше 1,1 — потери. Остановка (буферизация во время воспроизведения, не сразу после открытия и не в течение 3 с после перемотки) — на уровень выше.
- В пределах файла уровень только растёт — буфер не «дышит»; следующий файл начинает с обычного. Прокси ядра не меняется: он уже читает с упреждением (SMB — ADR-0033), а задержка, которую видит пользователь, — это кэш плеера.

## Последствия

- Хорошо: одна модель и один JSON для всех движков, правила проверяются одним кейсом; отчёт попадает туда же, куда пользователь уже отдаёт диагностику; буфер растёт сам на медленной сети; новых настроек, зависимостей и миграций нет.
- Плохо (цена решения): тип источника угадывается по URI (loopback = папка) — новый вид источника за loopback-прокси придётся учесть в `sourceOfUri`; уровень буфера не снижается до конца файла и может держать до 512 МиБ памяти на десктопе; свойства mpv новых версий (`display-width`, `video-target-params`, `dolby-vision-profile`) на старом libmpv дают `null`, а не ошибку.
- Нейтрально: изменилась подпись `diagnostics_export_report` (новый параметр `attachments`) — привязки FRB перегенерированы; запись `PlaybackStats` в `pa-ffi` выросла, но старые конструкторы Kotlin и Swift работают.

## Как проверяем соблюдение

- `cargo test -p pa-playback`: `tests/stats_model.rs` (фикстура JSON = модель, правила, подсказка о транскоде), кейс `stats` контракта на mock; `cargo test -p pa-log` — `extra/` в отчёте с редакцией; `cargo test -p pa-ffi` — контракт через FFI.
- `pa_player/test/playback_stats_test.dart`: та же фикстура, правила, сопоставление свойств mpv, уровни буфера, тип источника по URI, контракт `FakePlayerEngine`, оверлей, подсказка, отчёт в одно нажатие.
- `pa_player/test/stats_libmpv_test.dart` (на сервере сборки с libmpv): `MediaKitEngine` проходит контракт для файла и http, на ссылке медленнее потока буфер доходит до уровня «потери».
- `app/test/playback_stats_test.dart`: «done when» — отчёт CORE-008 из плеера со статистикой в `extra/`; скриншоты — `docs/screenshots/progress/play-010/`.
- `pa_core/test/diagnostics_test.dart`: `attachments` через мост FRB.
