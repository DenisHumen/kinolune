# ADR-0126: Поиск в сети Windows-шар, Plex, Jellyfin и Emby — WS-Discovery, NetBIOS, GDM и UDP-автообнаружение в одном раунде с SSDP

- **Статус:** Предложен
- **Дата:** 2026-11-18
- **Решают:** владелец проекта (поручил решать по правилу «максимально просто для клиента»), мейнтейнер
- **Связано:** NET-010, NET-009, NET-018, NET-020, NET-012, NET-014, NET-015, UI-028, PKG-012; [ADR-0019](0019-lan-discovery-mdns.md), [ADR-0124](0124-dlna-strm-m3u-sources.md)

## Контекст и проблема

ROADMAP NET-010: «обнаружение Windows-шар (WS-Discovery, NetBIOS NS), Plex (UDP 32414), Jellyfin (UDP 7359); multicast на Apple — только после выдачи entitlement (PKG-012)». Done when: в LAN-тесте находятся шара Windows и сервер Jellyfin в Docker.

Сейчас «В этой сети» в «Добавить источник» показывает то, что объявляет себя по mDNS (NET-009: SMB, WebDAV, NFS у NAS и Mac), и DLNA-серверы по SSDP (NET-018). Компьютер с Windows по mDNS не объявляется, Jellyfin, Emby и Plex — тоже. Пользователь должен узнать IP и ввести его сам.

Всё, что приходит в ответ на такие запросы, присылает любое устройство в сети: ответы — недоверенные данные.

## Факторы решения

- Для пользователя: компьютер с общими папками и медиасервер появляются в списке сами, касание открывает уже заполненную форму; ничего не надо знать про протоколы.
- Тот же список и тот же цикл поиска, что у DLNA (ADR-0124), без нового экрана.
- Ответы недоверенные: ограниченные размеры, разбор без паник, адрес — только IP, который ответил; никакого автоматического входа с паролем.
- Без новых зависимостей и без GPL; Samba и wsdd — только в тестовом контейнере.
- Не шуметь в сети и не тормозить список.

## Рассмотренные варианты

1. **Свой крейт `pa-lan-probe` поверх UDP-сокетов (`socket2`, `if-addrs`, уже в lock-файле): WS-Discovery, NetBIOS NS, Plex GDM и Jellyfin/Emby в одном вызове, в приложении — в том же раунде, что SSDP.**
2. **Только NetBIOS** (как старые клиенты SMB) — не находит Windows 10/11 с выключенным NetBIOS over TCP/IP, а WS-Discovery — это то, чем пользуется сам «Проводник» → «Сеть».
3. **Готовые библиотеки** (wsdd-клиент, `nbtscan`) — GPL или нет на Rust; внешние утилиты на телефоне не запустить.

## Решение

Выбран вариант **1**.

### Протоколы (`pa-lan-probe`)

- **WS-Discovery** (`239.255.255.250:3702`): `Probe` с типом `wsdp:Device` (на `wsdp:Device pub:Computer` wsdd не отвечает); из ответов берутся только компьютеры (`pub:Computer`) — принтеры и сканеры отбрасываются. Ответ должен ссылаться на наш `MessageID` (`RelatesTo`). Если в `ProbeMatch` нет `XAddrs` (wsdd), отправляется `Resolve`. Имя и рабочая группа — из метаданных (WS-Transfer `Get` по HTTP на `XAddrs`, `pub:Computer` = `ИМЯ/Workgroup:ГРУППА`), но **только если NetBIOS не дал имени** (это самый медленный шаг).
- **NetBIOS NS** (UDP 137): широковещательный node status (`NBSTAT *`) и запрос главного обозревателя (`__MSBROWSE__`), плюс node status каждому хосту **маленькой сети** (префикс /24…/30, не больше 254 датаграмм по 50 байт): Windows не отвечает на широковещательный node status. Шара — хост с уникальным именем `0x20` (файловый сервер); групповое имя `0x00` — рабочая группа. Хост из WS-Discovery без NetBIOS-ответа и главный обозреватель получают node status вторым раундом (1 с).
- **Plex GDM:** `M-SEARCH * HTTP/1.1` на `239.0.0.250:32414` и широковещательный адрес; принимаются только ответы `Content-Type: plex/media-server` (не плееры), адрес — `http://<IP>:<Port>`.
- **Jellyfin и Emby:** `who is JellyfinServer?` и `who is EmbyServer?` широковещательно на UDP 7359, отдельными сокетами (так видно, кто ответил). Сервер, ответивший на оба вопроса, — Jellyfin.
- **Адрес всегда строится на IP, который ответил:** `smb://<IP>/`; у Jellyfin/Emby из поля `Address` берутся только схема и порт (за обратным прокси там может быть чужой хост); `XAddrs` WS-Discovery на другом хосте отбрасываются; `Get` метаданных идёт через `HttpClient` с политикой «домашняя сеть и интернет, не само устройство» (ADR-0124).
- **Границы для недоверенных ответов:** датаграмма больше 8 КиБ отбрасывается целиком (не читается обрезанной), не больше 512 ответов за раунд, XML — глубина до 32 и до 4096 элементов, не больше 16 совпадений в датаграмме и 32 запросов метаданных (по 64 КиБ, таймауты 1,5 с + 2 с), имена без управляющих символов и не длиннее 64 символов, id — до 64.
- Сокеты: по одному на каждый IPv4-интерфейс (кроме loopback, link-local и точка-точка — VPN), неблокирующие, буфер отправки 512 КиБ: датаграммы хостам, которые не ответили на ARP, ждут в буфере, и блокирующая отправка останавливала поиск на секунды (замер на сервере сборки: 9,7 с → 3,5 с).
- **Время:** `wait` (в приложении 2,5 с), плюс 1 с, если нужен второй раунд, плюс до 3,5 с, если у компьютера всё ещё нет NetBIOS-имени.
- **iOS/tvOS:** до multicast-entitlement (PKG-012) `SUPPORTED = false`, `discover` сразу возвращает пустой список. Android: ответы приходят unicast на наш сокет, multicast-lock не нужен (как у SSDP, ADR-0124).

### Приложение

- FRB `lan_search(wait_ms)` → `CoreLanService` (вид, имя, IP, адрес, рабочая группа). В Dart `coreNetworkSearch` запускает SSDP (DLNA) и `lan_search` одновременно, раз в 15 с, пока открыт список (`CoreSourceDiscovery`, NET-020): отказ одного поиска оставляет результаты другого. Одинаковые вид + адрес (Samba по mDNS и по WS-Discovery) показываются один раз — первым остаётся mDNS.
- **Windows-шара** — строка «ИМЯ» с подписью «Сетевая папка SMB (Windows, NAS) · IP» и в шаге 1 мастера SMB («Найдены в вашей сети»); касание — сразу шаг входа на этот IP (UI-028), дальше список общих папок как обычно.
- **Jellyfin / Emby** — касание открывает форму входа с подставленными адресом и именем; вход (пароль или Quick Connect) делает пользователь.
- **Plex** — строка видна, но неактивна и помечена «скоро»: вход в Plex — NET-012. Найденный адрес уже лежит в `DiscoveredSource.url`, форма NET-012 возьмёт его так же, как Jellyfin.
- **Ничего не подключается само:** найденное только заполняет форму; никакие пароли не отправляются на найденные адреса без нажатия пользователя.
- Новых строк ARB нет: подписи видов и «Скоро» уже были.

## Последствия

- Новый крейт `pa-lan-probe` (зависимости — `if-addrs`, `socket2`, `quick-xml`, `serde_json`, `url`, `pa-vfs-http`; новых в lock-файле нет), `pa_sources::lan_discover`, FRB `lan_search`; `HttpClient::post` с произвольным `Content-Type` (SOAP 1.2) в `pa-vfs-http`.
- Пример `cargo run -p pa-lan-probe --example lan_search` печатает найденное в сети машины разработчика.
- Тесты: юнит-тесты разбора (ответы wsdd, Samba NBSTAT и Jellyfin 10.10.7, записанные в LAN-тесте; принтеры, чужие `RelatesTo`, `XAddrs` на другом хосте, обрезанные и враждебные датаграммы, XML-бомбы), локальный UDP-обмен; **LAN-тест в Docker** (`core/crates/pa-lan-probe/tests/lan/run.sh`, opt-in feature `server-tests`, исключён из `cargo nextest` по умолчанию): контейнеры `pa-test-net010-smb-*` (Alpine, Samba + nmbd + **wsdd, лицензия MIT** — только в тестовом образе) и `pa-test-net010-jellyfin-*` (`jellyfin/jellyfin:10.10.7`) на мосту Docker: широковещательный поиск находит шару (имя и рабочая группа) и Jellyfin (адрес на его IP), отдельно — node status и цепочка WS-Discovery `Probe` → `Resolve` → `Get`. Контейнеры удаляются после теста.
- В сети сервера сборки пример нашёл настоящие компьютеры Windows и NAS с рабочей группой (имена в репозиторий не записаны).
- Не проверено: настоящий Plex Media Server (только юнит-тест формата GDM), Emby (формат ответа как у Jellyfin, по документации), Windows с выключенным NetBIOS (только WS-Discovery), Android на телефоне и Windows с брандмауэром (запрос «разрешить доступ к частным сетям» — подсказка UI-029 уже есть), macOS. Windows, на котором выключено «Сетевое обнаружение», не отвечает ни на что — его по-прежнему вводят вручную.
- Синхронизация источников не меняется: найденное — только подсказка для формы.
