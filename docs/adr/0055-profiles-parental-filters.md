# ADR-0055: Профили и родительский контроль в ядре — активный профиль соединения и один SQL-предикат для всех запросов

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта
- **Связано:** `LIB-012`, `LIB-001`, `LIB-009`, `LIB-010`, `LIB-011`, `SYNC-003`, `UI-004`; ADR-0013; `docs/dev/db.md`; исследование 01 §3 п.2 и п.6

## Контекст и проблема

Состояние пользователя (прогресс, избранное, коллекции, плейлисты, версии, настройки видов, умные полки, прослушивания) хранится по `profile_id` со схемы v1, но `pa-catalog` везде подставлял константу `PROFILE = 1`, а UI-004 держал имя и аватар «профиля» в Preferences приложения. LIB-012 требует настоящие профили с PIN и фильтры родительского контроля: белый список библиотек и папок, лимит рейтинга, «нет рейтинга — скрыто», скрытие арта. Критерий готовности: детский профиль не видит ни одного элемента вне белого списка ни через один API — поиск, «Продолжить», файлы.

API каталога много (списки, запросы LIB-009 со снимком в памяти, FTS-поиск, «Продолжить», избранное, коллекции, плейлисты, детали, версии, эпизоды, браузер файлов, воспроизведение частей, субтитры, прокси потоков), и их добавляют параллельно. Фильтр, который каждый API применяет по-своему, рано или поздно где-то забудут.

## Факторы решения

- Один источник истины для «видит ли профиль этот файл / это произведение», который нельзя обойти новым запросом по ошибке.
- Без смены сигнатур всех функций `pa-catalog` и FRB (`profile_id` в каждом вызове).
- Скрытое для профиля ведёт себя как несуществующее (`NotFound`), а не как «запрещено» — названия не утекают через ошибки.
- PIN нигде не хранится в открытом виде; проверка не может стать атакой на время (подменённые параметры хэша).
- Рейтинги разных стран и собственная оценка родителя.
- Без новых тяжёлых зависимостей; лицензии MIT/Apache.

## Рассмотренные варианты

1. **Активный профиль соединения во временной таблице `temp.active_profile` и SQL-фрагменты `file_visible!` / `work_allowed!` / `file_allowed!` (макросы `pa-library`), которые встраиваются в базовые запросы элементов.**
2. `profile_id` параметром во всех функциях `pa-catalog` и фильтр в Rust после выборки.
3. Материализованная таблица видимых файлов и произведений на профиль, пересчитываемая после скана и изменения настроек.

## Решение

Выбран вариант 1.

- **Активный профиль.** `pa_library::profiles::activate` копирует фильтры профиля в `temp.active_profile` (одна строка, своя у каждого соединения); `pa_library::open` активирует профиль с самым поздним `last_active_at_ms` (по умолчанию — `id = 1`). `Catalog::switch_profile(id, pin)` проверяет PIN, запоминает выбор и активирует профиль; прогресс, избранное, списки, настройки видов и полки читаются и пишутся для него (`progress::profile(conn)` вместо константы). Синхронизация и передача просмотра (SYNC-003) идут по `sync_id` активного профиля, поэтому «перехват» по-прежнему только внутри одного профиля.
- **Один предикат.** `file_visible!("f")` — файл в белом списке (`profile_folders`: источник целиком или папка со всеми подпапками, сравнение по префиксу пути с `/`, так что `/KidsExtra` не попадает в `/Kids`). `work_allowed!("w.id")` — возраст произведения не выше лимита, а без рейтинга — только если политика это разрешает. `file_allowed!("f")` для файлов, к которым обращаются напрямую (браузер, воспроизведение, субтитры, прокси): файл в белом списке, его произведение разрешено, нераспознанное видео считается без рейтинга (музыка — нет). Фрагменты встроены в базовые запросы фильмов, сериалов, эпизодов и треков (`items.rs`), в снимок запросов LIB-009, версии, браузер, части, субтитры; поиск, «Продолжить», избранное, коллекции и плейлисты получают элементы через эти же запросы. API, принимающие id элемента (детали, версии, жанры, эпизоды, прогресс, точка продолжения, добавление в списки), сначала проверяют видимость и отвечают `NotFound`. Прокси потоков (`SourceOpener::open_file`) спрашивает `Catalog::may_open`. Без строки в `temp.active_profile` предикаты скрывают всё (fail closed).
- **Рейтинги.** `work_certifications(work_id, provider, country, certification, min_age)`; прогон метаданных пишет рейтинги TMDB (`release_dates` фильма — театральный релиз, иначе первый с рейтингом; `content_ratings` сериала), родитель может задать свой (`provider = 'user'`). `certification_age` переводит рейтинг в минимальный возраст (MPA и TV Parental Guidelines, BBFC, AU, CA, JP, KR, BR, NL, «чистые» возрасты `16`, `16+`, `FSK 16`, `-16`); непонятный рейтинг (`NR`) — `NULL`, то есть «без рейтинга». Возраст произведения для профиля: оценка родителя, иначе рейтинг страны профиля, иначе самый строгий из известных.
- **PIN.** 4–8 цифр, Argon2id (крейт `argon2` 0.6, RustCrypto, MIT/Apache, без `password-hash`), соль 16 байт из `getrandom`, 19 МиБ / 2 прохода / 1 поток (минимум OWASP), формат `argon2id$v=19$m=…,t=…,p=…$<соль hex>$<хэш hex>` — параметры в строке, их можно поднять позже. При проверке параметры из строки ограничены сверху (256 МиБ, 16 проходов), сравнение — без раннего выхода.
- **Скрытие арта.** При `hide_artwork` элементы и детали приходят без постеров, фонов, кадров и логотипов (и локальных картинок у файлов).
- **Список источников** для профиля с белым списком — только источники, в которых есть его папки; наблюдатель изменений и сканер видят все.
- **Приложение.** `RustLibrary` реализует `LibraryProfiles`; профиль UI-004 из Preferences один раз переносится в профиль по умолчанию (если у него ещё нет имени) и удаляется из Preferences; имя и аватар дальше живут в ядре.

### Последствия

- Хорошо: новый запрос элементов, построенный на базовых `MOVIE_SQL`/`SHOW_SQL`/`EPISODE_SQL`/`TRACK_SQL`, фильтруется сам; тест `pa-catalog/tests/profiles.rs` проходит по всем публичным API.
- Хорошо: сигнатуры `Catalog` и FRB не поменялись; профиль — состояние библиотеки, как и было задумано схемой v1.
- Плохо: состояние в соединении. Второе соединение к той же базе (сканер, `pa-sources`) активирует последний профиль само; запросы элементов там не выполняются, но новый код, читающий элементы через отдельное соединение, должен сам вызвать `activate`.
- Плохо: смена профиля меняет `total_changes()`, и снимок запросов LIB-009 перестраивается (десятки миллисекунд на большой медиатеке) — приемлемо для редкого действия.
- Плохо: коррелированные подзапросы на каждую строку файла. Для профиля без ограничений `CASE` отвечает сразу; у ограниченного — поиск по первичным ключам `profile_folders` и `work_certifications`.
- Ограничение: управлять профилями (создавать, менять фильтры) API ядра разрешает из любого профиля. Защита — PIN родителя в приложении перед экраном настроек профилей (экрана пока нет).
- Ограничение: число попыток PIN не ограничено в ядре; задержку после неверных попыток делает UI.
- Twitch, музыкальные рейтинги и рейтинги AniList/Shikimori фильтрами не покрыты; музыка подчиняется только белому списку папок.

### Как проверяем соблюдение

`cargo test -p pa-library` (`tests/profiles.rs`: CRUD, PIN, предикаты, страна и самый строгий рейтинг, активный профиль после открытия, fail closed; юнит-тесты `certification_age` и формата хэша; `tests/schema.rs` — новые таблицы, каскады, индексы FK). `cargo test -p pa-catalog --test profiles`: изоляция состояния профилей, детский профиль через все API (списки, запросы, алфавит, полки, поиск, «Продолжить», избранное, коллекции, плейлисты, детали, версии, эпизоды, прогресс, браузер, части, прокси), PIN при выходе, рейтинг родителя и политика «без рейтинга». `dart test test/profiles_test.dart` (`pa_library`), `flutter test test/profile_migration_rust_test.dart` (перенос профиля UI-004).

## Плюсы и минусы вариантов

### Вариант 2 — `profile_id` параметром и фильтр в Rust

- Плюсы: нет состояния в соединении.
- Минусы: десятки сигнатур и вызовов FRB; фильтр после выборки ломает пагинацию и счётчики LIB-009 и легко забывается в новом API.

### Вариант 3 — материализованная видимость

- Плюсы: самые быстрые запросы.
- Минусы: пересчёт после каждого скана, матча, прогона метаданных и изменения настроек; рассинхронизация = утечка; лишняя таблица размером с медиатеку на каждый профиль.
