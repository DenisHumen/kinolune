# ADR-0087: Встраивать anime-offline-database в приложение и обновлять её раз в сутки из релизов GitHub

- **Статус:** Предложен
- **Дата:** 2026-11-15
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** META-030 (эта задача, решение владельца 2026-11-15: «встраивай»), META-008, META-014, META-015, META-029; [ADR-0084](0084-scorer-pair-features-joint-group.md), [ADR-0085](0085-episode-numbering-module.md); `docs/legal/anime-mappings.md`; `docs/legal/privacy-policy.md` §4

## Контекст и проблема

Скорер (ADR-0084) и нумерация эпизодов (ADR-0085) опираются на anime-offline-database (AOD): названия и синонимы записей AniDB, их тип и число эпизодов. В приложении базы не было: `pa-catalog` распознавал аниме только поиском TMDB/AniList, поэтому работа, которую TMDB не знает под её названием (сезон как отдельный тайтл: `Bleach - Sennen Kessen-hen`, `Kimetsu no Yaiba - Mugen Ressha-hen`), уходила в ручную очередь. META-008 уже дал крейт `pa-anime-mappings` с `Updater` и производной ODbL-базой (`tools/anime-mappings/build.sh`), но ни в бандл, ни в путь приложения она не попадала. Владелец решил: базу встраивать, раз в сутки обновлять с GitHub, повреждённая или подменённая загрузка не должна заменять рабочую.

## Факторы решения

- Лицензия: AOD — ODbL-1.0 + DbCL-1.0, встраивание разрешено с атрибуцией и share-alike для базы (`docs/legal/anime-mappings.md` §2). Anime-Lists и Fribb — без лицензии: не встраивать и не зеркалить (§3–4).
- Upstream: `manami-project/anime-offline-database` архивирован 2026-07-04 (последний релиз `2026-27`); продолжение с той же лицензией — `cedya77/anime-offline-database`, еженедельные релизы `<год>-<неделя>` (на 2026-11-15 — `2026-46`). GitHub публикует SHA-256 каждого ассета (`digest`).
- Размер (замер 2026-11-15, релиз `2026-45`, 38 418 записей): upstream JSONL — 61,2 МБ, его `.zst` — 6,0 МБ; производная база — 14,7 МБ, `gzip -9` — 4,3 МБ, `zstd -19` — **3,0 МБ**.
- Своих серверов нет (ADR-0004): обновление — прямой запрос с устройства к GitHub, без идентификаторов, с выключателем.
- Ядро sans-IO для сети, тесты офлайн; тихие ошибки распознавания не должны расти.

## Рассмотренные варианты

1. Встроить производную базу в ассеты (zstd), обновлять раз в сутки из релизов upstream через GitHub API (выбран).
2. Не встраивать: скачивать базу при первом запуске.
3. Встроить несжатую базу (или исходный upstream JSONL).
4. Обновлять скачиванием `releases/download/latest/…jsonl` по ETag каждый день (как `Updater::refresh` для списков).

## Решение

Выбран вариант **1**: база работает с первого запуска без сети, а цена — 3 МБ на APK/AppImage — разумна (приложение уже везёт libmpv и FFmpeg на десятки мегабайт). Вариант 2 оставлял бы распознавание аниме без базы до первого выхода в сеть и противоречит «встраивай»; вариант 3 добавлял бы 15–61 МБ; вариант 4 тянул бы 6–60 МБ при каждой смене ETag и не даёт контрольной суммы.

**Бандл.** `tools/anime-mappings/build.sh` (META-008) скачивает закреплённый релиз (`upstream.env`, SHA-256), собирает производную базу `anime-offline-ids.jsonl` и теперь ещё `anime-offline-ids.jsonl.zst` (`zstd -19`). Шаг «Bundled anime database» в `release-app.yml` (Linux и Android) кладёт `.zst` и `LICENSE.anime-offline-database` в `clients/flutter/app/assets/anime-db/` (в git их нет). Приложение один раз на сборку копирует ассет в каталог поддержки (`anime_db_asset.dart`: сравнение по содержимому, запись через временный файл) и передаёт путь ядру. Сборка без файла (разработка) работает: база появится с первым обновлением.

**Обновление** (`pa_anime_mappings::release`, `Updater::refresh_offline_db`):

1. Не чаще раза в сутки (`checks` в `manifest.json`; ответ GitHub, в том числе ошибка или отказ, засчитывается — плохой релиз не качается на каждом старте; сбой сети — нет) запрос `api.github.com/repos/cedya77/anime-offline-database/releases/latest`.
2. Релиз не черновик, тег вида `YYYY-WW`, ассет `anime-offline-database.jsonl.zst` с URL ровно `https://github.com/cedya77/anime-offline-database/releases/download/<тег>/…` (подменённый ответ API не уведёт устройство на другой хост), размер ≤ 64 МБ, `digest` — `sha256:<64 hex>`.
3. Тег не новее встроенного и установленного — ничего не качается (`NotModified`).
4. Загрузка проверяется: длина = размер из релиза, SHA-256 = `digest` (если GitHub его не дал — остаются проверки формата), zstd с пределом 256 МБ, upstream JSONL с лицензией ODbL и репозиторием `anime-offline-database`, не меньше 20 000 записей и не меньше половины установленной базы.
5. Только после этого на устройстве строится производная база (тот же формат и заголовок, что в бандле), сжимается zstd (быстрый уровень, ~4 МБ), пишется под новым именем `anime-offline-ids.<sha16>.jsonl.zst`, `manifest.json` подменяется одним `rename`, старый файл удаляется. Чтение (`AnimeDb::load`) проверяет SHA-256 файла; повреждённое обновление не читается — берётся встроенная база, а тот же релиз при следующей проверке скачивается заново.

Распаковка — чистый Rust (`ruzstd`, MIT): без C-зависимостей для Android и Apple.

**Anime-Lists.** Решение META-008 не меняется: лицензии нет (issue #613 без ответа), поэтому список **не встраивается**, а скачивается устройством с upstream не чаще раза в сутки (`AnimeLists`, ETag, SHA-256, атомарная замена — то же, что выше). Новое: его обновление подчиняется тому же переключателю, что и AOD. Fribb не используется (кросс-ID строится из AOD и Anime-Lists на устройстве).

**Путь приложения** (`pa-catalog`):

- `AnimeDb` выбирает базу: установленное обновление, если файл цел и его тег не старше встроенного, иначе встроенную. `AnimeTitles` — индекс названий AOD (`TitleIndex` из `pa_recognition::title::anime`), в `pa-frb` кэшируется по (источник, тег) между прогонами метаданных.
- `metadata::local_anime`: аниме-работа без решения пользователя и без NFO ищется в локальном индексе; запись берётся, если её оценка ≥ 0.92 и никакая другая запись не ближе 0.03; ничью ТВ-сериала и одноимённого фильма (`Mugen Ressha-hen`) решает медиана длительности файлов (> 60 мин — фильм), без длительностей — не решается. Найденная запись даёт AniDB, AniList и MAL id, а со списком Anime-Lists — сериал TMDB.
- Если поиск TMDB ничего не нашёл, работа получает сериал TMDB своей записи AniDB (уверенность — оценка локального индекса); если нашёл — решение поиска не меняется (иначе `Bleach - 388` получил бы серию первой записи — тихая ошибка). AniList читается по id записи вместо поиска.
- Нумерация (`numbering::series_with`): записи серии берут число эпизодов и синонимы из AOD (выведенные из TMDB размеры заполняют только неизвестное); запись, найденная локально, — подсказка для сквозного счёта, если ни одно название работы не называет запись серии.
- Пороги и веса скорера не менялись. Миграций нет.

**Настройки и атрибуция.** «Настройки → Метаданные»: «Обновлять базу аниме» (включено по умолчанию; `metadata_anime_data_updates`), строка состояния (встроенная/обновлена, выпуск и дата, число тайтлов, время проверки), «Проверить сейчас». ODbL-атрибуция — в «О программе → Данные и товарные знаки», на странице лицензий и в `THIRD-PARTY-NOTICES.md`; запрос к GitHub — строка в политике конфиденциальности. Ежедневная проверка запускается при старте приложения и перед прогоном метаданных; отдельного планировщика нет: ядро само держит интервал в сутки (если PKG-018 даст общий планировщик проверок GitHub, вызов можно перенести туда).

### Последствия

- Хорошо — замер путём медиатеки (`pa-eval run --recognizer tmdb --anime <бандл .zst>`, синтетический TMDB и синтетический список Anime-Lists META-015, порог 0.92; отчёты `tools/recognition-eval/baselines/v0/meta030-library-*.md`): на train + dev ошибок A2 140 → 120 (−14 %), A3 23 → 13 (−43 %), A16 53 → 32 (−40 %), A4 235 → 229, всего 722 → 683; тихих 44 → 44. Test: A2 1 → 0, A16 1 → 0, остальное без изменений, тихих 3 → 3. Точность эпизода в схеме TMDB осталась 100 % на A1–A4 и A16; доля автоматически решённых в A2 выросла (полнота TMDB 98,7 %).
- Хорошо: аниме-работа распознаётся по ромадзи, английскому и русскому названию без запроса; AniList — без поиска.
- Плохо (цена решения): +3,0 МБ на каждый APK и AppImage (оценка по размеру ассета; zstd не сжимается повторно; реальный APK не собирался). Индекс AOD строится при первом прогоне метаданных за сессию (на сервере сборки ~2 с вместе с прогоном корпуса; на телефоне не мерили) и держит в памяти ~40 тыс. записей. Раз в неделю устройство качает ~6 МБ.
- Плохо: без списка Anime-Lists (выключено обновление, офлайн до первой загрузки) AOD не даёт TMDB id, и путь медиатеки не меняется (замер без списка: 0 изменений). Точность AniDB-схемы в медиатеке по-прежнему не меряется (медиатека не выдаёт номер AniDB).
- Плохо: на A2 точность схемы TVDB absolute среди авто снизилась 65,4 → 64,4 % (больше файлов уходит в авто с верной работой и верным TMDB-номером, но абсолютный номер синтетического списка не совпадает). Ошибкой это не считается (верна любая размеченная схема).
- Честно о замере: список Anime-Lists синтетический (правила мейнтейнера, ADR-0085), поэтому числа — точность *при верных маппингах*; TMDB — синтетический поиск. Test прогонялся дважды: до и после правила длительности (правило выведено из ошибок train + dev). Настоящий TMDB/Anime-Lists офлайн не измерить (ключей и данных в репозитории нет).
- Нейтрально: при подъёме закреплённого релиза в `upstream.env` встроенная база обновляется с выпуском приложения; устройство с более новым обновлением его и оставит.

### Как проверяем соблюдение

`pa-anime-mappings/tests/update.rs` (`offline_db_releases`): новый релиз ставится атомарно и остаётся один файл; тот же тег — только запрос к API; в течение суток — ни одного запроса; **подменённый ассет, неверный `digest`, обрезанная загрузка, повреждённый zstd, не-zstd, сменившаяся лицензия, слишком мало записей — рабочий файл байт в байт тот же**; ответ API с чужим URL отклоняется без загрузки; лимит GitHub засчитывается как проверка, сбой сети — нет; повреждённый установленный файл не читается и качается заново. `release.rs` — разбор тегов и ответа API. `pa-catalog/tests/numbering.rs` — работа, которую TMDB не знает, находится локальной базой и попадает в S02E05; ничья ТВ/фильм решается длительностью. Flutter: `test/anime_db_test.dart` (строка состояния, копирование ассета, переключатель по умолчанию включён и сохраняется). `baselines.sh` пересчитывает `meta030-library-*.md`.

## Плюсы и минусы вариантов

### Вариант 2 (загрузка при первом запуске)

- Плюс: APK меньше на 3 МБ.
- Минус: первый скан без сети распознаёт аниме хуже; первый запуск зависит от GitHub; решение владельца — встраивать.

### Вариант 4 (ETag на `latest/download`)

- Плюс: уже есть в `Updater::refresh`.
- Минус: нет контрольной суммы из релиза; 6–60 МБ при каждой смене ETag вместо раза в неделю; нет защиты от редиректа на чужой хост на уровне метаданных релиза.
