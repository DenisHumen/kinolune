# ADR-0165: `alpha-admin` — бэкенд админки NAS-ОС: демон без root, polkit, PAM-помощник, только LAN

- **Статус:** Предложен
- **Дата:** 2026-11-25
- **Решают:** мейнтейнер (владелец делегировал решения)
- **Связано:** DIST-013, DIST-014, DIST-015, DIST-018, DIST-009, DIST-005, SRV-003, SRV-004; [ADR-0010](0010-nas-os-phase0.md); [исследование 05](../research/05-nas-linux-distro.md) §5.1–5.2

## Контекст и проблема

Исследование 05 §5.1 выбрало свой бэкенд `alpha-admin` на Go поверх системных D-Bus API вместо Cockpit. Бэкенд должен входить пользователями ОС, менять систему (сервисы, сеть, firewall, диски, питание) и проксировать агент обновлений. Это самый опасный сервис в образе: он принимает пароли из сети и может перезагрузить машину. Нужно было решить: от чьего имени он работает и как получает права; как проверять пароли; как устроены сессии; кто его видит в сети; какой TLS.

## Рассмотренные варианты

**Права.**

1. Демон от root.
2. Демон от системного пользователя `alpha-admin`; изменения — вызовами D-Bus, которые разрешает polkit-правило только этому пользователю и только нужные действия.
3. Демон без прав + собственный привилегированный «исполнитель» по unix-сокету.

**Проверка паролей.**

1. PAM прямо в демоне (нужен root или setuid `unix_chkpwd`, который проверяет только пароль *вызывающего*).
2. Чтение `/etc/shadow` и проверка yescrypt на Go (нужен root; своей реализации yescrypt в стандартной библиотеке нет; обходит PAM — faillock, блокировки, срок действия).
3. Маленький помощник от root, запускаемый systemd на каждое подключение (`Accept=yes`) к сокету, доступному только демону; внутри — PAM `auth` + `account`.

**Сессии.** JWT/PASETO без состояния; непрозрачный токен в памяти.

**Сеть.** Слушать всё; только LAN (как медиасервер); только loopback + обратный прокси.

## Решение

- **Права — вариант 2.** Демон работает от `alpha-admin` (sysusers), с песочницей systemd. polkit-правило `50-alpha-admin.rules` разрешает этому пользователю: `manage-units` только с `verb=restart` и только для списка наших сервисов; `network-control` и `enable-disable-wifi`; firewalld `info`/`config`; UDisks2 `filesystem-mount*`/`unmount-others`; logind `reboot*`/`power-off*`. Людям правило ничего не даёт. Что человек — администратор, демон проверяет при входе и на каждом запросе до вызова D-Bus. Вариант 3 повторял бы polkit своими руками; вариант 1 отдаёт root веб-серверу.
- **Пароли — вариант 3.** `alpha-admin-auth@.service` (root, `PrivateNetwork`, `ProtectSystem=strict`, ограниченные capabilities) обслуживает одно подключение и завершается; сокет `0600 alpha-admin`, плюс сверка `SO_PEERCRED`. PAM-сервис `alpha-admin` включает `password-auth` и `account`, так что yescrypt, faillock, блокировка учётной записи и срок действия пароля работают как при входе в консоль. Помощник отвечает только «да + uid + группы» или «нет», без причины. root и UID < 1000 не входят. Помощник — единственный cgo-бинарник; демон собирается статически.
- **Только администраторы** (решение мейнтейнера, 2026-11-25): входят только члены `wheel` или `alpha-admin` (05 §5.2). Остальные с верным паролем получают `403 not_admin` «Нет прав администратора», сессия не создаётся, блокировка не растёт. Роли «только чтение» и «член семьи» нет; поле `role` в API оставлено (всегда `admin`), чтобы будущая роль не меняла формат. Пользователи и группы — ОС, их создаёт установщик (DIST-005) и позже админка.
- **Сессии:** непрозрачный 256-битный токен в cookie `__Host-…; Secure; HttpOnly; SameSite=Strict`, в памяти — только его SHA-256; 30 минут простоя, максимум 12 часов. CSRF-токен на сессию в заголовке плюс проверка `Origin`. Перезапуск демона завершает сессии — для админки это приемлемо и не оставляет секретов на диске. Токены для клиентского приложения (долгоживущие, с отзывом) — вместе с SRV-003, когда приложение начнёт ходить в админку.
- **Перебор:** блокируется пара «учётная запись + адрес» (5 ошибок → 5 мин, удвоение до часа) и адрес целиком (20 ошибок → 15 мин), плюс 10 попыток в минуту с адреса. Блокировка всей учётной записи по сети не делается: иначе любое устройство в LAN запрёт владельца. PAM добавляет свою задержку (`pam_faildelay`).
- **Сеть: только LAN**, те же диапазоны, что у медиасервера (`pa-vfs-http` Zone: loopback, RFC 1918, 100.64/10, ULA, site-local) плюс link-local. Фильтр в двух местах: в демоне (соединение закрывается до TLS) и в юните (`IPAddressAllow=`). Публичный доступ — только явным drop-in и флагом. `:80` только перенаправляет на HTTPS и отвечает `/health`.
- **TLS:** самоподписанный ECDSA P-256 на 10 лет, создаётся при первом запуске в `/var/lib/alpha/admin` и не меняется при обновлениях; отпечаток в `/api/v1/info` для пиннинга в приложении (TOFU, как SRV-004). Let's Encrypt/Tailscale cert — позже (05 §5.2).
- **Опасные действия** (перезагрузка, выключение) — в два шага с одноразовым токеном и показом ингибиторов logind.
- **Обновления:** не реализуются заново — фиксированная таблица маршрутов `/api/v1/system/update…` проксируется на сокет `alpha-updated` (DIST-009); произвольные пути не пробрасываются.
- **Зависимости:** `godbus/dbus/v5` (BSD-2), `msteinert/pam/v2` (BSD-2), `golang.org/x/sys` (BSD-3). Тесты D-Bus — на приватном `dbus-daemon` с фейковыми сервисами, без моков на уровне Go-интерфейсов.

## Последствия

- Компрометация веб-демона даёт атакующему ровно то, что разрешено в polkit-правиле, а не root; пароли и `/etc/shadow` ему недоступны.
- Новое действие в админке = новая строка в polkit-правиле и тест; это осознанное трение.
- Журнал (`journalctl`) читается через группу `systemd-journal` и ограничен списком наших сервисов.
- Сессии не переживают перезапуск демона и обновление ОС.
- Сборка образа скачивает модули Go через module proxy (проверка по `go.sum`); для офлайн-сборки понадобится `go mod vendor` или зеркало.
- SELinux: бинарники работают как `unconfined_service_t`; собственная политика — отдельная задача, если понадобится.

## Решения мейнтейнера

- Админка только для администраторов, роли `viewer` нет (2026-11-25).
- Отдельной роли «член семьи» пока нет (2026-11-25).
