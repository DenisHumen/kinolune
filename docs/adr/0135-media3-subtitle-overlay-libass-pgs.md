# ADR-0135: Субтитры плеера Media3 — ASS рисует libass из нашего `libmpv.so` по кадрам видео, PGS и остальное — Media3

- **Статус:** Предложен
- **Дата:** 2026-11-18
- **Решают:** владелец проекта (поручил решать по правилу «максимально просто для клиента»), мейнтейнер
- **Связано:** PLAY-AND-006, PLAY-AND-002, PLAY-AND-003, PLAY-006, PLAY-007, PLAY-AND-007; `docs/research/02` §2.6; [ADR-0008](0008-android-player-embedding.md), [ADR-0042](0042-subtitle-style-and-sidecars.md), [ADR-0056](0056-subtitles-rendered-by-libmpv.md), [ADR-0127](0127-media3-datasource-core-bytesource.md)

## Контекст и проблема

ROADMAP PLAY-AND-006: «RGBA-оверлей из PLAY-006 поверх SurfaceView с синхронизацией по времени плеера; PGS — через Media3 или наш рендер». Done when: ASS с караоке синхронизирован с точностью ±1 кадр на тестовом сэмпле.

Что есть. Плеер Media3 (`pa_player_android`, PLAY-AND-002) рисует видео в `SurfaceView` (ADR-0008) и до этой задачи **не показывал субтитры вовсе**: Flutter-OSD их не рисует, а `SubtitleView` есть только в запасном варианте с `PlayerView`. Media3 разбирает субтитры во время извлечения в свои cues: SRT, WebVTT, TTML, PGS, VobSub, DVB — хорошо, а SSA/ASS — только текст с базовыми стилями (нет караоке, поворотов, рисунков `\p`, шрифтов из MKV). PLAY-006 (ADR-0056) решил ASS/PGS/VobSub на пути media_kit силами libmpv и **не сделал** рендерер в ядре: «рендерер в ядре понадобится нативным движкам без mpv — это PLAY-AND-006». Значит, «RGBA-оверлея из PLAY-006» нет, его нужно сделать здесь.

Ограничения: FFmpeg и всё в клиентах — только LGPL/пермиссивное; нативные библиотеки — как можно меньше; плагин в приложение ещё не подключён (экран 0.1 — media_kit), но должен быть готов.

## Факторы решения

- Для пользователя: аниме-ASS выглядит как в mpv (караоке, надписи, шрифты из файла), Blu-ray PGS виден, обычные SRT — в системном стиле субтитров Android; ничего не надо настраивать.
- Караоке — с картинкой (±1 кадр), а не с часами звука.
- Размер APK: не добавлять вторую копию libass + FreeType + HarfBuzz + FriBidi (≈2 МБ на ABI).
- Без NDK в Gradle-сборке плагина и приложения (сейчас её там нет).
- Проверяемость на эмуляторе в CI-подобном прогоне.

## Рассмотренные варианты

1. **Рендерер в Rust-ядре** (libass + декодеры FFmpeg → RGBA через UniFFI). Ядро не линкует ни libass, ни FFmpeg; пришлось бы добавить их в `libpa_ffi.so`/`libpa_frb.so` на всех платформах — +2–3 МБ на ABI и новая сборочная цепочка, ради того, что пока нужно только Android.
2. **Свой JNI-модуль** со статическими libass/FreeType/HarfBuzz/FriBidi (CMake в плагине). Работает, но +≈2 МБ на ABI (≈6 МБ в универсальном APK) — копия того, что уже лежит в `libmpv.so`, — и NDK в каждой сборке приложения.
3. **libass из нашего `libmpv.so` через JNA.** В Android-сборке tools/mpv libass линкуется статически и его API `ass_*` экспортируется из `libmpv.so` (проверено `llvm-nm -D`: `ass_library_init`, `ass_render_frame`, `ass_process_chunk`…). `libmpv.so` лежит в каждом APK (media_kit сейчас, запасной движок PLAY-AND-007 потом), JNA уже есть (рантайм UniFFI). Кода на C нет, 0 байт к APK.
4. Оставить SSA парсеру Media3 — без караоке, рисунков и шрифтов; не выполняет задачу.

PGS: свой декодер не нужен — `PgsParser` Media3 даёт картинки с позицией и временем, `SubtitleView` их рисует; так же VobSub и DVB.

## Решение

Выбран вариант **3** для ASS и Media3 для всего остального.

### Как идёт ASS

- **Извлечение.** `DefaultMediaSourceFactory` получает фабрику парсеров `AssRenderer.parserFactory()`: все форматы — парсерам Media3, кроме SSA. Встроенная дорожка MKV (в `initializationData` есть заголовок) отклоняется и остаётся «сырой» (`text/x-ssa`, сэмплы Matroska с временем блока). Внешний `.ass` (без заголовка) получает парсер без cues: у Media3 остаётся обычная дорожка, которую можно выбрать и в которой можно перематывать (необработанная внешняя дорожка ломает перемотку: `MergingMediaPeriod` падает — найдено тестом), а сам файл движок читает тем же `DataSource` (`CoreDataSource`, ADR-0127) и отдаёт libass целиком (`ass_read_memory`).
- **`AssRenderer`** — текстовый рендерер Media3, стоит перед `TextRenderer` (при равной поддержке дорожку получает первый). Он ничего не рисует: читает сэмплы, переводит время в медиавремя и кладёт события в libass (`ass_process_chunk`, дубликаты по ReadOrder libass отбрасывает сам, поэтому после перемотки ничего не сбрасывается). Включение/выключение дорожки = старт/стоп трека libass.
- **`AssOverlayView`** (в `SubtitleOverlay` над `SurfaceView`): `VideoFrameMetadataListener` Media3 сообщает о каждом кадре, который вот-вот покажут (время кадра и время показа). Для этого времени на своём потоке рендерится картинка libass (`ass_render_frame` → смешивание `ASS_Image` в премультиплицированный ARGB в рамке, которая её содержит) и ставится в очередь с временем показа кадра. На каждом vsync поднимается последняя картинка, чей кадр будет на экране к моменту показа этого кадра UI: время показа — из frame timeline (`Choreographer.postVsyncCallback`, API 33+), иначе vsync + 2 периода. Так надпись меняется вместе с кадром, а не с часами звука. На паузе, при смене дорожки и при позднем приходе событий картинка перерисовывается для последнего кадра.
- Размер кадра libass = размер оверлея в пикселях (чёткий текст), storage size = размер видео (масштаб `ScaledBorderAndShadow`, `PlayRes`).
- **Шрифты.** Как в ADR-0056: Roboto, Noto Sans CJK, Noto Naskh Arabic, Noto Sans Hebrew, Noto Sans Thai из `/system/fonts` (что есть на устройстве) и запасное семейство по языку дорожки. Отличие: файлы добавляются в libass как шрифты в памяти один раз (`ass_add_font`), а не каталогом — каталог libass перечитывает при каждом `ass_set_fonts`. **Шрифты из вложений MKV** Media3 не отдаёт, поэтому `MkvAttachments` (минимальный разбор EBML: верхний уровень сегмента до первого кластера и `Attachments` оттуда или через `SeekHead`) читает только шрифты, до 64 МиБ, на фоновом потоке, когда у файла есть ASS-дорожка.
- **Без `libmpv.so`** (сборка без него, загрузка не удалась): `AssRenderer` не ставится, SSA уходит парсеру Media3 и рисуется `SubtitleView` как текст — плеер работает, только проще.

### Остальное

- **PGS, VobSub, DVB, SRT, WebVTT, TTML** — cues Media3 в `SubtitleView` оверлея, стиль — системный стиль субтитров (`setUserDefaultStyle`, `setUserDefaultTextSize`), как «системный стиль по умолчанию» PLAY-007. Перенос пользовательского стиля из настроек Flutter-приложения — вместе с подключением плагина к приложению.
- **HDR.** Оверлей — обычный SDR-слой окна: поверх HDR-видео Android композитит его в яркости интерфейса, отдельная настройка (как `sub-hdr-peak` в mpv) не нужна.
- **`VideoLayout`**: `SurfaceView` и оверлей внутри `AspectRatioFrameLayout` по пропорциям видео. Раньше `PlayerActivity` растягивала видео на весь экран (MediaCodec по умолчанию масштабирует под поверхность), и субтитры, размещённые относительно кадра, разъехались бы с ним. В варианте с `PlayerView` оверлей ASS кладётся в его `exo_content_frame`, а cues рисует его собственный `SubtitleView`.

### Размер и память

- APK: +0 байт нативного кода (libass уже в `libmpv.so`); Kotlin ≈ 1,3 тыс. строк; зависимость `media3-ui` у библиотеки движка (у плагина она уже была).
- Процесс: `libmpv.so` (≈8 МБ на x86_64) и библиотеки FFmpeg подгружаются при создании движка Media3 (отображение файлов, резидентно — только используемые страницы). Пока играет ASS, libass держит системные шрифты в памяти (≈20–25 МБ с Noto CJK, как в ADR-0056) и шрифты из MKV.
- Каждая изменившаяся картинка — новый `Bitmap` размером с текст (обычно 0,2–1 МБ); при караоке на 24–30 к/с это ~25 картинок в секунду, их собирает GC. Если на слабых устройствах это даст пропуски кадров (PLAY-103 в каталоге проверок), следующий шаг — пул из 2–3 битмапов.

### Связь с tools/mpv

`libmpv.so` для Android линкуется без `--exclude-libs` (на Linux оно есть, ADR-0056), поэтому `ass_*` видны. Если когда-нибудь скрыть символы и на Android, движок молча перейдёт на запасной путь (ASS текстом); это ловит instrumented-тест `AssSubtitlesTest.libassComesFromLibmpv` (тестовый APK собирается с `libmpv.so` из tools/mpv). Отдельную проверку в `tools/mpv/bundle.sh` не добавляли: правка рецепта меняет ключ готовых сборок CI-008 и пересобирает libmpv для всех целей.

## Проверка

- JUnit (`clients/android/player/src/test`): сэмплы Matroska SSA → события libass, смешивание картинок, выбор картинки к vsync, вложения MKV (до кластеров, через SeekHead, нет — когда после кластеров без SeekHead), запасные семейства, какие дорожки идут в libass.
- Instrumented на эмуляторе Android 14 x86_64 (тестовые медиа — `tools/make-fixtures.sh`, не коммитятся):
  - `SubtitleSyncTest` — «done when»: `karaoke.mkv` показывает номер кадра двоичным кодом, ASS поёт по квадрату на кадр (`\k4` при 25 к/с). Скриншоты дисплея (SurfaceFlinger: видео и оверлей как их видит зритель) дают одновременно кадр N и позицию караоке K. На паузе K = N; во время воспроизведения в трёх прогонах по 125–156 скриншотов K − N = 0 во всех, кроме одного (−1). С временем показа «vsync + 1 период» было бы −1 в трети скриншотов — отсюда «+2 периода» для API < 33.
  - `AssSubtitlesTest` — libass через JNA из `libmpv.so`, слоги караоке по кадрам, надпись с поворотом, шрифт DejaVu Sans из вложения MKV.
  - `SubtitleTracksTest` — PGS: картинки событий в своё время и снятие между ними; внешний `.ass` через libass, выключение дорожки убирает картинку.
  - Прежние тесты движка (контракт ядра, H.264/HEVC, `CoreDataSource`) проходят с новым рендерером и фабрикой парсеров.
- Временное приложение с плагином на эмуляторе: Flutter-OSD и вариант с `PlayerView` — скриншоты в `docs/screenshots/progress/PLAY-AND-006/`.

**Не проверено:** реальные устройства (Shield, Chromecast GTV, телефон), HDR-панель, 24p/60p с AFR, нагрузка на слабом процессоре, большие аниме-файлы с сотнями событий и десятками шрифтов, путь API < 33 на устройстве. Это строки PLAY-102…PLAY-106 каталога проверок.

## Последствия

- Хорошо: ASS со всеми эффектами и шрифтами из файла и PGS видны в плеере Media3; караоке совпадает с кадром на эмуляторе; размер APK не вырос.
- Хорошо: в `PlayerActivity` видео больше не растягивается.
- Плохо: Media3-движок зависит от того, что `libmpv.so` экспортирует libass (есть запасной путь и тест).
- Плохо: шрифты и картинки ASS живут в памяти процесса (см. «Размер и память»).
- Нейтрально: стиль пользователя из настроек приложения к текстовым субтитрам Media3 пока не применяется (системный стиль) — до подключения плагина к приложению.
