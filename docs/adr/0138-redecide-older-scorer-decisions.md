# ADR-0138: Решения старого скорера принимаются заново при первом прогоне новой версии

- **Статус:** Принят
- **Дата:** 2026-11-20
- **Решают:** мейнтейнер (владелец делегировал, BUG-009)
- **Связано:** BUG-009, META-015 ([ADR-0085](0085-episode-numbering-module.md)), META-033 ([ADR-0096](0096-other-language-titles.md)), META-016 (порог «на проверку»), LIB-025 ([ADR-0103](0103-content-kind-classifier.md)), UI-043

## Контекст и проблема

Отчёт владельца на alpha.17 (Windows, русский интерфейс, «чистая установка» через установщик): большая часть фильмов и аниме с английскими и ромадзи-названиями («Princess Mononoke 1997», «Millennium Actress 2001», «Steamboy 2004», «Pale Cocoon», «Youjo Senki», «Psycho-Pass»…) стоит с «?» и без постера, хотя подсказка в проверке верная.

Разбор (живой TMDB на сервере сборки, ответы не в git):

- Свежая медиатека на коде alpha.17 распознаёт весь набор сама: 16 из 16 работ `auto`, оценка 1,0 (у «Tenjou Tenge» 0,99). Порог `AUTO` = 0,92, сравнение с оригинальными и переводными названиями (META-033), типы и год работают.
- Медиатека остаётся при удалении и повторной установке (`%APPDATA%\app.kinolune`, packaging/app/windows/README.md). Медиатека, распознанная alpha.10 (до META-033: имя файла сравнивалось только с русским и оригинальным названием TMDB), после запуска alpha.17 не меняется вовсе: прогон метаданных берёт 0 работ. Все пять фильмов остаются `not_found` (четыре — «?» без постера, «Pale Cocoon» без года — в «Мои видео»), сериалы — только с данными AniList без TMDB.

Причины в коде:

1. META-033 изменил ранжирование, но `MODEL_VERSION` остался `scorer_v1`. Механизм ADR-0085 («автоматические матчи старой версии решаются заново») не сработал.
2. У `not_found` нет версии скорера: такие работы спрашиваются снова только через неделю (`retry_not_found_after_ms`), а `auto_review` с известным TMDB id при месячном обновлении читается по id, и состояние «проверьте» остаётся навсегда.
3. Классификатор LIB-025 переносит фильм без года, для которого ничего не нашлось, в «Мои видео» навсегда («решение прилипает»). Это происходило и по `not_found` старого скорера.
4. Попутно: работа, решённая по кадрам (AniList id, без TMDB), после смены версии брала бы себя в каждом прогоне — метка версии ставилась только при наличии TMDB.

## Решение

- `MODEL_VERSION` = `scorer_v2`. Версия повышается при любом изменении, которое может решить работу иначе (входы, веса, пороги). Правило записано в документации константы.
- Первый прогон новой версии заново решает всё, что решила автоматика старой версии. Это `auto` и `auto_review` матчи скорера (как в ADR-0085) и, что новое, работы `not_found`: на автоматических матчах такой работы теперь ставится версия, нашедшая «ничего». Работа `not_found` без метки текущей версии берётся сразу, а не через неделю. Папочное правило над файлом её не держит: правило решило не её (его матчи — `user_set`), а записываются только данные провайдера.
- Работа, прочитанная по известному id (пользователь, NFO, кадры), получает текущую версию на автоматических матчах и без TMDB — повторных прогонов по кругу нет.
- LIB-025: «ничего не найдено» переводит файл в «Мои видео», только если это сказал текущий скорер. Прилипшее решение помнит версию (`reasons_json` содержит `scorer_v2`). Решение, принятое по `not_found` старого скорера, при следующем скане снова становится «видео» и распознаётся. Один раз на версию: если новый скорер тоже ничего не нашёл, файл возвращается в «Мои видео» и остаётся там.
- Никогда не решаются заново: `user_confirmed`, `user_set` (в том числе матчи папочных правил), NFO, «Это не фильм и не сериал» (`work_reviews`), «Это не то» у папки. Пороги `ACCEPT`, `AUTO`, `REVIEW` и ранжирование не менялись: ложных совпадений не прибавляется. С «?» остаются только настоящая неоднозначность (ничья двух работ — `AMBIGUOUS`, потерянный маркер типа) и отсутствие совпадения.

## Последствия

- Хорошо: медиатека, пережившая обновление или переустановку, получает ответы нового скорера при первом запуске, без действий пользователя. На живом наборе из отчёта: alpha.10 → alpha.17 — 11 из 16 тихо, 0 работ пересмотрено; с исправлением — 16 из 16, у всех TMDB id и постер.
- Плохо: одно повышение версии — один повторный поиск TMDB для каждой автоматически решённой работы (ADR-0085 принимал ту же цену). Подробности, переводы и сезоны берутся из кэша, если он свежий. Для 1000 работ это несколько тысяч запросов, около минуты-двух при лимите TMDB.
- Нейтрально: миграций и изменений FRB API нет; меняются `pa_catalog::metadata` (`pending`, запись `not_found`, метка версии по известному id) и `pa_catalog::content_kind`.

## Как проверяем соблюдение

- `pa-catalog/tests/auto_recognition.rs` (синтетический TMDB в форме ответов `ru-RU`):
  - `a_fresh_library_recognizes_the_report_on_its_own` — 15 названий из отчёта плюс второй сезон «Darker than Black» `auto`; с «?» только «Dune» без года (ничья) и неизвестное название; `clip.mp4` не уходит в TMDB (BUG-005);
  - `decisions_of_an_older_build_are_made_again_on_the_next_run` — медиатека «старой сборки»: 0 из 15 → 13 из 15, плюс 2 решения пользователя, которые не тронуты; «Pale Cocoon» возвращается из «Мои видео»; третий прогон не берёт ни одной работы.
- `pa-catalog/tests/metadata.rs`, `numbering.rs` — версия текущего скорера через `MODEL_VERSION`.
