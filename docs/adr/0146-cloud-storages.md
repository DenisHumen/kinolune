# ADR-0146: Облачные хранилища — MEGA своим клиентом JSON API, Google Drive, OneDrive и Dropbox через OAuth с PKCE

- **Статус:** Предложен
- **Дата:** 2026-11-24
- **Решают:** владелец проекта (набор облаков — решение 2026-11-24), мейнтейнер
- **Связано:** NET-017; NET-004 (контракт `pa-vfs`), NET-011 (менеджер источников), LIB-018 и ADR-0038 (воспроизведение через loopback-прокси), CORE-015 и ADR-0037 (защищённое хранилище), UI-042 (простое «Добавить»), ADR-0004 (своих серверов нет)

## Контекст

NET-017 — облачные хранилища как источники медиатеки: файлы сканируются в общую медиатеку и играют с перемоткой, как SMB или WebDAV. Владелец решил (2026-11-24): Kinolune — украинский продукт, **российских сервисов нет** (Яндекс.Диск убран из задачи); набор — **MEGA** и **Google Drive** в первую очередь, затем **OneDrive** и **Dropbox**.

Ограничения проекта: своих серверов и облака нет (ADR-0004), всё идёт с устройства пользователя; секреты — только в защищённом хранилище (CORE-015); в коде нет client secret; в клиентах нет GPL; ядро синхронное (`pa-vfs`, ADR-0013).

## Решение

### Один крейт `pa-cloud`, один контракт

Новый крейт `core/crates/pa-cloud`: каждое облако — `Drive` (дерево узлов с id: `root`, `children`, `open`), а `CloudFs<D>` превращает любой `Drive` в `pa_vfs::Vfs` только на чтение:

- пути разрешаются через кэш листингов (60 с), источник может начинаться с папки внутри облака (адрес `<облако>:/<папка>`);
- одинаковые имена в одной папке (Google Drive и MEGA это разрешают) получают ` (2)`, ` (3)` перед расширением, порядок устойчивый (по id); `/` в имени заменяется;
- файлы — `RangeFile`: чтение диапазонами с упреждением одного блока (2 МиБ), `hint_random_access` для trickplay читает ровно запрошенное; перемотка — один запрос;
- документы без байтов (Google Docs, ярлыки, OneNote) — `EntryKind::Other`, сканер их пропускает.

Все облака проходят общий контракт `pa_vfs::contract` против моков их API (в тестах — локальный HTTP-сервер, который отвечает как настоящий API).

### MEGA — свой клиент документированного JSON API, не SDK

Официальный SDK MEGA — C++ под BSD-2-Clause (совместим), но это тяжёлая нативная зависимость со своими библиотеками на каждой платформе. Плееру нужно пять команд API (`us0`, `us`, `ug`, `f`, `g`), поэтому клиент написан на Rust поверх уже имеющихся в lock-файле крейтов RustCrypto (`aes`, `ctr`, `pbkdf2`, `sha2`) и `num-bigint`:

- **Вход:** e-mail + пароль (+ код 2FA, если включён: ошибка `-26` → приложение спрашивает код). Ключ пароля — PBKDF2-HMAC-SHA512 100 000 раундов (аккаунты v2) или старый `prepare_key` (v1). Мастер-ключ расшифровывается ключом пароля; id сессии — RSA-расшифровка `csid` закрытым ключом аккаунта (или проверка временной сессии `tsid`). **Пароль не хранится**: в защищённом хранилище — сессия (`sid`, мастер-ключ, handle пользователя). Сессия кончилась — понятная ошибка «войдите снова».
- **Шифрование:** у каждого файла свой ключ AES-128 и nonce; содержимое — AES-128-CTR, счётчик = nonce ‖ номер 16-байтового блока. Любой диапазон расшифровывается с его смещения (поиск в потоке ключей), поэтому перемотка не требует скачивания с начала. Диапазон запрашивается у ссылки загрузки MEGA как `/<начало>-<конец>`. MAC файла не проверяем: плеер читает диапазоны, а не весь файл.
- **Публичные ссылки** (`/folder/<id>#<ключ>`, `/file/<id>#<ключ>`, старые `#F!`/`#!`): без аккаунта. Адрес источника — ссылка **без ключа**, ключ — секрет в защищённом хранилище; на серверы MEGA ключ не уходит.
- Входящие общие папки других пользователей (ключи под RSA-ключами шаринга) пока не показываются — только своё «Облачное хранилище».
- Ключ приложения MEGA (`ak`) необязателен; вшивается из сборки (`PA_MEGA_APP_KEY`), если владелец его получит.

### Google Drive, OneDrive, Dropbox — OAuth 2.0 с PKCE как публичный клиент

- **PKCE S256**, `state`, только чтение: Google `drive.readonly`, Microsoft `Files.Read offline_access`, Dropbox `files.metadata.read files.content.read account_info.read`. Хранится только refresh token (JSON `CloudSecret`); access token живёт в памяти. Ответ 401 — один refresh и повтор. Microsoft ротирует refresh token — новый сразу перезаписывается в защищённом хранилище (`TokenSink`).
- **Redirect:** loopback `http://127.0.0.1:47290/` (RFC 8252 §7.3) на всех платформах, включая Android: ядро поднимает одноразовый слушатель только на 127.0.0.1, принимает ответ браузера и показывает «вернитесь в приложение». Если порт занят — любой свободный (Google и Microsoft не сравнивают порт loopback; у Dropbox зарегистрирован точный адрес). Для своего клиента, зарегистрированного с `kinolune://oauth`, на Android есть переключатель «возвращаться по ссылке»: ссылка приходит через существующий канал `kinolune://` (TvBridge → `app_links.dart`) в ожидающую форму.
- **Client ID проекта** — из сборки (`PA_*_CLIENT_ID`, в Flutter-сборке `CARGO_PA_*`, в репозитории пусто; `.env.example`, `docs/dev/secrets.md`). **Client secret в коде нет.** Google для клиентов «Desktop app» всё равно требует secret; по RFC 8252 §8.5 он не конфиденциален — берётся только из сборки (`PA_GDRIVE_CLIENT_SECRET`) или от пользователя.
- **Свой client ID пользователя** — в «Дополнительно» формы (для Google — и secret). Нужен, пока у сборки нет ключа или пока Google не проверил приложение: `drive.readonly` — restricted scope, публичному приложению нужна верификация (CASA). Client ID хранится в настройках источника, secret — вместе с refresh token.

### Приложение

- Тип источника: `mega`, `gdrive`, `onedrive`, `dropbox` (`pa-sources`), адрес `<облако>:/<папка>` или ссылка MEGA без ключа; имя по умолчанию «Облако · аккаунт».
- `CoreCloud` (FRB): `providers`, `start`/`wait`/`complete`/`finish`/`cancel` для браузерного входа, `add_mega`, `add_mega_link`. Ошибки `mfa_required` и `cancelled` — отдельные коды для формы.
- В «Добавить» — заголовок «Облачные хранилища» и четыре пункта (иконка облака, название текстом — логотипы сервисов не используем). Шаги как у SMB (UI-028/UI-042): кнопка «Войти через браузер» → ожидание → «Вход выполнен: …» → необязательная папка → «Добавить». MEGA: «Аккаунт» (почта, пароль, код 2FA по запросу) или «Ссылка».
- Сканирование и воспроизведение — общие: источник идёт в медиатеку и играет через loopback-прокси (ADR-0038), как SMB.

## Последствия

- Плюс: четыре облака без нативных SDK и без своих серверов; один контракт `pa-vfs`; пароли нигде не хранятся.
- Плюс: MEGA работает и без ключа приложения, ссылки — без аккаунта.
- Минус: для Google без верификации — экран «приложение не проверено» и до 100 пользователей на ключ проекта; иначе свой client ID. Решение о верификации (и платной оценке CASA) — за владельцем.
- Минус: Dropbox в режиме Development ограничен по числу пользователей; заявка на Production — владелец.
- Минус: свой клиент MEGA — своя поддержка протокола; при изменениях API MEGA чинить нам. Покрыто тестами с векторами (NIST SP 800-38A для CTR/ECB, RFC-вектор PBKDF2-SHA512, RSA на простых Мерсенна) и моком, шифрующим как MEGA.
- Синхронизация источника с паролем (SYNC-010) переносит refresh token на другие устройства; у Microsoft ротация может разлогинить одно из них — тогда «войдите снова» на нём.
- Проверка на настоящих аккаунтах — вручную по чек-листу [docs/qa/cloud-storages-checklist.md](../qa/cloud-storages-checklist.md).

## Отклонённые варианты

- **Официальный SDK MEGA** — тяжёлая нативная сборка для 7 платформ ради пяти команд.
- **rclone как библиотека/процесс** — Go, отдельный бинарь на каждую платформу, MIT, но тянет весь rclone; не встраивается в FRB и сторы.
- **Яндекс.Диск** — российский сервис, решение владельца.
- **Схема `kinolune://` по умолчанию на Android** — Google не принимает свои схемы для «Desktop»-клиентов, Dropbox требует точного адреса; loopback работает везде одинаково.
- **Хранить пароль MEGA** — не нужно: сессии достаточно, пароль — лишний риск.
