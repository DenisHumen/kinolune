# ADR-0162: Аккаунты сервера, PASETO-токены и вход с сопряжённых устройств (SRV-003)

- **Статус:** Предложен
- **Дата:** 2026-11-25
- **Решают:** владелец проекта (поручил решать самому, ADR — для записи), мейнтейнер
- **Связано:** SRV-003, SRV-001, SRV-002, SRV-004, SYNC-005, SYNC-008, SYNC-017; [ADR-0004](0004-no-project-servers-local-sync.md), [ADR-0055](0055-profiles-parental-filters.md), [ADR-0118](0118-openapi-contract.md), [ADR-0157](0157-server-cluster-sync.md) §5; `docs/research/04` §1.5, §5.3

## Контекст и проблема

Медиасервер (`alpha-media`) уже умеет сопрягать устройства (SYNC-005: SPAKE2 по 6-значному коду или QR) и пускает в хаб синхронизации только устройства семьи. Пользователей у сервера не было: приглашения, список и отзыв устройств работали только с самой машины (loopback). Поэтому сервер по умолчанию слушал только `127.0.0.1`.

ROADMAP SRV-003 требует:

- локальных пользователей (администратор и домочадцы) с Argon2;
- PASETO v4.public: access-токен на 15 минут, refresh с ротацией;
- PIN-профилей;
- ограничения частоты входа;
- pairing клиента по QR или коду без облачного аккаунта, полностью офлайн.

«Done when»: тесты перебора (блокировка), ротации и отзыва токенов.

Ограничения:

- облака проекта нет (ADR-0004);
- только MPL/MIT/Apache-крейты (`cargo deny`);
- контракт API генерируется из кода и меняется только добавлениями (ADR-0118);
- серверы кластера сопрягаются так же, как устройства (ADR-0157 §5);
- протокол хаба параллельно меняет SYNC-017, его трогать нельзя.

## Факторы решения

- Для семьи — просто: администратор создаётся один раз, ребёнок выбирает профиль и вводит PIN.
- Утёкший токен живёт недолго, украденный refresh замечается, отозванное устройство теряет доступ сразу.
- Никаких внешних сервисов и аккаунтов; всё в каталоге данных сервера.
- Минимум новых зависимостей; криптография — из уже проверенных крейтов workspace.
- Совместимость: существующие эндпоинты, протокол хаба и pairing не ломаются.

## Рассмотренные варианты

1. **Сессии в cookie + CSRF.** Удобно для веб-админки, неудобно для нативных клиентов и ТВ.
2. **JWT (HS256/RS256).** Известный формат, но алгоритм выбирается заголовком токена (классические атаки `alg: none` и подмена алгоритма); задача прямо называет PASETO.
3. **PASETO v4.public на `ed25519-dalek` + непрозрачные refresh-токены в SQLite.** Выбран.
4. **Крейт `pasetors`.** Готовая реализация, но тянет `ed25519-compact`, `orion` и другие крейты. Сам `v4.public` — это PAE плюс подпись Ed25519, около 60 строк поверх `ed25519-dalek`, который уже есть в workspace (ключи устройств SYNC-005).

## Решение

### Аккаунты

- `auth.sqlite3` в каталоге данных: таблицы `users`, `sessions`, `refresh_tokens`.
- Роли: `admin` и `member`. Имя уникально без учёта регистра.
- Пароль (8–256 символов, NIST SP 800-63B) и PIN (4–8 цифр) хранятся как хэши Argon2id в формате профилей ядра (`pa_library::profiles::hash_secret` / `pin_matches`). Параметры: 19 МиБ, 2 прохода — минимум OWASP; они записаны в каждом хэше и могут расти.
- У администратора обязателен пароль. У домочадца — пароль и/или PIN.
- Неизвестное имя проверяется против фиктивного хэша, чтобы по времени ответа нельзя было понять, есть ли такой пользователь.

### Первый запуск

- Пока администратора нет, сервер пишет одноразовый код настройки в `<data_dir>/setup-code.txt` (права 0600) и пишет в лог путь к файлу, но не сам код.
- `POST /api/v1/auth/setup` создаёт первого администратора:
  - с самой машины (loopback) — без кода;
  - с другой машины — с кодом из файла.
- Пока администратора нет, loopback администрирует без входа. Так продолжают работать существующие сценарии и тесты SYNC-005. Это доверие — **только к loopback, никогда к пирам из LAN**: до появления администратора пиру из сети доступны лишь `/health`, `/healthz` и `POST /api/v1/auth/setup` с одноразовым кодом, всё остальное — 403.
- Когда администратор создан, файл кода удаляется, а приглашения, список устройств, отзыв и управление пользователями требуют токен администратора.
- Опция `[auth] trust_loopback = true` возвращает доверие к loopback (одноместная машина).

### Токены

- **Access-токен:** PASETO `v4.public`, подписан ключом Ed25519 сервера.
  - Ключ лежит в зашифрованном файле секретов рядом с ключами семьи: `server.auth.signing-key` в `pa_secrets::EncryptedFileStore`, общий экземпляр с `Pairing`.
  - Claims: `iss` (id сервера), `sub`, `sid` (сессия), `scope`, `amr` (как открыта сессия), `dev` (устройство), `iat`, `exp` (RFC 3339), `jti`.
  - Footer: `{"kid": …}` — первые 8 байт SHA-256 публичного ключа, задел на ротацию ключа.
  - Живёт 15 минут.
  - Проверяется на каждом запросе: подпись, `iss`, `exp`, затем **сессия в БД не отозвана** и, если сессия привязана к устройству, **устройство ещё в семье**. Отзыв действует сразу, а не через 15 минут.
  - Реализация проверена официальными векторами `paseto-standard/test-vectors` (4-S-1…3).
- **Refresh-токен:** 256 случайных бит (base64url). В БД хранится только SHA-256. Живёт 30 дней.
  - Одноразовый: обмен (`/api/v1/auth/refresh`) помечает его использованным и выдаёт новую пару в той же сессии.
  - **Повторное предъявление использованного токена — признак кражи: отзывается вся сессия** (RFC 9700 §4.14.2). Клиенты обязаны обновлять токен последовательно.
- `/api/v1/auth/logout` отзывает сессию по refresh-токену.
- Смена пароля или PIN завершает остальные сессии пользователя. Удаление пользователя завершает все его сессии.
- Последнего администратора удалить нельзя.

### Устройства и PIN-профили

1. Клиент сопрягается с сервером как раньше (SYNC-005: код или QR из `POST /api/v1/pair/invite`), без облачного аккаунта.
2. Устройство берёт `POST /api/v1/auth/challenge` (одноразовый nonce на 60 с) и подписывает его ключом устройства тем же транскриптом, что и в хабе: `pa_pairing::auth::prove(identity, server_id, nonce, challenge)`. Затем `POST /api/v1/auth/device` выдаёт **сессию устройства** (`scope: device`).
3. С сессией устройства клиент показывает профили (`GET /api/v1/auth/profiles`), и домочадец входит по PIN (`POST /api/v1/auth/pin`). **PIN работает только на сопряжённом устройстве.** Пароль работает везде, например в веб-админке.
4. Вход по паролю с токеном устройства в заголовке тоже привязывает сессию к устройству.
5. Администрирование требует администратора, вошедшего **паролем**: PIN — для выбора профиля на диване, а не для управления.

Отзыв устройства (`DELETE /api/v1/devices/{id}` или обновление `family` от другого члена семьи) закрывает его соединения с хабом, как раньше, и отзывает все сессии, привязанные к нему: и сессию устройства, и сессии людей, вошедших на нём. Их access- и refresh-токены сразу перестают работать.

Серверы кластера (ADR-0157 §5) сопрягаются тем же `/api/v1/pair` и могут получить сессию устройства тем же challenge. Протокол pairing не менялся.

### Защита от перебора

Счётчики неудач хранятся в памяти:

- **по аккаунту:** 5 попыток бесплатно, затем блокировка на 30 с, дальше удваивается до 15 минут;
- **по адресу клиента:** 20 попыток, затем такая же схема.

Во время блокировки отказ приходит и на правильный пароль: HTTP 429 с `Retry-After`. Успешный вход сбрасывает счётчик аккаунта. Счётчик забывается через час без неудач. Так же ограничены PIN, вход устройства и неверные коды настройки. 4-значный PIN при такой схеме перебирается годами.

Блокировку можно вызвать злонамеренно: злоумышленник в LAN заблокирует администратора на 15 минут. Это принято — дешевле, чем подбор, и уже открытые сессии не страдают.

### Сеть: домашняя сеть по умолчанию, интернет — никогда

**Решение владельца 2026-11-25:** «В домашней сети да, по умолчанию открыть».

- Адрес по умолчанию — `0.0.0.0:8487`: все IPv4-интерфейсы, чтобы устройства дома находили сервер (mDNS-анонс SRV-004 и TLS остаются включены). `[::]` — явной настройкой `listen`.
- Кого пускать, решает настройка `clients` (`ALPHA_MEDIA_CLIENTS`):
  - `lan` (по умолчанию) — loopback, RFC 1918 (10/8, 172.16/12, 192.168/16), IPv4 link-local 169.254/16, IPv6 ULA fc00::/7 и link-local fe80::/10; IPv4-mapped IPv6 приводится к IPv4;
  - `local` — только эта машина (mDNS тогда не анонсируется);
  - `any` — все адреса, включая интернет: только явным выбором, в лог пишется предупреждение, в документации — тоже.
- CGNAT 100.64/10 в `lan` **не входит**: там живут другие абоненты провайдера. Tailscale и подобные VPN — через `clients = "any"` на свой риск или `listen` на адрес VPN.
- Отказ — сразу после `accept`, до TLS и HTTP: соединение закрывается молча (в лог — только debug, чтобы сканирование не заливало журнал).
- UPnP и проброса портов нет и не будет: сервер сам себя в WAN не открывает. Требование SRV-017 «по умолчанию сервер не слушает WAN» остаётся верным: даже при пробросе порта роутером публичные адреса отклоняются.
- Обратный прокси на той же машине приходит с loopback и пропускается; фильтровать внешних клиентов — его забота.

### HTTP и контракт

- Слой `authenticate` проверяет `Authorization: Bearer` у всех `/api/`-запросов, где он есть: неверный, просроченный или отозванный токен даёт 401. Исключение — `/refresh` и `/logout`, у них учётные данные в теле.
- Хаб `/api/v1/sync` затронут только этим слоем. Устройства по-прежнему аутентифицируются ключами в протоколе (SYNC-005), так что изменения SYNC-017 не задеты.
- Новые эндпоинты: `/api/v1/auth/{setup,login,pin,challenge,device,refresh,logout,me,profiles}`, `/api/v1/users`, `/api/v1/users/{id}`.
- В OpenAPI добавлена схема безопасности `bearer`. У существующих операций добавились только ответы 401 и 403 — по правилам ADR-0118 это совместимо. Версия API — **1.1**.

## Последствия

**Плюсы:**

- Отзыв устройства или сессии действует мгновенно.
- Кража refresh-токена обнаруживается.
- Перебор PIN и паролей практически невозможен.
- Никаких облачных аккаунтов.
- Новых крейтов из реестра нет: `ed25519-dalek`, `sha2`, `base64`, `getrandom`, `argon2` уже были в workspace.

**Минусы и риски:**

- Каждый запрос с токеном читает `auth.sqlite3`. Для домашнего сервера это микросекунды; при необходимости можно добавить кэш отозванных сессий.
- Счётчики блокировок живут в памяти и сбрасываются при перезапуске. Перезапустить чужой сервер злоумышленник не может, так что это принято.
- Блокировку можно вызвать злонамеренно (см. выше).
- Ротация ключа подписи пока не реализована (есть только `kid`).
- Клиенты должны обновлять refresh-токены последовательно: два параллельных обмена одного токена отзовут сессию.
- В debug-сборках `argon2` и `blake2` собираются с `opt-level = 3`, иначе тесты хэшей идут секундами.

**Дальше (не в этой задаче):**

- клиент в ядре (SRV-006): хранение токенов в `pa-secrets`, автообновление, экран выбора профиля;
- привязка аккаунтов сервера к профилям медиатеки (ADR-0055);
- веб-админка (`server/web/`);
- адрес сервера в QR-приглашении при `0.0.0.0`: сейчас QR несёт адрес только при конкретном `listen`, иначе клиент находит сервер по mDNS.
