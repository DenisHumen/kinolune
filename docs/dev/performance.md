# Бюджеты производительности UI (QA-006)

> Как мерить, что намерено и что считается регрессией. Бюджеты — из [ROADMAP](../ROADMAP.md) (QA-006) и [тест-стратегии](testing.md) §1: сетка на 10 000 элементов — 60 fps на среднем телефоне и Android TV-стике, холодный старт на десктопе — меньше 2 с, регрессия больше 20 % помечает PR. Контекст — 02 §1.1 (плавный скролл тысяч элементов), 01 §4.6 (blur выключается на слабом железе и программном рендере).

## Коротко

- **Холодный старт на десктопе — 0,42–0,49 с** до главной с обложками (Linux, release, библиотека на 10 000; бюджет — 2 с). Первый запуск после сборки — 1,85 с.
- **Сетка на 10 000 элементов**: UI-поток укладывается в кадр везде, где мерили (p90 build 5,7–8,4 мс на Linux, 1,2–1,6 мс на эмуляторе Android). Растеризация на стендах программная (llvmpipe, SwiftShader), поэтому **60 fps на телефоне и ТВ-стике этими замерами не подтверждено и не опровергнуто** — нужны настоящие устройства; оценка — ниже.
- Найдено и исправлено: поиск локальных постеров O(N²) на UI-потоке (277 с → 55 мс на 10 000 файлов в одной папке) и падение ряда «Продолжить» при повторной подписке.
- Регрессия больше 20 % помечается: намеренно замедленный прогон (+3 мс на кадр) — 12 из 12 метрик build с пометкой и аннотацией `::warning`; контрольный прогон — 0.
- CI: информационный job Linux/Xvfb на PR, ничего не блокирует; база для раннера GitHub — за владельцем (см. «CI»).

## Как устроено

- **Сценарии** — `clients/flutter/app/integration_test/perf_test.dart`, profile-сборка, `flutter drive --profile`, кадры — из `FrameTiming` движка (`IntegrationTestWidgetsFlutterBinding.watchPerformance`, политика кадров `benchmarkLive`):

  | Сценарий | Что делает |
  |---|---|
  | `grid_scroll_demo` | сетка «Фильмы» на 10 000 тайтлов демо-библиотеки (обложки рисуются кодом, `GeneratedArt`) |
  | `grid_scroll_posters` | то же, у каждого тайтла — PNG-постер 500×750 с диска (48 разных), декодируется в размер ячейки, как файлы кэша обложек LIB-013 |
  | `grid_scroll_core` | настоящее Rust-ядро: 10 000 файлов в одной папке `Movies/`, скан ядром, сетка на `RustLibraryQueries` (страницы по 120) |
  | `home_scroll` | главная демо-библиотеки: вниз до конца и обратно, затем вдоль трёх рядов |
  | `detail_open` | шесть раз: тап по постеру → страница фильма (до кнопки Play) → назад |
  | `osd_toggle` | плеер на фейковом движке: восемь раз скрыть и показать OSD (fade 0,25 с) |

  Скролл сетки детерминированный: `animateTo` на 20 000 px со скоростью 2500 px/с, обратно на 10 000 px со скоростью 5000 px/с, прыжок к 90 % и до конца, затем четыре флинга. Каждый сценарий прогоняется трижды (`KINOLUNE_PERF_REPEATS`, по умолчанию 3), драйвер оставляет лучший прогон по p90 build: на общей машине соседняя нагрузка только замедляет. Разброс прогонов — в `build_p90_of_runs` результата.
- **Метрики** (`tool/perf/perf_report.dart`): время build (UI-поток: build, layout, запись paint) и raster (растеризация) по кадрам — среднее, p50, p90, p99, худшее; **jank** — кадры, у которых build *или* raster дольше 16,7 мс (фазы идут конвейером, любая из них сверх бюджета роняет кадр).
- **Холодный старт** — `lib/services/startup_probe.dart`: с `KINOLUNE_STARTUP_PROBE=1|exit` (переменная окружения или dart-define) приложение печатает `KINOLUNE_STARTUP first_frame_ms=… library_visible_ms=…` — от запуска процесса (`/proc/self/stat`) до конца растеризации первого кадра и первого кадра с обложками медиатеки (`Artwork`: hero главной, карточка ряда или сетки; на телефоне ряды постеров начинаются ниже первого экрана). Linux и Android: старт процесса из `/proc`, конец кадра из `FrameTiming` (одни монотонные часы); вывод — через `print` (на Android он попадает в logcat). Без переменной ничего не регистрируется.
- **Скрипт** — `clients/flutter/app/tool/perf_bench.sh linux|android [--core] [--runs N] [--baseline F] [--github]`: сценарии, холодный старт (Linux — release-бандл, N запусков; Android — profile-APK с пробой), `build/perf/results.json`, сравнение с базой.
- **Сравнение** — `dart run tool/perf/compare.dart <база> <результат> [--github] [--fail-on-regression]`: таблица Markdown; регрессия — отслеживаемая метрика хуже базы больше чем на 20 % **и** больше порога шума (0,5 мс для времени кадра, 1 п. п. для доли jank, 100 мс для старта). Отслеживаемые метрики — поле `tracked` базы (суффиксы имён), по умолчанию build p50/p90, raster p90, jank и старт; остальное печатается с пометкой `info`. С `--github` — аннотации `::warning` на PR и таблица в сводке job.
- **Базы** — `clients/flutter/app/perf/baseline/*.json` (тот же формат, что `results.json`, плюс `tracked`).

## Замеры

Все замеры — 15 ноября 2026, ветка `feat/QA-006-perf-budgets`, Flutter 3.50.0, profile-сборки (холодный старт Linux — release). Сервер сборки общий: 32 потока, во время замеров load average 25–50 (сборки других агентов, виртуальные машины). Поэтому каждый сценарий — лучший из нескольких прогонов (в замерах ниже — из двух; теперь по умолчанию из трёх), старт — лучший и медиана из семи.

### Linux, Xvfb (программный рендер)

Контейнер Ubuntu 24.04 (`tool/perf/linux.Dockerfile`), закреплён за 8 ядрами (`--cpuset-cpus`; лимит `--cpus` давал троттлинг CFS и разброс в разы), Xvfb 1920×1080, Mesa llvmpipe (`LP_NUM_THREADS=4`), окно приложения 1280×720. База — [`perf/baseline/linux-xvfb.json`](../../clients/flutter/app/perf/baseline/linux-xvfb.json).

Время кадра, мс, p50 / p90 / p99:

| Сценарий | Кадров | build (UI-поток) | raster (llvmpipe) | jank |
|---|---:|---|---|---:|
| `grid_scroll_demo` | 419 | 6,1 / 10,6 / 21,8 | 73,9 / 84,6 / 98,8 | 100 % |
| `grid_scroll_posters` | 1054 | 3,4 / 5,7 / 9,7 | 28,4 / 33,3 / 38,0 | 99,7 % |
| `grid_scroll_core` | 880 | 4,8 / 8,4 / 12,8 | 34,6 / 42,4 / 57,6 | 100 % |
| `home_scroll` | 136 | 0,3 / 0,5 / 2,1 | 65,4 / 80,4 / 99,9 | 100 % |
| `detail_open` | 146 | 0,2 / 2,0 / 10,5 | 40,7 / 108,1 / 119,2 | 100 % |
| `osd_toggle` | 273 | 0,2 / 0,6 / 1,0 | 29,2 / 41,2 / 49,7 | 76 % |

Прочее из того же прогона: первая карточка сетки — 0,82–0,86 с после `pumpWidget` (демо, постеры, ядро); скан 10 000 файлов ядром — 3,6 с (бюджет тест-стратегии — 60 с); открытие страницы фильма (тап → кнопка Play) — медиана 56 мс.

Что из этого следует:

- **UI-поток укладывается в бюджет кадра**: p90 build — 5,7 мс у сетки с настоящими постерами и 8,4 мс у сетки на ядре, p99 — 9,7 и 12,8 мс (бюджет 16,7 мс). Главная, страница фильма и OSD почти ничего не стоят UI-потоку. Худший — демо-сетка (p90 10,6, p99 21,8 мс): обложки демо рисуются кодом (`GeneratedArt`: градиенты и кривые на каждую карточку); в настоящей медиатеке их нет.
- **Растеризация под Xvfb — это CPU-растеризатор**, 30–110 мс на кадр, отсюда «100 % jank». Это не число приложения: на GPU десктопа или телефона raster другой. Поэтому для Xvfb база отслеживает только build и старт, raster печатается как `info`.

Release-бандл, библиотека ядра на 10 000 фильмов (тот же скан), `XDG_DATA_HOME` на неё, Xvfb, без D-Bus и связки ключей (секреты — в зашифрованном файле, CORE-007). Семь запусков подряд:

| | первый кадр | первый кадр с медиатекой |
|---|---:|---:|
| лучший | 300 мс | 420 мс |
| медиана | 336 мс | 475 мс |
| первый запуск после сборки | 1087 мс | 1845 мс |

**Бюджет «меньше 2 с» выполнен** с запасом: 0,42–0,49 с до главной с постерами. Первый запуск после сборки медленнее (1,8 с): файлы бандла и базы ещё не в кэше страниц, и это ближе к «первому старту после установки», чем к обычному. Повторы позже: лучший 456 и 421 мс, медиана 581 и 500 мс (нагрузка сервера; второй повтор — уже с пробой, которая считает и hero главной, см. ниже). Кэш страниц ОС не сбрасывался (нужен root), «холодный» здесь — новый процесс.

### Android, эмулятор (программный рендер)

Свой эмулятор на сервере сборки (`emulator-5600`, только он: скрипт отказывается работать с чем-то, кроме эмулятора): Android 14, образ `sdk_phone64_x86_64`, профиль pixel_5 (1080×2340), 4 vCPU с KVM, `-gpu swiftshader_indirect` — **растеризация на CPU (SwiftShader), это не числа телефона**. Сценарии запускаются profile-APK без `flutter drive` (тот опрашивает все устройства adb, а к серверу подключены настоящие телефоны), результаты — через logcat. Окно телефона: сетка в две колонки, на экране меньше карточек, чем на десктопе. База — [`perf/baseline/android-emulator.json`](../../clients/flutter/app/perf/baseline/android-emulator.json).

Скан 10 000 файлов ядром на эмуляторе — 7,8 с; первая карточка сетки — 0,80–0,88 с; страница фильма — медиана 21 мс.

Холодный старт (profile-APK с пробой, семь запусков, библиотека ядра на 10 000 фильмов): первый кадр — медиана 232 мс (198–273), первый кадр с обложками — медиана 455 мс (232–614) от старта процесса. ### Средний телефон и ТВ-стик

Честной оценки «60 fps или нет» по этим замерам нет: и Xvfb, и эмулятор растеризуют на CPU, а на телефоне и стике растеризует GPU — именно то, что не измерено.

Оценить можно только UI-поток, и то по порядку величины. Опорные числа сняты на x86 (i9-14900KF, до 6 ГГц, под нагрузкой соседей):

- **Телефон.** Эмулятор (раскладка телефона, KVM, то же ядро x86) — p90 build сетки 1,2–1,6 мс, p99 до 5 мс. Ядра Cortex-A76/A78 среднего телефона в однопоточных задачах медленнее примерно в 3 раза: p90 около 4–5 мс, p99 около 15 мс — в бюджете 16,7 мс. Растеризацию на GPU (Mali/Adreno среднего класса) не оценить: не мерили.
- **ТВ-стик.** Раскладка ТВ ближе к десктопу (1920×1080, больше карточек в кадре). На Linux p90 build сетки 5,7–8,4 мс, но там кадр приходит раз в 30–40 мс (растеризация на CPU) и несёт прокрутку двух-трёх кадров; при 60 fps работы на кадр меньше — порядка 3–4 мс. Cortex-A55 стика (1,8–2 ГГц) медленнее в однопоточных задачах раз в 10: **около 30–40 мс на кадр, то есть UI-поток сетки на стике, скорее всего, в 16,7 мс не укладывается** и даст рывки на быстрой прокрутке.

Это оценка, не замер. Проверить — `tool/perf_bench.sh android` на настоящих устройствах (device lab, testing.md §7); сценарии готовы, нужно устройство и снятое ограничение «только эмулятор» (см. «Решения владельца» в PR). Если оценка для стика подтвердится, следующие шаги — дешевле карточка сетки (меньше виджетов на постер: `LayoutBuilder` на каждую ячейку, `KFocusable` с анимацией масштаба, бейджи) и меньший `cacheExtent` на слабом железе.

## Найдено и исправлено

1. **Поиск локальных постеров — O(N²) на UI-потоке** (`pa_library`, `RustLibrary._item`). Для каждого элемента без постера провайдера ядро-обёртка листала папку файла (`listSync`) и кэшировала ответ только по пути файла. Плоская папка `Movies/` на 10 000 фильмов листалась 10 000 раз на каждый список. Замер (`packages/pa_library/tool/bench_local_images.dart`, сервер): **27,7 мс на элемент — 277 с на список из 10 000**; сетка на ядре не показала ни одной карточки за минуты, профиль VM: 25 % в `findLocalImage`, 8 % в `getdents64`. Исправление — `LocalImageIndex`: папка листается один раз до следующего скана или события watcher-а. После: **55 мс на все 10 000**, первая карточка сетки на ядре — 0,84–0,93 с. Тест — `scanner_test.dart` («LocalImageIndex finds what findLocalImage finds»).
2. **Ряд «Продолжить» на главной падал при повторной подписке** («Stream has already been listened to»): источники ряда (VOD Twitch, TWI-013) создавались один раз на главную, а ряд подписывается заново, когда главная строит его снова (например, когда появляется hero и ряд сдвигается в списке). Вместо ряда — коробка ошибки. Найдено сценарием `home_scroll`; исправление — свежие источники на каждую подписку (`HomeFeed.continueRow(extra:)`), тест — `home_test.dart` («the Continue row subscribes again without errors»: без исправления падает с этой ошибкой).

Не исправлялось (замечено): сканер v0 (`library.dart`, запасной путь без ядра) вызывает `findLocalImage` на каждый новый файл — тот же O(N²), но один раз при скане; демо-обложки `GeneratedArt` — самый дорогой build, но только в демо-режиме.

Контрольные прогоны без замедления на том же стенде, той же базой:

- первый — **ни одной регрессии**: build p50/p90 от −11 до +6 % (кроме OSD p50 −47 %: 0,17 → 0,09 мс, под порогом шума 0,5 мс), лучший старт +7 и +9 %;

У сетки на ядре в том же прогоне один из двух прогонов был 40,8 мс, второй 8,7 мс — «лучший из N» спас.

Отсюда «лучший из трёх» по умолчанию и то, что job в CI только помечает, но не блокирует: на сильно загруженной общей машине ложные срабатывания остаются возможны.

Порог шума и «лучший из N» появились после первых прогонов: без них неизменный код на этом сервере давал «регрессии» до +500 % (троттлинг CFS при `--cpus=8`, медиана старта под нагрузкой +22 %).

## CI

`.github/workflows/perf.yml` — job «UI perf (Linux, Xvfb, informational)»: на PR (открытие и «ready», как `flutter.yml`) и вручную; `tool/perf_bench.sh linux --core --runs 5 --github`. Шаг с `continue-on-error`, job не входит в `flutter-green` и ничего не блокирует; при регрессии — аннотации на PR и таблица в сводке job, результаты — артефакт `perf-linux-xvfb`. Сравнение — с `perf/baseline/linux-ci.json`; пока её нет, job только публикует числа. Базу для CI нужно снять на самом раннере GitHub (другое железо, чем у сервера): взять `results.json` из артефакта первого прогона в `main`, добавить `tracked` как в `linux-xvfb.json` и закоммитить как `linux-ci.json`. Android в CI не замеряется: эмулятор на раннере без KVM-ускорения GPU нестабилен и в разы медленнее — шум больше 20 %.

## Что не проверено

- Настоящие телефоны, Android TV-стик, GPU десктопа: ничего из этого не мерилось (см. выше).
- Job CI ни разу не запускался (draft PR; базы `linux-ci.json` нет).
- Холодный старт с пустым кэшем страниц ОС и на HDD.
